# Аудит выполнения задач LR-BE-0001 — LR-BE-1509

Дата аудита: 2026-08-26. Статусы сверены с кодом, миграциями и тестами текущей
ветки, а не только с историей слияний. `Частично` означает, что контракт или
реализация в памяти есть, но производственное требование (прежде всего
PostgreSQL либо настоящий внешний сервис) не закрыто.

## Сводная карта готовности

Эта таблица описывает не наличие файлов, а готовность этапа в рабочем контуре.
`Прототип` означает, что предметная логика или HTTP-обработчик полезны для
следующей реализации, но состояние ещё хранится в памяти. `Не подключено`
означает, что код не включён в `cmd/api`, `cmd/worker` или `cmd/scheduler`.

| Этап | Состояние | Что это означает сейчас |
|---|---|---|
| 0 | Частично | Архитектурные правила и ADR приняты; отсутствующие `frontend` и `infra` не мешают текущей разработке backend. |
| 1–3 | Готово | Основа, пользовательский контур, организации, точки и каталог работают с PostgreSQL. |
| 4 | Частично | Приём и сохранение событий готовы; полный набор живых сценариев Telegram не проверен. |
| 5 | Частично | Канонический контур готов; загрузка двоичных вложений и живые направления Telegram остаются неподтверждёнными. |
| 6 | Готово | PostgreSQL-задания, проверки по расписанию и исходящий журнал подключены к рабочим процессам. |
| 7 | Готово | Opportunity, история этапов, ограничение одной активной записи и REST API работают с PostgreSQL. |
| 8 | Готово | `NO_RESPONSE` проходит рабочий контур PostgreSQL: сообщение, планирование, повторное чтение, дедупликация и автоматическое закрытие. |
| 9 | Готово | Radar, команды Risk, PostgreSQL-проекция и межпроцессные SSE-сигналы подключены к рабочим командам. |
| 10–12 | Прототип, не подключено | Уведомления, действия, результаты и выручка проверены преимущественно в памяти. |
| 13–14 | Прототип, не подключено | Контракты AI Node и анализа существуют, но долговечный серверный контур не реализован. |
| 15 | Частично, не подключено | Средство измерения есть; модель не зафиксирована без набора 300–500 случаев и испытания на целевом оборудовании. |

## Этап 0 — Architecture / Repository Freeze

  предусмотренные картой `frontend` и `infra` отсутствуют, часть platform-каталогов
  остаётся пустой.
- **LR-BE-0002 — частично.** На реализованных модулях видны слои domain,
  application, infrastructure и transport, но шаблон не создан для большинства
  доменов из спецификации.
- **LR-BE-0003 — выполнено.** Есть статический architecture check и его тесты.
- **LR-BE-0004 — выполнено.** Приняты 31 ADR, фиксирующие исходные решения.
- **LR-BE-0005 — выполнено.** MVP non-goals вынесены в отдельный документ.

## Этапы 2–7 — базовые бизнес-модули

- **LR-BE-0201 — выполнено.** User и tenant-independent PostgreSQL repository
  используют UUIDv7-compatible IDs, canonical email и UTC timestamps.
- **LR-BE-0202 — выполнено.** Пароли хэшируются Argon2id в PHC format;
  plaintext не сохраняется и не попадает в публичные ответы.
- **LR-BE-0203 — выполнено.** Реализованы server-side opaque sessions с 256-bit
  token, SHA-256 digest в PostgreSQL, expiry, revocation и atomic rotation.
- **LR-BE-0204 — выполнено.** Organization является tenant и создаётся
  транзакционно вместе с OWNER Membership.
- **LR-BE-0205 — выполнено.** Membership поддерживает OWNER/MANAGER и active,
  invited, disabled statuses.
- **LR-BE-0206 — выполнено.** Центральный permission resolver переводит роль
  Membership в named permissions; MANAGER не получает settings permissions.
- **LR-BE-0207 — выполнено.** Location хранится tenant-scoped с IANA timezone,
  active state и response threshold 1-1440 минут (default 45).
- **LR-BE-0208 — выполнено.** Полное недельное расписание из семи дней
  валидируется и заменяется атомарно вместе с timezone Location.
- **LR-BE-0209 — выполнено.** Подключены register/login/logout/refresh/me,
  HttpOnly SameSite=Strict cookie и browser Origin validation.
- **LR-BE-0210 — выполнено.** Подключены create/get/update Organization API;
  update защищён `organization.manage`.
- **LR-BE-0211 — выполнено.** Подключены list/create/update Location и replace
  business-hours API с явным `X-Tenant-ID`.
- **LR-BE-0212 — выполнено.** Есть isolated PostgreSQL harness для Tenant A/B и
  integration exit-gate test: onboarding, relogin persistence, MANAGER denial и
  cross-tenant 404/403 без раскрытия данных.
- **LR-BE-0301 — выполнено.** Добавлен `ServiceCatalogItem` domain с display и
  normalized name, optional Location, active state и nullable price range.
- **LR-BE-0302 — выполнено.** Миграция `service_catalog_items` использует
  tenant/location composite FK, `NUMERIC(14,2)`, DB checks и tenant indexes.
- **LR-BE-0303 — выполнено.** Точная decimal-модель запрещает JSON number,
  отрицательные/слишком точные суммы и диапазон `price_from > price_to`;
  REST всегда возвращает две дробные цифры.
- **LR-BE-0304 — выполнено.** Подключены OWNER-only list/create/update и
  idempotent soft-deactivate API `/api/v1/services` с явным `X-Tenant-ID`.
- **LR-BE-0305 — выполнено.** Unit и isolated PostgreSQL tests покрывают
  nullable цены без догадок, OWNER/MANAGER, tenant A/B, foreign Location,
  cross-tenant 404 и отсутствие чужих данных в list.
- **LR-BE-0401 — выполнено.** Добавлен tenant-scoped `ChannelConnection` с
  provider, capabilities, optional Location, безопасным verifier hash и
  PostgreSQL constraints/composite tenant FK.
- **LR-BE-0402 — выполнено.** Health хранит `ACTIVE`, `DEGRADED`, `ERROR` или
  `DISCONNECTED`, timestamps последнего события/успеха/ошибки и безопасный error
  code; valid event восстанавливает здоровье development-коннектора.
- **LR-BE-0403 — выполнено.** Domain-контракт Connector определяет Provider,
  VerifyEvent, NormalizeEvent и Health; отдельная capability извлекает внешний
  event ID до постановки normalize work.
- **LR-BE-0404 — выполнено.** `raw_events` хранит JSONB payload и SHA-256,
  tenant/connection/provider scope, processing status и уникальность
  `(connection_id, external_event_id)`.
- **LR-BE-0405 — выполнено.** Короткая PostgreSQL-транзакция атомарно сохраняет
  новый RawEvent, ровно одно версионированное событие исходящего журнала и
  состояние подключения; webhook отвечает до канонизации и AI. Временные записи
  этапа 4 перенесены миграцией 000007 и удалены только после сохранения намерений.
- **LR-BE-0406 — LR-BE-0408 — выполнены.** TEST, IMPORT и GENERIC_WEBHOOK имеют
  детерминированные local adapters с secret verification, строгим fixture
  envelope, external ID и normalization fixture.
- **LR-BE-0409 — частично.** Connected Business Bot connector вызывает
  `setWebhook`, сверяет `getWebhookInfo`, выполняет `deleteWebhook`, проверяет
  официальный secret-token header и преобразует `business_connection`,
  `business_message`, edit/delete. Токен хранится только в зашифрованном виде.
  Обязательный real-account spike выше по-прежнему не выполнен, поэтому задача
  не переводится в состояние «выполнено» только по автоматизированным тестам.
- **LR-BE-0410 — выполнено.** OWNER-only connect/list/idempotent disconnect/health
  API подключён к runtime; cross-tenant ID возвращается как missing. Webhook
  endpoint аутентифицируется provider secret без user session.
- **LR-BE-0411 — выполнено.** Модульные, хранилищные и сквозные HTTP/PostgreSQL
  тесты доказывают, что 10 одинаковых доставок дают один RawEvent и одно событие
  канонизации; тот же внешний ID с другим содержимым даёт конфликт.
- **LR-BE-0412 — выполнено.** Неверный secret ничего не сохраняет; корректно
  аутентифицированный malformed payload сохраняется один раз как `FAILED` без
  намерения канонизации, включая сохраняющую исходные байты оболочку base64 для
  данных, не являющихся JSON.
- **Exit Gate этапа 4 — частично.** Persist-once, быстрый `202` и независимость
  от downstream AI доказаны для local/fixture adapters. Настоящий Telegram
  update нельзя подтвердить до выполнения feasibility spike с credentials.
- **LR-BE-0501 — выполнено.** Определены строгие канонические события
  `message.received.v1`, `message.edited.v1` и `message.deleted.v1` с направлением,
  видом сообщения, ссылкой на исходное событие, контактом, ответом, вложениями и
  произвольными метаданными в объекте JSON.
- **LR-BE-0502 — выполнено.** Контакт создаётся при первой встрече внешней
  личности и затем разрешается через неё; имя, телефон и почта обновляются только
  данными не старше уже сохранённых.
- **LR-BE-0503 — выполнено.** Уникальность внешней личности учитывает
  организацию, поставщика, подключение и внешний идентификатор; два подключения
  с одинаковым идентификатором контакта не склеиваются.
- **LR-BE-0504 — выполнено.** Переписка создаётся один раз на пару
  `(connection_id, external_id)` и повторно используется следующими сообщениями.
- **LR-BE-0505 — выполнено.** Каноническое сообщение сохраняется в PostgreSQL;
  повтор с тем же содержимым безопасен, а противоречащее содержимое даёт конфликт.
- **LR-BE-0506 — выполнено для локальных адаптеров и программного коннектора Telegram.** TEST,
  IMPORT и GENERIC_WEBHOOK принимают явное направление. Макет Connected Business
  Bot различает входящие сообщения и ручные исходящие по `sender_business_bot`
  и соотношению отправителя с личным чатом. Настоящий Telegram всё ещё требует
  проверки отдельного этапа применимости.
- **LR-BE-0507 — выполнено.** Изменение обновляет каноническое состояние
  существующего сообщения, включая ответ и вложения; точный повтор ничего не
  меняет.
- **LR-BE-0508 — выполнено.** Удаление сохраняет историю и выставляет
  `provider_deleted_at`; повтор удаления безопасен.
- **LR-BE-0509 — частично.** Метаданные вложений, ключ объекта, MIME-тип, размер,
  SHA-256 и внешний идентификатор сохраняются отдельно от сообщения. Двоичные
  данные не попадают в PostgreSQL, но фактическая загрузка в S3-совместимое
  объектное хранилище пока заменена явными ключами-заглушками.
- **LR-BE-0510 — выполнено.** `conversations.revision` атомарно увеличивается в
  той же транзакции, что фактическое создание, изменение или удаление сообщения;
  безопасный повтор счётчик не увеличивает.
- **LR-BE-0511 — выполнено.** Подключены чтение списка переписок, одной
  переписки с контактом и сообщений с вложениями; OWNER и MANAGER используют
  `conversation.read`, страницы имеют непрозрачный курсор, чужие данные не
  раскрываются.
- **LR-BE-0512 — выполнено.** Для TEST, IMPORT, GENERIC_WEBHOOK и коннектора Telegram
  добавлено по пять файлов-примеров: новое, изменённое, удалённое сообщение,
  вложение и повтор события.
- **Exit Gate этапа 5 — выполнено для канонического контура.** Сквозной тест
  `webhook → RawEvent + исходящий журнал → общая очередь → обработчик → Contact +
  ExternalIdentity + Conversation + Message → HTTP-чтение` проходит на
  PostgreSQL 18. Второе сообщение создаёт
  только Message; модуль переписок не содержит логики конкретного поставщика.
  Производственная готовность двоичных вложений и настоящего Telegram остаётся
  ограниченной заглушками, как указано выше.
- **LR-BE-0601 — выполнено.** Миграция 000007 создаёт общую tenant-scoped
  PostgreSQL-таблицу `jobs` с полезной нагрузкой JSONB, приоритетом, доступностью,
  попытками, арендой, безопасным кодом ошибки и полным жизненным циклом.
- **LR-BE-0602 — выполнено.** Атомарный захват использует
  `FOR UPDATE SKIP LOCKED`, стабильный порядок и ограниченную пачку; параллельные
  процессы не получают одну действующую аренду.
- **LR-BE-0603 — выполнено.** Истёкшее `PROCESSING` повторно захватывается другим
  владельцем. Подтверждение проверяет владельца и срок аренды, поэтому прежний
  процесс не может завершить уже переданное задание.
- **LR-BE-0604 — выполнено.** Ошибки явно делятся на временные и постоянные.
  Применена сетка ТЗ: 5 секунд, 30 секунд, 2 минуты и 10 минут; неизвестная
  ошибка безопасно считается временной.
- **LR-BE-0605 — выполнено.** Постоянная ошибка сразу получает `DEAD`; временная
  получает `DEAD` после пятой попытки. Истёкшая последняя аренда также не
  оставляет задание навечно в `PROCESSING`.
- **LR-BE-0606 — выполнено.** `lidradar-scheduler` теперь является рабочим
  циклом с проверкой PostgreSQL, ограниченными пачками, ожиданием, журналированием
  ошибок и штатной остановкой.
- **LR-BE-0607 — выполнено.** `scheduled_checks` хранит субъект, срок, вид
  будущего задания и ключ дедупликации. Наступившая проверка и задание меняются
  в одной транзакции; повтор планировщика не создаёт вторую запись.
- **LR-BE-0608 — выполнено.** `outbox_events` хранит неизменяемый версионированный
  конверт события. Connector Core записывает RawEvent и
  `connector.raw-event.received` в одной транзакции; принудительный конфликт
  исходящего журнала откатывает и RawEvent.
- **LR-BE-0609 — выполнено.** Диспетчер исходящего журнала имеет собственную
  аренду, восстановление, ограниченные повторы и `DEAD`; повтор публикации
  создаёт не более одного задания благодаря ключу дедупликации.
- **LR-BE-0610 — выполнено.** Общий worker регистрирует обработчики по
  версионированному виду задания, передаёт устойчивые ID и ключ дедупликации,
  не подтверждает отменённую работу и сохраняет только безопасный код ошибки.
- **LR-BE-0611 — выполнено.** Интеграционный crash-test запускает отдельный
  worker-процесс, ждёт захвата, завершает его через `kill -9` и доказывает, что
  после аренды другой процесс завершает то же задание.
- **LR-BE-0612 — выполнено.** Тест сценария «побочный эффект → падение до ACK →
  повтор» использует уникальный ID задания и получает ровно одну запись эффекта.
  Сквозной тест канонизации дополнительно сохраняет одно сообщение при повторе.
- **Exit Gate этапа 6 — выполнено.** Падение после захвата не теряет работу,
  второй worker завершает её после аренды, а зафиксированный RawEvent всегда
  имеет долговечное намерение в исходящем журнале.
- **LR-BE-0701 — выполнено.** Opportunity является отдельным от Conversation
  агрегатом с tenant-scoped PostgreSQL repository.
- **LR-BE-0702 — выполнено.** Машина этапов разрешает только утверждённые
  переходы вперёд, закрытие и последующую архивацию.
- **LR-BE-0703 — выполнено.** Частичный уникальный индекс PostgreSQL допускает
  не более одной активной Opportunity на переписку даже при гонке обработчиков.
- **LR-BE-0704 — выполнено.** История этапов добавляется только в конец;
  PostgreSQL-триггер запрещает прямые `UPDATE` и `DELETE`.
- **LR-BE-0705 — выполнено.** Потенциальная выручка хранится точным
  `NUMERIC(14,2)` и остаётся `NULL`, если каталог не даёт надёжной точной цены.
- **LR-BE-0706 — выполнено.** Коммерческий кандидат обрабатывается после
  фиксации переписки и перечитывает её актуальное состояние из PostgreSQL.
- **LR-BE-0707 — выполнено.** Подключены tenant-scoped чтение Opportunity и
  ручное изменение этапа через разрешение `opportunity.manage`.
- **LR-BE-0708 — выполнено.** Проверены допустимые и запрещённые переходы,
  идемпотентный повтор, гонка кандидатов, история и изоляция организаций.
- **Exit Gate этапа 7 — выполнено.** Conversation и Opportunity физически и
  логически разделены, а текущее состояние воспроизводится из истории этапов.

## Этап 8 — NO_RESPONSE

- **LR-BE-0801 — выполнено.** Агрегат Risk хранит тип, важность, состояние,
  источник, версию правила, код и текст причины, сообщение-основание, срок
  ответа и временные отметки жизненного цикла.
- **LR-BE-0802 — выполнено.** Миграция 000009 и PostgreSQL-хранилище реализуют
  tenant-scoped создание/обновление, чтение и автоматическое закрытие.
- **LR-BE-0803 — выполнено.** `NO_RESPONSE` использует детерминированное правило
  `no-response/v1`; сохранённый риск остаётся объяснимым после будущих изменений.
- **LR-BE-0804 — выполнено.** Рабочее время считается в IANA timezone точки по
  недельному расписанию; закрытые периоды и переходы летнего времени не
  засчитываются.
- **LR-BE-0805 — выполнено.** Проверяются последнее значимое сообщение,
  отсутствие ответа бизнеса, активность Opportunity и порог точки; AI не
  вызывается. 45–89 рабочих минут дают `HIGH`, 90 и более — `CRITICAL`.
- **LR-BE-0806 — выполнено.** Для каждого нового входящего сообщения создаётся
  долговечная запись `scheduled_checks`; scheduler атомарно переносит
  наступившую проверку в общую очередь.
- **LR-BE-0807 — выполнено.** Полезная нагрузка содержит только идентификатор
  Opportunity. В момент выполнения PostgreSQL-проекция заново читает сделку,
  переписку, последнее неудалённое сообщение, Location и рабочие часы.
- **LR-BE-0808 — выполнено.** Частичный уникальный индекс гарантирует не более
  одного активного риска типа на Opportunity; конкурентный тест из 24 goroutine
  создаёт одну строку.
- **LR-BE-0809 — выполнено.** Исходящее сообщение либо закрытие Opportunity
  создаёт событие перепроверки и идемпотентно переводит активный риск в
  `RESOLVED`. Более новое входящее до собственного срока не закрывает старое
  предупреждение ошибочно.
- **LR-BE-0810 — выполнено.** Покрыты границы 12:00 +45 минут, перенос с 20:50,
  ответ до порога, повтор и гонка проверок, timezone/DST, tenant-изоляция и
  сквозной сценарий `webhook → Opportunity → scheduled check → NO_RESPONSE →
  исходящий ответ → RESOLVED` на PostgreSQL 18.
- **Exit Gate этапа 8 — выполнено.** Настоящий канонический поток автоматически
  создаёт корректный `NO_RESPONSE`; Telegram и локальный AI-сервер для правила
  не требуются.

## Этап 9 — Radar API / SSE

- **LR-BE-0901 — выполнено.** PostgreSQL-проекция Radar объединяет Risk,
  Opportunity и Conversation с обязательным ограничением по организации и
  фильтрами `locationId`, `severity`, `riskType`.
- **LR-BE-0902 — выполнено.** Сервер реализует канонический лексикографический
  порядок ТЗ: важность, `BOOKING_INTENT`, потенциальная выручка, длительность
  ожидания, время обнаружения и ID; непрозрачный курсор связан с фильтрами.
- **LR-BE-0903 — выполнено.** Сводка считает активные и критические риски,
  уникальную потенциальную выручку в основной валюте организации и возвращает
  `0.00` для подтверждённой возвращённой выручки до этапа 12.
- **LR-BE-0904 — выполнено.** Список Risk подключён к `cmd/api`, поддерживает
  фильтры, состояние, ограничение размера и курсор.
- **LR-BE-0905 — выполнено для доступных данных.** Детали читают реальные
  Opportunity и Conversation; отсутствующие до этапов 11–12 Recommendation,
  Actions, Outcome и Revenue не имитируются (`actions` — пустой массив).
- **LR-BE-0906 — LR-BE-0907 — выполнены.** PostgreSQL-команды подтверждения и
  закрытия идемпотентны, ограничены организацией и не обновляют время при
  повторе.
- **LR-BE-0908 — LR-BE-0909 — выполнены.** `worker` и команды API публикуют
  краткоживущие сигналы после долговечного изменения через PostgreSQL
  `LISTEN/NOTIFY`; API раздаёт их по SSE только клиентам той же организации.
- **LR-BE-0910 — выполнено.** Проверены `risks.read`, `risks.manage`, отсутствие
  межорганизационной утечки, фильтры, пагинация, идемпотентность и сквозной путь
  `Risk → SSE → REST refetch` на PostgreSQL.
- **Exit Gate этапа 9 — выполнено.** Созданный фоновым обработчиком Risk доступен
  без перезагрузки страницы через сигнал `risk.changed` и последующее чтение
  авторитетного REST API.

- **LR-BE-1008 — выполнено.** Используется детерминированный dedup key открытия

- **LR-BE-1009 — выполнено.** Разрешены только OPEN_RISK, ACKNOWLEDGE и SNOOZE,

- **LR-BE-1010 — выполнено.** Тесты покрывают ошибку Telegram и повторную

- **LR-BE-1501 — выполнено.** Добавлен строгий versioned JSONL format с

- **LR-BE-1502 — не выполнено.** Цель 300–500 размеченных случаев не достигнута:

- **LR-BE-1503 — выполнено на уровне формата.** Runner принимает только TRAIN,

- **LR-BE-1504 — выполнено.** Golden JSONL защищён reviewable SHA-256; runner
  прекращает запуск при несовпадении.
- **LR-BE-1505 — частично.** Добавлен manifest с contract/prompt/dataset/runtime,
  target hardware и местами под gates. Числа gate, model artifact и checksum

- **LR-BE-1506 — выполнено.** `ai-benchmark` вызывает llama.cpp, валидирует каждый

- **LR-BE-1507 — выполнено.** Считаются TP/FP/FN, precision, recall, F1, exact

- **LR-BE-1508 — выполнено.** Считаются p50/p95/p99 latency и throughput; runner

- **LR-BE-1509 — не выполнено по объективной причине.** `lidradar-main-v1`

## Итог аудита

Этапы 2–7 теперь образуют связный PostgreSQL-контур от регистрации организации
до аварийно восстанавливаемой канонизации переписки и отдельной Opportunity.
Проверки ограничений базы, повторных событий, ролей, изоляции организаций,
аренды, исходящего журнала и одной активной Opportunity проходят на PostgreSQL
18. Не закрыты все живые сценарии Telegram, перенос двоичных вложений в
объектное хранилище и RLS, который по ТЗ относится к этапу 24.

Общая очередь этапа 6 готова принимать задания следующих доменов, но сама по
себе не превращает прототипы этапов 10–15 в производственные PostgreSQL-модули.
Этап 15 даёт воспроизводимый контур измерений, но его выходной критерий не
пройден без размеченного набора, выбранной модели и измерения на целевом
оборудовании.

## Проверки текущего аудита

Проверки выполнены 2026-08-26 на PostgreSQL 18:

- весь набор `go test -race -count=1 ./...`, включая изолированные схемы двух
  организаций, сквозной путь этапов 5–6 и настоящий `kill -9` дочернего worker;
- `go vet ./...` и `staticcheck ./...`;
- проверка направлений зависимостей `archcheck`;
- двукратное применение всех миграций, подтверждающее повторяемость запуска;
- проверка конкурентного `FOR UPDATE SKIP LOCKED`, восстановления аренды,
  `RETRY`, `DEAD`, планировщика, исходящего журнала и повторного побочного эффекта;
- проверка приоритета Radar, курсорной пагинации, денежных сумм, разрешений,
  межорганизационной изоляции, идемпотентных команд и `Risk → SSE → REST`;
- проверка OpenAPI через Redocly;
- сборка всех команд `backend/cmd/...`;
- запуск API с успешными `/health/ready` и `/health/live`;
- запуск и штатная остановка фонового обработчика;
- сборка контейнерного образа API.

Ни одна из этих локальных проверок не подменяет обязательные испытания на
настоящем Telegram, загрузку двоичных файлов в объектное хранилище и измерения
локальной модели на целевом графическом ускорителе.
