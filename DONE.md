# Аудит выполнения задач LR-BE-0001 — LR-BE-2209 и LR-BE-RM-001 — LR-BE-RM-026

Дата аудита: 2026-09-02, обновлено 2026-09-03 (этапы R, 17–22). Статусы сверены с кодом, миграциями и тестами текущей
ветки, а не только с историей слияний. `Частично` означает, что контракт или
реализация в памяти есть, но производственное требование (прежде всего
PostgreSQL либо настоящий внешний сервис) не закрыто.

## Сводная карта готовности

Эта таблица описывает не наличие файлов, а готовность этапа в рабочем контуре.
`Прототип` означает, что предметная логика или HTTP-обработчик полезны для
следующей реализации, но состояние ещё хранится в памяти. `Не подключено`
означает, что код не включён в `cmd/api`, `cmd/worker` или `cmd/scheduler`.

## Критические усиления после этапа 16

- **Защита аутентификации — выполнено.** Регистрация, вход и обновление сеанса
  используют общие атомарные счётчики PostgreSQL. Вход ограничен одновременно
  по сетевому адресу и нормализованной учётной записи; ответ 429 содержит
  `Retry-After` и не раскрывает существование пользователя.
- **Изоляция AI-узлов — выполнено.** Узел получает инструкции только явно
  разрешённых организаций. Фильтр применяется до чтения `payload`, а составные
  внешние ключи запрещают межорганизационные аренды и запуски на уровне базы.
  Подробности находятся в
  [`SECURITY_HARDENING_2026_09_02.md`](docs/roadmap/SECURITY_HARDENING_2026_09_02.md).
- **Возвращённая выручка в сводке Radar — исправлено.** Показатель
  `confirmedRecoveredRevenue` считался только по активным рискам и потому
  обнулялся при закрытии риска, ради которого деньги и вернули. Теперь сводка
  следует ТЗ §39: сумма подтверждённых событий с атрибуцией `RECOVERED`.
  Запрошенные фильтры Radar продолжают действовать, состояние риска — нет.
  Счётчики рисков и потенциальная выручка по-прежнему считаются только по
  активным рискам.
- **Наблюдение за подтверждённой записью — исправлено.** Проекция риска считала
  неактивной Opportunity на этапе `BOOKED`, тогда как ТЗ §26 и частичный
  уникальный индекс относят к неактивным только `WON`, `LOST` и `ARCHIVED`.
  Из-за расхождения переписка после записи выпадала из правила `NO_RESPONSE` и
  при этом не могла получить вторую Opportunity. Определение приведено к
  индексу; исключение `BOOKED` осталось внутри правила R3, которое его и
  требует.

  предусмотренные картой `frontend` и `infra` отсутствуют, часть platform-каталогов

- **LR-BE-0005 — выполнено.** MVP non-goals вынесены в отдельный документ.

## Этапы 2–7 — базовые бизнес-модули

- **LR-BE-0201 — выполнено.** User и tenant-independent PostgreSQL repository
  используют UUIDv7-compatible IDs, canonical email и UTC timestamps.
- **LR-BE-0202 — выполнено.** Пароли хэшируются Argon2id в PHC format;
  plaintext не сохраняется и не попадает в публичные ответы.
- **LR-BE-0203 — выполнено.** Реализованы server-side opaque sessions с 256-bit
  token, SHA-256 digest в PostgreSQL, expiry, revocation и atomic rotation.
- **LR-BE-0204 — выполнено.** Organization является tenant и создаётся
  транзакционно вместе с OWNER Membership.
- **LR-BE-0205 — выполнено.** Membership поддерживает OWNER/MANAGER и active,
  invited, disabled statuses.
- **LR-BE-0206 — выполнено.** Центральный permission resolver переводит роль
  Membership в named permissions; MANAGER не получает settings permissions.
- **LR-BE-0207 — выполнено.** Location хранится tenant-scoped с IANA timezone,
  active state и response threshold 1-1440 минут (default 45).
- **LR-BE-0208 — выполнено.** Полное недельное расписание из семи дней
  валидируется и заменяется атомарно вместе с timezone Location.
- **LR-BE-0209 — выполнено.** Подключены register/login/logout/refresh/me,
  HttpOnly SameSite=Strict cookie и browser Origin validation.
- **LR-BE-0210 — выполнено.** Подключены create/get/update Organization API;
  update защищён `organization.manage`.
- **LR-BE-0211 — выполнено.** Подключены list/create/update Location и replace
  business-hours API с явным `X-Tenant-ID`.
- **LR-BE-0212 — выполнено.** Есть isolated PostgreSQL harness для Tenant A/B и
  integration exit-gate test: onboarding, relogin persistence, MANAGER denial и
  cross-tenant 404/403 без раскрытия данных.
- **LR-BE-0301 — выполнено.** Добавлен `ServiceCatalogItem` domain с display и
  normalized name, optional Location, active state и nullable price range.
- **LR-BE-0302 — выполнено.** Миграция `service_catalog_items` использует
  tenant/location composite FK, `NUMERIC(14,2)`, DB checks и tenant indexes.
- **LR-BE-0303 — выполнено.** Точная decimal-модель запрещает JSON number,
  отрицательные/слишком точные суммы и диапазон `price_from > price_to`;
  REST всегда возвращает две дробные цифры.
- **LR-BE-0304 — выполнено.** Подключены OWNER-only list/create/update и
  idempotent soft-deactivate API `/api/v1/services` с явным `X-Tenant-ID`.
- **LR-BE-0305 — выполнено.** Unit и isolated PostgreSQL tests покрывают
  nullable цены без догадок, OWNER/MANAGER, tenant A/B, foreign Location,
  cross-tenant 404 и отсутствие чужих данных в list.
- **LR-BE-0401 — выполнено.** Добавлен tenant-scoped `ChannelConnection` с
  provider, capabilities, optional Location, безопасным verifier hash и
  PostgreSQL constraints/composite tenant FK.
- **LR-BE-0402 — выполнено.** Health хранит `ACTIVE`, `DEGRADED`, `ERROR` или
  `DISCONNECTED`, timestamps последнего события/успеха/ошибки и безопасный error
  code; valid event восстанавливает здоровье development-коннектора.
- **LR-BE-0403 — выполнено.** Domain-контракт Connector определяет Provider,
  VerifyEvent, NormalizeEvent и Health; отдельная capability извлекает внешний
  event ID до постановки normalize work.
- **LR-BE-0404 — выполнено.** `raw_events` хранит JSONB payload и SHA-256,
  tenant/connection/provider scope, processing status и уникальность
  `(connection_id, external_event_id)`.
- **LR-BE-0405 — выполнено.** Короткая PostgreSQL-транзакция атомарно сохраняет
  новый RawEvent, ровно одно версионированное событие исходящего журнала и
  состояние подключения; webhook отвечает до канонизации и AI. Временные записи
  этапа 4 перенесены миграцией 000007 и удалены только после сохранения намерений.
- **LR-BE-0406 — LR-BE-0408 — выполнены.** TEST, IMPORT и GENERIC_WEBHOOK имеют
  детерминированные local adapters с secret verification, строгим fixture
  envelope, external ID и normalization fixture.
- **LR-BE-0409 — частично.** Connected Business Bot connector вызывает
  `setWebhook`, сверяет `getWebhookInfo`, выполняет `deleteWebhook`, проверяет
  официальный secret-token header и преобразует `business_connection`,
  `business_message`, edit/delete. Токен хранится только в зашифрованном виде.
  Обязательный real-account spike выше по-прежнему не выполнен, поэтому задача
  не переводится в состояние «выполнено» только по автоматизированным тестам.
- **LR-BE-0410 — выполнено.** OWNER-only connect/list/idempotent disconnect/health
  API подключён к runtime; cross-tenant ID возвращается как missing. Webhook
  endpoint аутентифицируется provider secret без user session.
- **LR-BE-0411 — выполнено.** Модульные, хранилищные и сквозные HTTP/PostgreSQL
  тесты доказывают, что 10 одинаковых доставок дают один RawEvent и одно событие
  канонизации; тот же внешний ID с другим содержимым даёт конфликт.
- **LR-BE-0412 — выполнено.** Неверный secret ничего не сохраняет; корректно
  аутентифицированный malformed payload сохраняется один раз как `FAILED` без
  намерения канонизации, включая сохраняющую исходные байты оболочку base64 для
  данных, не являющихся JSON.
- **Exit Gate этапа 4 — частично.** Persist-once, быстрый `202` и независимость
  от downstream AI доказаны для local/fixture adapters. Настоящий Telegram
  update нельзя подтвердить до выполнения feasibility spike с credentials.
- **LR-BE-0501 — выполнено.** Определены строгие канонические события
  `message.received.v1`, `message.edited.v1` и `message.deleted.v1` с направлением,
  видом сообщения, ссылкой на исходное событие, контактом, ответом, вложениями и
  произвольными метаданными в объекте JSON.
- **LR-BE-0502 — выполнено.** Контакт создаётся при первой встрече внешней
  личности и затем разрешается через неё; имя, телефон и почта обновляются только
  данными не старше уже сохранённых.
- **LR-BE-0503 — выполнено.** Уникальность внешней личности учитывает
  организацию, поставщика, подключение и внешний идентификатор; два подключения
  с одинаковым идентификатором контакта не склеиваются.
- **LR-BE-0504 — выполнено.** Переписка создаётся один раз на пару
  `(connection_id, external_id)` и повторно используется следующими сообщениями.
- **LR-BE-0505 — выполнено.** Каноническое сообщение сохраняется в PostgreSQL;
  повтор с тем же содержимым безопасен, а противоречащее содержимое даёт конфликт.
- **LR-BE-0506 — выполнено для локальных адаптеров и программного коннектора Telegram.** TEST,
  IMPORT и GENERIC_WEBHOOK принимают явное направление. Макет Connected Business
  Bot различает входящие сообщения и ручные исходящие по `sender_business_bot`
  и соотношению отправителя с личным чатом. Настоящий Telegram всё ещё требует
  проверки отдельного этапа применимости.
- **LR-BE-0507 — выполнено.** Изменение обновляет каноническое состояние
  существующего сообщения, включая ответ и вложения; точный повтор ничего не
  меняет.
- **LR-BE-0508 — выполнено.** Удаление сохраняет историю и выставляет
  `provider_deleted_at`; повтор удаления безопасен.
- **LR-BE-0509 — частично.** Метаданные вложений, ключ объекта, MIME-тип, размер,
  SHA-256 и внешний идентификатор сохраняются отдельно от сообщения. Двоичные
  данные не попадают в PostgreSQL, но фактическая загрузка в S3-совместимое
  объектное хранилище пока заменена явными ключами-заглушками.
- **LR-BE-0510 — выполнено.** `conversations.revision` атомарно увеличивается в
  той же транзакции, что фактическое создание, изменение или удаление сообщения;
  безопасный повтор счётчик не увеличивает.
- **LR-BE-0511 — выполнено.** Подключены чтение списка переписок, одной
  переписки с контактом и сообщений с вложениями; OWNER и MANAGER используют

- **LR-BE-0512 — выполнено.** Для TEST, IMPORT, GENERIC_WEBHOOK и коннектора Telegram
  добавлено по пять файлов-примеров: новое, изменённое, удалённое сообщение,

- **Exit Gate этапа 5 — выполнено для канонического контура.** Сквозной тест
  `webhook → RawEvent + исходящий журнал → общая очередь → обработчик → Contact +

  только Message; модуль переписок не содержит логики конкретного поставщика.

  0.65 не поступают policy.
- **LR-BE-1408 — LR-BE-1409 — выполнены в PostgreSQL.** Job/Run долговечно
  сохраняют версии model/prompt/schema, снимок свежести, сырой результат и
  ошибку проверки для каждой попытки.
- **LR-BE-1410 — LR-BE-1411 — выполнены в PostgreSQL.** Revision и
  through-message freshness повторно проверяются в транзакции завершения;

  Через message ID сравнивается последнее действительно анализируемое текстовое

## Этап R — Consistency Remediation (вне очереди, между 16 и 17)

Реализация сверена с реальной схемой репозитория, а не с Планом v1.2: часть
DDL этапа описывает таблицы, которых ещё нет, а часть требований уже была
выполнена раньше. Все изменения схемы собраны в одну forward-only миграцию
`000016_consistency_remediation.sql` (ТЗ называет `000018`; занят следующий
свободный номер, карта сдвинута на два).

### Блок R1 — целостность схемы

- **LR-BE-RM-001 — выполнено.** `revenue_attributions` уже несла
  `opportunity_id`; добавлены составные ключи `(tenant_id, id, opportunity_id)`
  на `revenue_events`, `risk_signals`, `outcomes` и денормализованный
  `actions.opportunity_id` со своим ключом, внешние ключи атрибуции переведены
  на три столбца, создан частичный уникальный индекс «одна `RECOVERED` на
  Opportunity». Приложение возвращает `409 RECOVERED_ALREADY_ATTRIBUTED`;
  оплата частями подтверждается как `ORGANIC`. 30-дневное окно по-прежнему
  держит триггер `validate_revenue_attribution`: денормализованный `outcome_at`
  не добавлялся, потому что окно задаётся центрально в Go, а не столбцом.
- **LR-BE-RM-002, RM-003, RM-008, RM-015, RM-020 — не применимо сейчас.**
  Таблицы `risk_policy_configs`, `encrypted_secrets`, `feature_flags`,
  `platform_admins`, `notification_preferences` ещё не созданы. Канонический
  DDL зафиксирован в `BACKEND_SPEC.md`, раздел «Отложенные правила схемы».
- **LR-BE-RM-004 — уже выполнено ранее.** `ai_runs` содержит `tenant_id`,
  `UNIQUE (tenant_id, id)` и tenant-aware ключ на `ai_jobs`; `Run` в Go несёт
  `TenantID`. Чтение run по идентификатору остаётся машинным: узел
  удостоверяется отдельно, а принадлежность проверяется по узлу и заданию.
- **LR-BE-RM-005 — выполнено.** Upsert проекции защищён условием по ревизии,
  а проверка свежести выполняется под блокировкой строки переписки. Добавлен
  тест: run ревизий 5 и 7 в любом порядке фиксации оставляют ревизию 7,
  устаревший run получает `STALE` (это и есть след «отброшенного upsert»).
- **LR-BE-RM-006 — выполнено с намеренным отступлением.** Частичный уникальный
  индекс покрывает только `PENDING/RETRY`: захваченное задание в него не
  входит, потому что узел уже получил инструкцию, а запуск копирует снимок из
  строки при старте. Постановка идемпотентна и обновляет снимок ожидающего
  задания; дебаунс 60 секунд; повторное планирование после `STALE` использует
  ту же паузу. Тест: пять сообщений за двадцать секунд — одно задание с
  последней ревизией. Решение — ADR 0036.
- **LR-BE-RM-007 — уже выполнено ранее.** `ai_jobs_lease_valid` не допускает
  владельца без срока; теперь он требует ещё и `leased_at`.
- **LR-BE-RM-009 — выполнено.** `memberships.revoked_at`, проверка
  согласованности со статусом `DISABLED`, триггер против `DELETE`,
  `RevokeMembership` в репозитории. Частичный уникальный индекс из ТЗ не
  вводился: на `(tenant_id, user_id)` ссылаются внешние ключи фактов, и
  уникальность обязана оставаться полной; история выдач живёт в `audit_log`.

- **LR-BE-RM-010 — выполнено.** `lease_owner` переименован в `leased_by` в

- **LR-BE-RM-013 — выполнено.** Список допустимых стадий R3 —

### Блок R3 — корректность runtime

- **LR-BE-RM-016 — выполнено.** `ai_jobs.leased_at` ставится при захвате и не
  продлевается heartbeat; перехват при `lease_until < now()` или
  `leased_at + 15m < now()` помечает запуск `LEASE_CAP_EXCEEDED` и увеличивает
  `attempts`. Тест: зависший узел с живым heartbeat теряет задание, резервный
  узел его завершает, поздний `complete` отбрасывается.
- **LR-BE-RM-017 — выполнено в части домена.** Каждый сохранённый факт несёт

  прислать поле не может. Метрика `ai_facts_weak_total` и
  `/admin/ai/.../summary` относятся к этапу 23.
- **LR-BE-RM-018 — выполнено как решение.** ADR 0034 фиксирует три роли,
  fail-closed политику и явный список запросов под `lidradar_platform`;
  AI-узел доступа к PostgreSQL не имеет. Сами политики создаёт этап 24
  (LR-BE-2401), как и было запланировано.
- **LR-BE-RM-019 — не применимо сейчас.** `risk_feedback` создаётся этапом 21;
  канонический запрос с `DISTINCT ON (risk_id)` и `coverage_rate` записан в
  спецификации.
- **LR-BE-RM-021 — уже выполнено ранее.** Все сервисы принимают
  `now func() time.Time`, значимые метки передаются параметрами, истечение
  аренды в тестах — сдвигом часов; `clock.time` в репозитории нет.

## Этап 17 — PROMISE_NOT_FULFILLED

- **LR-BE-1701 — выполнено.** Факт `BUSINESS_COMMITMENT` контракта
  `analyze-conversation.v1` читается из проекции AI как `CommitmentSignal`:
  только доверенный факт, доказательство — исходящее сообщение компании,
  проекция берётся без условия ревизии (обещание — исторический факт).
- **LR-BE-1702 — выполнено с решением по границе AI.** Срок извлекается из
  текста обещания детерминированным разбором в часовом поясе точки («через
  десять минут», «в течение часа», «сегодня до 18:00», «к 17 часам», «завтра
  утром/до полудня/после обеда/вечером», «не позднее завтра», «до конца дня»,
  дни недели). Контракт модели не менялся: замороженный `lidradar-main-v1`
  срок не сообщает, а расширение схемы потребовало бы v2, новой разметки и
  повторной заморозки на узле. Разбор версионируется вместе с правилом и
  объясняется в тексте причины; переход на срок от модели остаётся возможным
  без изменения правила.
- **LR-BE-1703 — выполнено.** Не названный или неоднозначный срок заменяется
  60 рабочими минутами от обещания по расписанию точки.
- **LR-BE-1704 — выполнено.** Проверка `PROMISE_NOT_FULFILLED_DUE` и задание
  `risk.evaluate-promise-not-fulfilled.v1` идут через общий планировщик; планер
  теперь берёт сообщение-основание из решения правила и не требует входящего
  последнего сообщения (обещание — исходящее). Закрытие старого риска и
  планирование новой проверки в одном проходе не исключают друг друга.
- **LR-BE-1705 — выполнено консервативно.** Соответствующий follow-up — любое
  исходящее сообщение компании после сообщения-основания; смысловая проверка
  ответа отложена, потому что ложное срабатывание опаснее пропуска.
- **LR-BE-1706 — выполнено.** Один активный риск типа на Opportunity (общий
  частичный индекс); исходящее после основания закрывает риск даже когда новая
  проекция AI уже не содержит факта — состояние несёт сообщения-основания
  активных рисков и признак последующего исходящего.
- **LR-BE-1707 — выполнено.** Табличные тесты разбора срока (явные формы и
  неоднозначные отказы), тесты правила (срок из текста, запас, follow-up,
  слабый факт, исчезнувший факт, новое обещание), сквозной PostgreSQL-тест
  `webhook → обещание → AI-факт → проверка → R4 → Radar → рекомендация →
  Telegram → исходящее → RESOLVED`.
- **Exit Gate этапа 17 — выполнен.** Риск создаётся только при реальном
  просроченном обязательстве: без факта, при слабом факте, при follow-up до
  срока и по закрытой сделке риск не появляется.

  валютой читается из проекции AI как `PriceSignal`; доказательство —
  исходящее сообщение компании, проекция без условия ревизии.
- **LR-BE-1802 — выполнено.** Факт переводит активную сделку в `PRICE_SENT`
  (источник истории `AI`, только вперёд, идемпотентно); цена обрабатывается
  раньше намерения записаться, чтобы не потерять этап. Правило работает и по
  этапу без факта (источник `RULE`, основание — последнее исходящее).
- **LR-BE-1803 — выполнено.** 24 рабочих часа → `MEDIUM`, 48 → `HIGH`
  (канон RM-012) по расписанию точки; первая проверка назначает проверку
  эскалации того же основания (суффикс ключа `escalation`), для чего
  наступившая проверка теперь выполняется через планер и может назначить
  следующую.
- **LR-BE-1804 — выполнено.** `BOOKED`, `WON`, `LOST`, `ARCHIVED` не создают и
  закрывают риск.
- **LR-BE-1805 — выполнено как деривация.** В контракте v1 нет факта отказа;
  `CUSTOMER_REJECTED` выводится из последнего исхода `LOST` или `NOT_A_LEAD`.
  Смысловое обнаружение отказа — этап 19 (LR-BE-1902).
- **LR-BE-1806 — выполнено.** Входящее клиента после основания закрывает риск,
  в том числе при исчезнувшем факте (состояние несёт признак входящего после
  основания активного риска).
- **LR-BE-1807 — выполнено.** Оценка выручки записывается только из
  доверенного факта, только в валюте сделки, только с точной суммой до двух
  дробных знаков и не поверх более надёжной оценки; защита стоит в SQL.
  Немедленное уведомление для R2 не создаётся — тип доставляется дайджестом
  (ТЗ §46), обработчик открытия риска пропускает DIGEST-типы без ошибки.
- **Exit Gate этапа 18 — выполнен.** Неопределённая сумма никогда не
  выдумывается: диапазон каталога оставляет оценку пустой, чужая валюта и
  слишком точная сумма отклоняются, сделка на `PRICE_SENT` без факта риск
  получает, а оценку — нет. Покрыто тестами правила, обработчика и сквозным
  PostgreSQL-тестом `webhook → цена → AI-факт → PRICE_SENT + оценка →
  проверка → R2 MEDIUM + эскалация → Radar → входящее → RESOLVED`.

## Этап 21 — FEEDBACK / QUALITY CONTROL

- **LR-BE-2101 — выполнено.** `POST /api/v1/risks/{id}/feedback` записывает
  вердикт `TRUE_POSITIVE` или `FALSE_POSITIVE` в append-only таблицу
  `risk_feedback` (миграция `000018_risk_feedback.sql`, триггер против
  UPDATE/DELETE). Ложное срабатывание закрывает активный риск статусом
  `FALSE_POSITIVE` и оповещает Radar; закрытый риск не переписывается.
- **LR-BE-2102 — выполнено.** Причины `CUSTOMER_ALREADY_BOOKED`,
  `CUSTOMER_ALREADY_ANSWERED`, `NOT_A_LEAD`, `CUSTOMER_REJECTED`,
  `WRONG_INTERPRETATION`, `OTHER`; для ложного срабатывания причина
  обязательна на уровне домена и схемы.
- **LR-BE-2103 — выполнено.** Причина `NOT_A_LEAD` закрывает сделку как
  `LOST` через сервис Opportunity с источником `USER` и автором вердикта;
  `ARCHIVED` по машине этапов §26 достижим только из `WON`/`LOST`. Закрытие
  сделки через событие снимает остальные активные риски.
- **LR-BE-2104 — выполнено.** Запись хранит снимок: тип, важность, статус,
  источник, версию правила, AI-прогон, сообщение-основание, стадию сделки и
  время обнаружения на момент вердикта.
- **LR-BE-2105 — выполнено.** Вердикт требует `risks.manage`, метрики —
  `analytics.read`; чужой участник получает 403, чужой риск — 404; каждая
  запись пишет аудит `RISK_FEEDBACK_RECORDED`.
- **LR-BE-2106 — выполнено.** `GET /api/v1/risks/precision?from&to` считает по
  типу риска за окно обнаружения precision, долю ложных и покрытие по
  последнему вердикту на риск (LR-BE-RM-019); отчёт содержит пять типов,
  порог `0,5` и признак `reliable`.
- **LR-BE-2107 — выполнено.** Граница ML (§70): `ml_consents` — явное,
  активное и отзываемое согласие организации на наборы данных с историей
  выдач и аудитом; `GET/POST/DELETE /api/v1/organization/ml-consent`
  (владелец). Запись обратной связи фиксирует `dataset_eligible` на момент
  вердикта; без согласия данные служат только сервису.
- **Отклонения и границы.** Окно метрики привязано ко времени обнаружения
  риска, а не записи обратной связи, чтобы покрытие было определено
  (ADR 0038). Ключ идемпотентности для вердикта не вводился: несколько
  записей на риск допустимы по ТЗ, метрика читает последнюю.
- **Exit Gate этапа 21 — выполнен.** Precision и доля ложных считаются по
  каждому типу риска; сквозной PostgreSQL-сценарий «риск → согласие → вердикты
  → ложное срабатывание «не лид» → риск FALSE_POSITIVE и сделка LOST →
  отчёт точности → аудит».

## Итог аудита

Этапы 2–7 теперь образуют связный PostgreSQL-контур от регистрации организации
до аварийно восстанавливаемой канонизации переписки и отдельной Opportunity.
Проверки ограничений базы, повторных событий, ролей, изоляции организаций,
аренды, исходящего журнала и одной активной Opportunity проходят на PostgreSQL
18. Не закрыты все живые сценарии Telegram, перенос двоичных вложений в
объектное хранилище и RLS, который по ТЗ относится к этапу 24.

Этап 13 перенёс узлы, AI Job/Run, freshness и ConversationSummary из
испытательной памяти в PostgreSQL и доказал физический контур Ubuntu/RTX 4060 по
Wi‑Fi. Этап 14 добавил строгую проверку и безопасное применение анализа,
включая натурные отклонённые и применённые результаты Qwen3. Этап 15 добавил
воспроизводимый набор из 300 случаев и выбрал Qwen3-8B измерениями на целевом
оборудовании. Статус `FROZEN` ограничен текущими четырьмя фактами контракта и не
подменяет будущую проверку стадий, услуг и живой речи. Этап 16 впервые использует
один из этих фактов в рабочем Risk Engine, сохраняя детерминированный порог и
полную трассировку решения.
