# Отказоустойчивость

Документ описывает, какие гарантии система даёт при сбоях, как ведёт себя
при отказе каждой зависимости, как восстанавливается и как это проверено.

Уточнение 2026-10-05: описания прежней реализации и нормативные требования
не означают нового прогона. Полное DR, аудит и freshness оцениваются в
[release-gates](../engineering/RELEASE_GATES.md).

## 1. Принципы

- **Один источник истины.** Всё долговременное состояние — в PostgreSQL;
  очереди, расписания, идемпотентность и outbox тоже там (ADR 0003, 0026,
  0027). Потеря процесса никогда не теряет принятую работу.
- **Сначала сохранить, потом обрабатывать.** Внешнее событие пишется до
  любой интерпретации (ADR 0004, 0025); ответ `202` означает «сохранено», а
  не «обработано».
- **Как минимум один раз + идемпотентность.** Доставка событий и заданий
  повторяется; каждый обработчик опирается на устойчивый ключ дедупликации
  или уникальное ограничение (карта ключей — [../backend/06-async-processing.md](../backend/06-async-processing.md) § 5).
- **Аренды вместо блокировок.** Захваченная работа привязана к владельцу на
  30 с; павший процесс ничего не держит вечно.
- **Fail-closed.** Недоступный троттлер блокирует вход; отсутствие контекста
  организации даёт пустую выборку; несовпадение миграций делает API не
  готовым; отсутствие семи строк расписания — постоянная ошибка, а не
  круглосуточный режим.
- **Деградация без потери бизнес-состояния.** Отказ Telegram, AI-узла или
  SSE не меняет риски, сделки и деньги.

## 2. Поведение при отказе зависимостей

| Отказ | Что продолжает работать | Что деградирует | Восстановление |
|---|---|---|---|
| PostgreSQL недоступна | ничего: API отвечает `503` на `/health/ready` и `500`/`503` на запросы, worker и scheduler логируют ошибку и повторяют через 1 с | всё | автоматически при возврате базы; пул переподключается, аренды истекают |
| Журнал миграций не совпал со сборкой | `/health/live` | `/health/ready` → `503`, оркестратор не пускает трафик | применить миграции той же сборкой (`cmd/migrate`) |
| worker остановлен | API, приём вебхуков (сырые события копятся), Radar по уже созданным рискам | нормализация, риски, уведомления, AI-постановка; очереди растут, видно в панели администратора и событии `background.queue.status` | запуск worker; накопленное обрабатывается по порядку |
| worker упал после захвата | — | одно задание/событие/доставка задерживается на срок аренды | другой владелец подхватывает после 30 с, попытка увеличивается; прежний владелец не может подтвердить результат (`ErrLeaseLost`) |
| scheduler остановлен | всё, кроме перевода проверок в задания | проверки копятся как `scheduled_checks_overdue`; риски по правилам не открываются вовремя | запуск; `PromoteDue` продвигает пачками по 100, `available_at = due_at` сохраняет исходный срок |
| Telegram Bot API недоступен | всё; `IN_APP`-доставки завершаются | Telegram-доставки уходят в `RETRY` (5 с … 10 мин) и после пятой попытки в `DEAD` | автоматически; мёртвые доставки видны администратору, повтор не предусмотрен — при необходимости риск остаётся в Radar |
| Токен бота не задан | всё | Telegram-канал не захватывается, предупреждение `notification.telegram.disabled` | задать `LIDRADAR_TELEGRAM_TOKEN`, перезапустить worker |
| Публичный URL или ключ шифрования не заданы | все каналы, кроме Telegram | подключение Telegram отвечает `503 CONNECTOR_UNAVAILABLE` | задать оба параметра |
| AI-узел офлайн / llama.cpp не готов | API, `NO_RESPONSE`, Radar, деньги | семантические риски (R2–R5 по фактам) ждут; `ai_jobs` копятся в `PENDING`, узел помечается `OFFLINE` через 60 с | автоматически при возврате узла; аренды перехватываются, потолок 15 мин |
| Версия модели узла не совпадает | всё | `claim` пуст, задания висят | выровнять `LIDRADAR_AI_MODEL_VERSION` |
| Соединение `LISTEN` для SSE разорвано | REST | сигналы между процессами могут потеряться при живом клиентском SSE | LISTEN переподключается, но bounded REST recovery требует отдельной проверки H-16 |
| Переполнен буфер SSE-подписчика | всё | накопленные сигналы отброшены, послан маркер `resync.required` | клиент перечитывает сводку и открытые списки целиком |
| Ошибка транзакционного аудита | остальные операции | транзакция команды должна откатиться вместе с фактом | replay по исходному ключу; требуется fault injection текущей сборки |
| Ошибка post-commit аудита | изменение могло сохраниться | возможны `500` и отсутствие следа; это ограничение H-04 | сверить результат; без доказанной идемпотентности не повторять вслепую |
| Панику вызвал обработчик задания | процесс завершается | текущая работа задержана на аренду | оркестратор перезапускает процесс |
| Панику вызвал HTTP-обработчик | остальные запросы | ответ `500 INTERNAL_ERROR` | — |

## 3. Транзакционные границы

| Операция | В одной транзакции |
|---|---|
| приём вебхука | блокировка подключения, `raw_events`, `outbox_events`, здоровье подключения |
| каноническое изменение | контакт, переписка, сообщение, вложения, ревизия, `outbox(conversation.changed)` |
| создание сделки | сделка, история, `outbox(opportunity.created)`; гонка кандидатов разрешается `ON CONFLICT` на частичный индекс без ошибки |
| открытие риска | `risk_signals`, `outbox(risk.opened)`; сигнал `pg_notify` — вне транзакции, допускает потерю |
| действие / исход / выручка | ключ идемпотентности, факт, перевод риска (для действия), аудит |
| выдача/отзыв ML-согласия | согласие и запись аудита |
| завершение AI-прогона | прогон, задание, проекция резюме, `outbox(ai.analysis.applied)`, постановка замены через savepoint |
| продвижение проверок | пачка проверок и создание заданий; расхождение payload откатывает всю пачку |
| команды администратора | изменение очереди и `admin_audit_log` |
| миграции | все файлы одним коммитом под advisory-lock |

Побочные эффекты вне базы (Telegram, Bot API `setWebhook`) намеренно
выполняются **после** коммита локального состояния и повторяемы: ошибка
регистрации вебхука оставляет подключение в `ERROR`, ошибка удаления
позволяет повторить `Disconnect`.

## 4. Восстановление после сбоев процессов

- **Аренды.** События, задания, доставки и AI-задания несут `leased_by` и
  `lease_until`; истёкшая аренда делает элемент доступным другому владельцу,
  а при исчерпанных попытках — `DEAD` с `LEASE_EXPIRED_MAX_ATTEMPTS`. Владелец
  аренды — свежий идентификатор на запуск процесса, поэтому перезапуск не
  «наследует» чужие аренды. Проверено реальным `kill -9` дочернего процесса
  после захвата (`TestWorkerProcessCanBeKilledAfterClaim`).
- **Повторы.** 5 попыток по расписанию 5 с / 30 с / 2 мин / 10 мин;
  постоянные ошибки — сразу `DEAD`. Классификация — на обработчике; неизвестная
  ошибка считается временной.
- **Мёртвые элементы.** Панель `dead-letters`, команды `retry`/`replay`
  (сброс попыток и аренды) и `discard`; повтор AI-задания уважает
  единственность ожидающего задания.
- **Плавная остановка.** `SIGINT`/`SIGTERM`: API дренирует запросы в пределах
  `LIDRADAR_SHUTDOWN_TIMEOUT` (10 с по умолчанию, таймаут считается от нового
  контекста), worker и scheduler завершают текущую итерацию и выходят с кодом
  0; незавершённое задание освобождается по аренде. `migrate`,
  `platform-admin`, `load-generate` сигналы не слушают.
- **Готовность.** `/health/ready` — `Ping` базы и сверка журнала миграций с
  набором сборки поэлементно; Compose и CI пускают трафик только после
  готовности.

## 5. Пул соединений и его пределы

- Пулы по ролям: API — `lidradar_app` + `lidradar_platform`, worker —
  `lidradar_worker` + `lidradar_platform`, scheduler — `lidradar_platform`;
  размер `LIDRADAR_DATABASE_MAX_CONNS` (10 в Compose) и минимум
  `LIDRADAR_DATABASE_MIN_CONNS` (1); таймаут подключения 5 с.
- Правило: репозиторий **не** обращается к пулу при открытом курсоре. Страница
  сообщений раньше делала вложенный запрос на каждое сообщение и требовала два
  соединения на запрос; при конкуренции, равной размеру пула, запросы висли
  навсегда. Исправлено пакетной загрузкой; регрессионный тест держит пул из
  двух соединений под шестью читателями. Держите
  `LIDRADAR_DATABASE_MAX_CONNS` не меньше ожидаемого параллелизма API.
- Контекст RLS ставится хуком перед каждой выдачей соединения с кэшем
  состояния, поэтому смена организации между запросами не требует
  переподключения.

## 6. Резервные копии и восстановление

Runbook: `docs/runbooks/backup-restore.md`.

- `scripts/backup.sh` — `pg_dump -Fc --no-owner --no-privileges
  --enable-row-security` той же версии, что сервер; до выгрузки проверяется,
  что роль копии видит все строки при `FORCE ROW LEVEL SECURITY`
  (суперпользователь, `BYPASSRLS` или член `lidradar_platform`), иначе скрипт
  останавливается без файла (режимы `compose`, `container`, `local`), файлы
  `backups/lidradar-<UTC>.dump`, ротация `LIDRADAR_BACKUP_KEEP` (14), копия
  меньше 1 КиБ считается ошибкой. Каталог `backups/` вне git; перенос во
  внешнее хранилище — задача планировщика хоста.
- `scripts/restore.sh <dump> [db]` создаёт новую целевую базу (существующую не
  трогает) и восстанавливает с `--exit-on-error`. Роли и права в dump не входят:
  следом обязателен `scripts/bootstrap-roles.sh <db>` (создаёт роли, выдаёт
  права, проверяет RLS), затем `cmd/migrate` только для новых миграций и
  проверка `/health/ready`. Миграция `000020` в восстановленном журнале повторно
  не выполняется.
- `scripts/restore-drill.sh` — учение: копия → восстановление в отдельную
  базу → сравнение семи счётчиков (таблицы, последняя миграция, организации,
  сообщения, риски, выручка, аудит) → удаление учебной базы. Учение входит в
  чек-лист пилота и повторяется перед релизом; последнее выполнено против
  локального контейнера с результатом `restore drill OK`.
- Форвард-совместимость миграций проверяется тестом: схема прежнего выпуска
  принимает следующие миграции, повтор ничего не меняет, подмена применённой
  миграции останавливает запуск.

## 7. Целостность данных при гонках

| Гонка | Защита |
|---|---|
| два worker открывают один риск | частичный уникальный индекс + `ON CONFLICT DO NOTHING` и повтор `UPDATE` до трёх раз |
| два кандидата на одну переписку | частичный уникальный индекс одной активной сделки, второй получает существующую |
| одинаковый переход этапа параллельно | `FOR UPDATE` на сделке, одна запись истории |
| повтор команды с `Idempotency-Key` параллельно | `INSERT … ON CONFLICT DO NOTHING` на ключе, второй читает сохранённый ответ |
| две ротации одной сессии | `FOR UPDATE OF s` и проверка `RowsAffected = 1` |
| параллельные попытки входа | атомарный `INSERT … ON CONFLICT DO UPDATE` счётчика (40 параллельных → ровно 5 разрешены) |
| два узла AI претендуют на задание | `FOR UPDATE SKIP LOCKED`, один активный прогон на задание, проверка владения при завершении, повторная проверка свежести внутри транзакции |
| несколько экземпляров `migrate` | advisory-lock и транзакция |

## 8. Ограничения и что не гарантируется

- Ровно одна обработка не гарантируется — только идемпотентность.
- Порядок событий между разными агрегатами не гарантируется; внутри одной
  переписки ревизии и ключи дедупликации делают повторы безопасными.
- Уведомление после пяти неудачных попыток не доставляется; риск остаётся
  в Radar и в сводке.
- Сигнал SSE может быть потерян; frontend обязан автоматически сверять REST
  в пределах утверждённого SLA, не только по focus/online/manual.
  Полная гарантия ещё не подтверждена: [H-16](../engineering/RELEASE_GATES.md#rg-sse).
- Регистрация вебхука Telegram зависит от внешнего сервиса: подключение может
  остаться в `ERROR` и требует явного переподключения.
- Описанная копия логическая и периодическая; PITR/репликация не подтверждены.
  Фактический RPO зависит от возраста пригодной независимой точки, включая
  длительность/передачу и ошибки, не только от расписания.
  Суточная копия не соответствует требованию 15 минут;
  [полное DR](../runbooks/backup-restore.md) является обязательным gate.
- Один PostgreSQL и исходный набор процессов являются начальной топологией,
  не доказанной ёмкостью для ста организаций; границы исторических измерений:
  [../backend/10-operations.md](../backend/10-operations.md) §6.
