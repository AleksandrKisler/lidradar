# Развёртывание за reverse proxy и доверенный адрес клиента

Статус: механизм реализован ([ADR 0049](../adr/0049-trusted-proxies-client-address.md))
и проверен автоматическими тестами и стендом с proxy-заглушкой 2026-10-10;
проверка на настоящем edge остаётся `REQUIRED_NOT_VERIFIED`, H-10. Эта
инструкция задаёт условия допуска, а не готовые параметры конкретного ingress.
Готовый edge пилота — Caddy в [production-стеке](production-deployment.md)
([ADR 0050](../adr/0050-production-topology.md)): его адрес закреплён, а
`LIDRADAR_TRUSTED_PROXIES` задаёт сам compose. Проверки ниже остаются обязательными
и для него; результат на настоящем хосте в стек пока не внесён.

## Исходное ограничение

До ADR 0049 ограничители использовали адрес соединения, то есть адрес proxy. При
обычной TLS-терминации все пользователи выглядели одним адресом и делили пределы:
замер 2026-10-10 показал 20 входов в минуту и 5 регистраций в час на всю
платформу, верный пароль получал `429`. Доверять произвольному `X-Forwarded-For`
нельзя (ADR 0032): клиент подделывает его свободно.

## Как приложение определяет адрес клиента

- `LIDRADAR_TRUSTED_PROXIES` — адреса и сети через запятую (`10.0.0.5`,
  `172.16.0.0/12`, `fd00::/8`): узлы, которые завершают TLS перед API. Только
  proxy: клиент из этих сетей может назвать любой адрес. `/0` и записи с битами
  узла (`172.16.0.1/12`) отвергаются при загрузке.
- Заголовок `X-Forwarded-For` читается, только если адрес соединения входит в
  список. Записи обходятся справа налево: доверенные узлы пропускаются, первый
  недоверенный адрес — клиент, всё левее него не читается. Повреждённая или
  слишком длинная цепочка оставляет клиентом ближайший к API доверенный узел.
  Другие заголовки (`X-Real-IP`, `Forwarded`, заголовки CDN) не читаются.
- Адрес один на запрос и общий для потребителей: ограничитель частоты по
  префиксам, постоянные пределы входа, регистрации и обновления сеанса в
  PostgreSQL, `sessions.ip`, журнал входа.
- `api` в `staging` и `production` без списка не запускается
  (`runtime.configuration_invalid`); остальные процессы список не требуют.

## До открытия трафика

1. Записать всю цепочку: клиент, CDN/LB, ingress, API; для каждого hop указать
   доверенную сеть, способ установления исходного IP и владельца конфигурации.
2. Внести в `LIDRADAR_TRUSTED_PROXIES` адреса или сети узлов, которые соединяются
   с API, так, как их видит API (в Docker и Kubernetes — адрес контейнера или pod
   ingress; закрепить подсеть сети, чтобы адрес не менялся). Если перед API
   несколько hop (CDN, балансировщик, ingress), внести адреса всех: иначе
   клиентом окажется внешний hop, а не пользователь. Не вносить сети клиентов и
   `0.0.0.0/0`.
3. Закрыть прямой внешний доступ к backend в обход доверенного edge (не
   публиковать порт наружу, ограничить сетевым правилом).
4. Настроить edge: добавлять адрес своего соседа в конец `X-Forwarded-For` или
   заменять значение этим адресом. Передавать присланное клиентом значение как
   есть, без добавления, нельзя: правый край цепочки должен принадлежать proxy.
5. Разделить auth, webhook и AI rate limits. Учесть per-process лимиты,
   общий адрес провайдера (вебхуки Telegram приходят с нескольких общих
   адресов, и организации делят предел этого адреса), несколько API и отдельный
   persistent account limiter.
6. Указать публичный origin веб-клиента в `LIDRADAR_ALLOWED_ORIGINS`. Proxy
   завершает TLS, API видит `http` и не узнаёт свой origin по схеме: без списка
   каждая мутация браузера, включая вход, получает `403 ORIGIN_NOT_ALLOWED`.
   В `staging` и `production` процесс `api` без списка не запускается.
7. Сохранить версию конфигурации без секретов и выполнить тесты ниже.

## Диагностика

- При старте `api` пишет `http.trusted_proxies` со списком принятых сетей.
- `http.forwarded_header_ignored` (не чаще раза в минуту, без адресов) значит, что
  заголовок пришёл, но не принят. Причина `no_trusted_proxies` — список пуст и
  клиенты за proxy делят один адрес; `peer_not_trusted` — заголовок прислал узел
  вне списка: либо в списке нет адреса proxy, либо к API обращаются мимо proxy.
  Адрес proxy, каким его видит API, определяют по сети контейнеров или pod
  (`docker network inspect`, `kubectl get pod -o wide`).
- Если все пользователи получают `429` одновременно, сначала проверить этот
  журнал, а не поднимать пределы.

## Обязательные тесты

Автоматические (в CI, ADR 0049): разбор цепочки (подделка слева, несколько
строк, порт, IPv6, повреждённые записи, длинная цепочка), клиенты за proxy не
делят предел, подмена заголовка недоверенным узлом не обходит предел и не
переносит его на постороннего, постоянные пределы PostgreSQL и адрес в сеансе и
журнале входа, отказы конфигурации, правила частоты независимы по префиксам.
Сквозной прогон запущенных API и proxy-заглушки (2026-10-10) повторил это же на
процессах. Эти проверки не заменяют следующие на настоящем edge:

- Два разных внешних клиента получают разные персональные IP-buckets там,
  где это предусмотрено политикой; пять регистраций одного не исчерпывают
  лимит всех пользователей за proxy.
- Произвольный `X-Forwarded-For` снаружи, отправленный через настоящий proxy, не
  меняет доверенный IP и не позволяет обойти ограничитель; отсутствующий или
  повреждённый заголовок не даёт bypass.
- Прямое соединение с API извне недоступно; внутренние разрешённые пути не
  смешиваются с пользовательскими.
- Реальные webhook burst и опрос AI не расходуют auth bucket.
- Вход и другие изменяющие запросы с `Origin` публичного адреса проходят
  через proxy; запрос с чужим `Origin` получает `403 ORIGIN_NOT_ALLOWED`.
- При нескольких экземплярах измеряется фактический суммарный предел,
  возвращаются корректные `429`/`Retry-After`, секреты не попадают в журнал.

## Условие остановки

Если список не задан или в нём нет адреса proxy, production за proxy не
допускается: клиенты делят адрес, а при прямом обращении мимо proxy заголовок
подделывается. Не отключать rate limit, не вносить в список сети клиентов или
`0.0.0.0/0` и не начинать доверять всем forwarded headers как временное
исправление.

Для непредвиденного агрегирования лимитов закрыть/ограничить входящий трафик,
вернуть проверенную конфигурацию и повторить тесты. Доказательства хранятся
в [deployment-gate](../engineering/RELEASE_GATES.md#rg-deploy).
