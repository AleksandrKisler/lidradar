# Развёртывание за reverse proxy и доверенный адрес клиента

Статус: `REQUIRED_NOT_VERIFIED`, H-10. Эта инструкция задаёт условия допуска,
а не несуществующий набор готовых параметров конкретного ingress.

## Исходное ограничение

Описанный HTTP-лимитер использует адрес соединения, а не произвольные
forwarded headers. При обычной TLS-терминации на proxy разные пользователи
могут выглядеть как один адрес и делить лимиты входа/регистрации.

## До открытия трафика

1. Записать всю цепочку: клиент, CDN/LB, ingress, API; для каждого hop указать
   доверенную сеть, способ установления исходного IP и владельца конфигурации.
2. Выбрать поддержанный реализацией механизм: сохранение адреса на транспортном
   уровне либо валидация forwarded headers только от явно доверенных proxy.
   Название runtime-настройки подтверждается по коду, здесь оно не выдумывается.
3. Закрыть прямой внешний доступ к backend в обход доверенного edge.
4. На edge удалять/перезаписывать недоверенные клиентские заголовки; порядок
   разбора цепочки должен быть однозначным для одного и нескольких proxy.
5. Разделить auth, webhook и AI rate limits. Учесть per-process лимиты,
   общий адрес провайдера, несколько API и отдельный persistent account limiter.
6. Сохранить версию конфигурации без секретов и выполнить тесты ниже.

## Обязательные тесты

- Два разных внешних клиента получают разные персональные IP-buckets там,
  где это предусмотрено политикой; пять регистраций одного не исчерпывают
  лимит всех пользователей за proxy.
- Произвольный `X-Forwarded-For` снаружи не меняет доверенный IP и не позволяет
  обойти ограничитель; отсутствующий/повреждённый заголовок не даёт bypass.
- Прямое соединение с API извне недоступно; внутренние разрешённые пути не
  смешиваются с пользовательскими.
- Реальные webhook burst и опрос AI не расходуют auth bucket.
- При нескольких экземплярах измеряется фактический суммарный предел,
  возвращаются корректные `429`/`Retry-After`, секреты не попадают в журнал.

## Условие остановки

Если механизм определения IP не подтверждён кодом и тестом, production
за proxy не допускается. Не отключать rate limit и не начинать доверять
всем forwarded headers как временное исправление.

Для непредвиденного агрегирования лимитов закрыть/ограничить входящий трафик,
вернуть проверенную конфигурацию и повторить тесты. Доказательства хранятся
в [deployment-gate](../engineering/RELEASE_GATES.md#rg-deploy).
