# Резервные копии по расписанию и копия вне хоста

Редакция 2026-10-10, [ADR 0051](../adr/0051-offhost-backups.md). Служба `backup`
production-стека ([production-deployment.md](production-deployment.md)) каждые 10 минут
снимает копию PostgreSQL, шифрует её открытым ключом age и загружает в S3-совместимое
хранилище вне хоста. Процедура проверена на Docker Desktop с настоящими PostgreSQL 18,
age и rclone и с MinIO в роли хранилища; на настоящем поставщике хранилища и Linux-хосте
она не выполнялась (см. «Что не закрыто»).

```
хост                                                 хранилище вне хоста           операторы
backup (каждые 10 мин)                               frequent/<штамп>.dump.age     приватные ключи age
  pg_dump → проверка → age (публичный ключ)  ──▶     frequent/<штамп>.manifest.json ключ чтения хранилища
  загрузка → скачивание обратно и сверка             daily/ (раз в сутки)          копия .env
  манифест последним = «копия полная»                _check/ (пробные циклы)
```

На хосте нет приватного ключа age и нет права удалять вынесенные копии. Расшифровать копию
может только оператор, а срок хранения задаёт поставщик правилами жизненного цикла.

## 1. Подготовка (один раз, до первого запуска)

### 1.1. Хранилище

Любое S3-совместимое. Страну и поставщика выбирает владелец, в том числе с учётом
требований к месту хранения персональных данных: копии содержат переписки клиентов.

1. Создайте бакет и **включите версионирование** (или блокировку объектов). Ключ записи
   способен перезаписать существующий объект; версионирование оставляет оригинал доступным
   по идентификатору версии (проверено на MinIO: после перезаписи мусором оригинал читается,
   удалить его ключом записи нельзя).
2. Создайте два ключа доступа. Политики ниже проверены на MinIO; названия действий общие
   для S3-совместимых хранилищ, но у вашего поставщика их нужно проверить.

   Ключ **записи** (на хосте): только запись и чтение объектов, без перечня и удаления.

   ```json
   {"Version": "2012-10-17", "Statement": [{"Effect": "Allow", "Action": ["s3:PutObject", "s3:GetObject"], "Resource": ["arn:aws:s3:::BUCKET/*"]}]}
   ```

   Ключ **чтения** (у операторов, на хосте не хранится): чтение и перечень.

   ```json
   {"Version": "2012-10-17", "Statement": [
     {"Effect": "Allow", "Action": ["s3:GetObject"], "Resource": ["arn:aws:s3:::BUCKET/*"]},
     {"Effect": "Allow", "Action": ["s3:ListBucket"], "Resource": ["arn:aws:s3:::BUCKET"]}]}
   ```

   Проверьте границы: ключ записи должен получать отказ на перечень (`rclone lsf`) и на
   удаление, ключ чтения — на запись. С такими правами многочастная загрузка файлов больше
   порога `upload_cutoff` тоже работает (проверено).
3. Правила жизненного цикла (срок хранения — предложение до решения H-12):

   ```bash
   mc ilm rule add --prefix "frequent/" --expire-days 2  --noncurrent-expire-days 3 ALIAS/BUCKET
   mc ilm rule add --prefix "daily/"    --expire-days 35 --noncurrent-expire-days 3 ALIAS/BUCKET
   mc ilm rule add --prefix "_check/"   --expire-days 1  --noncurrent-expire-days 1 ALIAS/BUCKET
   ```

   Синтаксис проверен на MinIO (правила создаются и выводятся), срабатывание по времени не
   проверялось. У другого поставщика задайте те же сроки его средствами; без правил копии
   копятся бесконечно, потому что процесс на хосте ничего не удаляет. Данные удалённых
   клиентов остаются в копиях до истечения срока.

### 1.2. Ключи age

Каждый хранитель на **своём** компьютере (не на хосте и не в репозитории):

```bash
age-keygen -o lidradar-backup-<имя>.key        # печатает публичный ключ age1…
age-keygen -y lidradar-backup-<имя>.key        # публичный ключ ещё раз
```

Храните приватный файл в менеджере паролей и во второй офлайн-копии. Назначьте не меньше
двух хранителей: публичные ключи всех идут через запятую в `LIDRADAR_BACKUP_AGE_RECIPIENTS`,
и любой из них расшифровывает копию. **Потеря всех приватных ключей делает все копии
нечитаемыми** — восстановить их нечем. Ошибка в публичном ключе (чужой, с опечаткой) тоже
не заметна по успешным циклам: поэтому в п. 2.3 расшифровка обязательна.

### 1.3. Внешний мониторинг

Возраст последней копии надёжно контролирует сервис, который ждёт сигнала и поднимает
тревогу, когда он не пришёл (healthchecks.io или аналог, в том числе на своём сервере).
Создайте проверку «успех» с периодом 10 минут и допуском 5 минут и, если сервис умеет,
отдельный адрес сбоя. Их адреса содержат секрет и идут в `.env` как
`LIDRADAR_BACKUP_PING_URL` и `LIDRADAR_BACKUP_FAIL_URL`. Службе достаточно простого GET. Если
хост пропадёт, сигналы прекратятся, и тревога придёт сама. Каналы оповещения (почта,
Telegram) настраиваются в самом сервисе.

### 1.4. Переменные `.env`

Обязательны (без них стек не запустится):

```bash
LIDRADAR_BACKUP_REMOTE=offhost:BUCKET/prod            # бакет и префикс
LIDRADAR_BACKUP_S3_ENDPOINT=https://s3.example.com    # адрес API хранилища
LIDRADAR_BACKUP_S3_ACCESS_KEY_ID=…                    # ключ записи из п. 1.1
LIDRADAR_BACKUP_S3_SECRET_ACCESS_KEY=…
LIDRADAR_BACKUP_AGE_RECIPIENTS=age1…,age1…            # публичные ключи хранителей
```

Необязательные: `LIDRADAR_BACKUP_S3_REGION`, `LIDRADAR_BACKUP_S3_PROVIDER` (по умолчанию
`Other`; для AWS `AWS` без адреса), `LIDRADAR_BACKUP_INTERVAL` (`10m`, не чаще раза в минуту),
`LIDRADAR_BACKUP_MAX_AGE` (`15m`), `LIDRADAR_BACKUP_PING_URL`, `LIDRADAR_BACKUP_FAIL_URL`,
`LIDRADAR_BACKUP_DATABASE_URL` (по умолчанию как у приложения), `LIDRADAR_BACKUP_MEMORY`.
Для хранилища не на S3 (SFTP и другие бэкенды rclone) задайте имя и путь в
`LIDRADAR_BACKUP_REMOTE` и параметры rclone переменными `RCLONE_CONFIG_<ИМЯ>_*` через
compose-override; такие хранилища не проверялись.

Образ `lidradar-backup` собирает тот же `scripts/build-images.sh`; на хост он доставляется
вместе с остальными образами выпуска.

## 2. Первый запуск и проверка

1. Пробный цикл без влияния на статус и мониторинг: объекты уходят в `_check/`.

   ```bash
   cd /opt/lidradar/deploy/production
   docker compose run --rm backup check
   ```

   Ожидается событие `backup.succeeded` с `"tier":"_check"`. При ошибке сообщение называет
   шаг (`database`, `dump`, `validate`, `encrypt`, `upload`, `verify`); типичные причины —
   в разделе 7.
2. Запустите стек: `docker compose up -d`. Служба снимает первую копию сразу и затем по
   сетке времени (:00, :10, :20…). Состояние:

   ```bash
   docker compose exec -T backup lidradar-backup status
   docker compose logs backup
   ```

3. **Обязательно: докажите, что приватный ключ подходит.** На компьютере хранителя (не на
   хосте) скачайте и расшифруйте последнюю копию ключом чтения и приватным ключом. Нужен
   тот же образ (`docker load` или сборка):

   ```bash
   mkdir -p restore && docker run --rm --user "$(id -u):$(id -g)" \
     -e LIDRADAR_BACKUP_REMOTE=offhost:BUCKET/prod -e LIDRADAR_BACKUP_S3_ENDPOINT=https://s3.example.com \
     -e LIDRADAR_BACKUP_S3_ACCESS_KEY_ID -e LIDRADAR_BACKUP_S3_SECRET_ACCESS_KEY \
     -e LIDRADAR_BACKUP_SPOOL=/out/.spool \
     -v "$PWD/lidradar-backup-<имя>.key:/run/age.key:ro" -v "$PWD/restore:/out" \
     lidradar-backup:<тег> fetch --identity /run/age.key --output /out
   ```

   (ключи доступа — в окружении оболочки хранителя). Команда скачивает самую новую полную
   копию (с манифестом), сверяет сумму шифротекста и расшифрованной выгрузки и проверяет
   оглавление; результат — файл `restore/lidradar-<штамп>.dump` и JSON манифеста. Расшифрованный файл —
   открытый текст всех данных: после проверки удалите его. Без этого шага настройку нельзя
   считать законченной.
4. Учение с восстановлением в базу. Нужен PostgreSQL для учебной базы (staging или
   временный контейнер у оператора), его адрес — в `LIDRADAR_BACKUP_DATABASE_URL`; роль в
   адресе должна уметь создавать базы (на стеке это владелец `lidradar`, рабочий логин
   `lidradar_runtime`, под которым по умолчанию идут копии, не может):

   ```bash
   docker run --rm --user "$(id -u):$(id -g)" … -e LIDRADAR_BACKUP_DATABASE_URL=postgres://… \
     -v "$PWD/lidradar-backup-<имя>.key:/run/age.key:ro" lidradar-backup:<тег> drill --identity /run/age.key
   ```

   `drill` создаёт базу `lidradar_drill_<штамп>`, восстанавливает копию, сверяет число таблиц,
   миграцию и счётчики с манифестом, удаляет базу и печатает время скачивания, расшифровки
   и восстановления. Код 1 — расхождение. Не запускайте `drill` на production-хосте: ему
   нужен приватный ключ, а учебная база нагружает рабочий кластер.
5. Проверьте тревогу: остановите службу (`docker compose stop backup`) и убедитесь, что
   через 15 минут пришло оповещение мониторинга; верните (`docker compose start backup`).

## 3. Повседневно

| Что | Как |
|---|---|
| Возраст последней точки | `docker compose exec -T backup lidradar-backup status` (код 1, если старше допустимого; `--json` для машин) |
| Здоровье | `docker compose ps backup` (`healthy`, пока точка не старше `LIDRADAR_BACKUP_MAX_AGE`) |
| Журнал | `docker compose logs backup`; события ниже |
| Приёмка выпуска | `scripts/smoke-production.sh … --compose-dir deploy/production` читает тот же статус |
| Копии в хранилище | `docker run … lidradar-backup:<тег> list` (ключ чтения) |
| Копия вручную перед обновлением | `docker compose exec -T backup lidradar-backup once`, либо прежний `scripts/backup.sh` |

События журнала (JSON, как у приложения): `backup.started`, `backup.succeeded`
(`seconds`, `dump_seconds`, `upload_seconds`, `bytes`, `gap_seconds`), `backup.failed`
(`step`: `database`, `dump`, `validate`, `encrypt`, `upload`, `verify`, `manifest`,
`timeout`, `cycle`), `backup.daily_failed` (суточный ярус не записан, основная точка
подтверждена), `backup.skipped` (предыдущий цикл ещё идёт), `backup.ping_failed` (сигнал
мониторингу не доставлен, копия при этом создана), `backup.stopping`. Секреты, пароль
базы и адреса сигналов в журнал не попадают.

**RPO.** Наихудшая потеря данных при внезапной гибели хоста — время от начала выгрузки
последней подтверждённой копии до этого момента, то есть до `интервал + время цикла`.
`status` показывает наибольший разрыв между подтверждёнными точками с запуска (`maxGapSeconds`):
это измеренный RPO для RG-DR. Замер 2026-10-10 на наборе этапа 25 (100 организаций, 500 000
сообщений, база 386 МБ, шифротекст 21,4 МиБ, хранилище без глобальной сети): выгрузка 1–2 с, загрузка
со сверкой 0–2 с, цикл 2–4 с, разрыв при интервале 60 с — 62–63 с, то есть интервал плюс 2–3 с.
Пик памяти службы 21,8 МиБ. На настоящем канале и на ваших данных замер повторите: он входит в RG-DR.

## 4. Восстановление

Для любого восстановления нужны: приватный ключ age, ключ чтения хранилища, `.env` (ключ
шифрования приложения, токен Telegram, пароль базы) и файлы `deploy/` и `scripts/` того же
выпуска, что образы. Ключ шифрования приложения (`LIDRADAR_INTEGRATION_ENCRYPTION_KEY`) в копию
базы не входит: без него сохранённые токены каналов не расшифровать.

### 4.1. Потеря хоста: новый хост

1. Подготовьте хост по [production-deployment.md](production-deployment.md) §§ 1–2: образы
   выпуска (`docker load`), `deploy/` и `scripts/`, `.env`. Не запускайте весь стек.
2. Поднимите **только** базу и дождитесь готовности: `docker compose up -d --wait postgres`. Если
   запустить стек целиком, служба `backup` снимет копию пустой базы, и она станет самой новой точкой.
   Готовой база считается по TCP, то есть после выполнения файла ролей при инициализации тома.
3. Восстановите одной командой (приложение остановлено, `backup` не запущен). Ключ чтения
   передаётся окружением команды и заменяет ключ записи из `.env` только на этот запуск:

   ```bash
   cd /opt/lidradar/deploy/production
   read -rs LIDRADAR_RESTORE_S3_SECRET_ACCESS_KEY && export LIDRADAR_RESTORE_S3_SECRET_ACCESS_KEY
   export LIDRADAR_RESTORE_S3_ACCESS_KEY_ID=…
   ../../scripts/restore-offhost.sh --identity /safe/place/lidradar-backup-<имя>.key --replace-database
   ```

   Скрипт скачивает копию контейнером `backup` (сверка сумм, расшифровка), восстанавливает её
   в новую базу, выдаёт роли и права и переименовывает: пустая `lidradar` становится
   `lidradar_replaced_<время>`, восстановленная — `lidradar`. Ничего не удаляется. Выбрать
   точку: `--stamp ШТАМП` (штампы видны в `list`), ярус суточных копий: `--tier daily`.
   Без `--replace-database` скрипт восстанавливает в `lidradar_restored` и рабочую базу не трогает.
4. Запустите стек: `docker compose up -d`; убедитесь, что `migrate` завершился, а `backup` снял
   первую копию (`status`). Удалите приватный ключ age с хоста.
5. Проверьте: `scripts/smoke-production.sh … --version <тег> --compose-dir deploy/production`; вход
   прежним пользователем; число организаций и сообщений; **ключ шифрования**:
   `POST /api/v1/integrations/{id}/health/check` для существующего подключения Telegram даёт `200`
   (реквизиты расшифрованы), а `503 CONNECTOR_UNAVAILABLE` означает неверный ключ приложения.
   Замер 2026-10-10 (набор этапа 25, образы уже на хосте, хранилище без глобальной сети): `postgres`
   готов за 7 с, `restore-offhost.sh --replace-database` — 8 с (скачивание 1 с, расшифровка меньше
   секунды, восстановление, роли, переименование), остальной стек здоров через 11 с: 26 с от пустого
   хоста до здорового стека. К этому добавляются установка Docker, доставка образов и файлов,
   подготовка `.env`, время загрузки копии по вашему каналу и проверки оператора.
6. Запишите в [RG-DR](../engineering/RELEASE_GATES.md#rg-dr): точку восстановления (момент
   данных из манифеста), потерянное окно, время каждого шага и ограничения.

### 4.2. Порча данных на живом хосте

Тот же скрипт: остановите `api worker scheduler backup`, выполните `restore-offhost.sh … --replace-database`,
верните сервисы. Испорченная база сохраняется как `lidradar_replaced_<время>` для разбора и
удаляется вручную после проверки. Данные после выбранной точки потеряны.

## 5. Ротация и потери

| Событие | Что делать |
|---|---|
| Смена ключа доступа к хранилищу | Создайте новый ключ записи, обновите `.env`, `docker compose up -d backup`, дождитесь `backup.succeeded`, удалите старый ключ |
| Новый хранитель age или смена ключа | Добавьте публичный ключ в `LIDRADAR_BACKUP_AGE_RECIPIENTS`, `docker compose up -d backup`. Действует на новые копии; прежние читаются прежними ключами, поэтому старый приватный ключ храните до истечения срока старых копий |
| Подозрение на утечку приватного ключа age | Замените получателей как выше; копии, снятые под скомпрометированный ключ, считайте раскрытыми и удалите их у поставщика |
| Утеряны все приватные ключи | Прочитать существующие копии нельзя. Сразу создайте новые ключи и добавьте их: новые копии будут читаемы |
| Подозрение на компрометацию хоста | Ключ записи отзовите. Версионирование хранилища сохраняет оригиналы, переписанные ключом записи; восстановитесь из версии до инцидента |

## 6. Диагностика

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| Стек не запускается: «задайте LIDRADAR_BACKUP_REMOTE» | пропущена обязательная переменная | заполнить `.env` (п. 1.4) |
| `backup.configuration_invalid`: получатель не принят | опечатка в публичном ключе | проверить `age-keygen -y файл`; значение — `age1…` |
| `backup.failed step=database` | база недоступна или нет таблиц приложения | `docker compose ps postgres migrate`; `backup` ждёт завершения `migrate` |
| `step=dump`: роль не видит все строки | роль копии — не суперпользователь и не член `lidradar_platform` (на стеке копии идут рабочим логином `lidradar_runtime`, он состоит в этой роли) | задать `LIDRADAR_BACKUP_DATABASE_URL` с подходящей ролью |
| `step=dump`: server version mismatch | сервер новее клиента `pg_dump` образа | поднять версию клиента в `deploy/backup/Dockerfile` и пересобрать образ |
| `step=upload`/`verify`: 403 или `Access Denied` | ключ записи без прав, неверный секрет, бакет или адрес | проверить политику п. 1.1 и `LIDRADAR_BACKUP_S3_*` |
| `step=verify`: объект не совпал | повреждение при передаче или прокси между хостом и хранилищем | повторить; при постоянстве — сеть или поставщик |
| `step=timeout` | цикл длиннее `LIDRADAR_BACKUP_CYCLE_TIMEOUT` (20 минут) | база выросла: пересмотреть интервал и хранилище (ADR 0051, последствия) |
| `backup.skipped` часто | цикл дольше интервала | то же |
| `list`, `fetch` без `--stamp`, `drill`: `403` на перечне бакета | использован ключ записи с хоста (у него нет права на перечень) | взять ключ чтения; с известным штампом `fetch --stamp` обходится правом на чтение |
| `fetch`: «ключ не подходит» | приватный ключ не соответствует публичным в `.env` на момент копии | сверить `age-keygen -y` с получателями в манифесте (`recipients`) |
| `fetch`: контрольная сумма не совпала | объект в хранилище повреждён или подменён | взять предыдущую копию (`--stamp`); оригинал — из версии объекта у поставщика |
| контейнер `backup` `unhealthy` | точка старше `LIDRADAR_BACKUP_MAX_AGE` | `status` показывает ошибку последнего цикла; чинится по строке выше |
| От мониторинга нет тревоги при остановленной службе | неверный адрес, период или допуск проверки | п. 1.3 и проверка из п. 2.5 |

## Что не закрыто

- На настоящем поставщике хранилища и Linux-хосте не проверялось: политики доступа и
  срабатывание правил жизненного цикла (проверены на MinIO), реальная пропускная способность
  канала, квоты и стоимость трафика сверки.
- Размер базы выше набора этапа 25 не измерялся. Цикл длиннее ~5 минут означает, что логические
  копии исчерпаны: нужна WAL-архивация (ADR 0051, альтернативы).
- Сроки хранения — предложение до H-12; удаление данных клиента из копий до истечения срока
  невозможно.
- Хранение `.env`, образов и ключей у операторов, график ротации и учение на новом хосте с
  реальным провайдером остаются ручными; RG-DR не закрыт.
