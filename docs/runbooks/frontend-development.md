# Локальный бэкенд и учебные данные для разработки интерфейса

Это отдельный стенд для фронтенда после этапа 25. Рабочий `compose.yaml`,
существующая база, `.env`, Telegram и домашний AI-сервер не используются.
Все клиенты, сообщения и суммы вымышлены. Настоящие данные сюда не переносите.

## 1. Быстрый запуск

Нужны запущенный Docker Desktop и команда `make`. Go на компьютере не нужен:
сборка выполняется в контейнерах из существующего Dockerfile проекта.
При первой сборке нужен доступ к реестру образов и зависимостям Go.

Из терминала:

```sh
cd /Users/aleksandrkisler/Develop/Lidradar
make frontend-up
curl --fail http://127.0.0.1:8081/health/ready
```

На другом компьютере первая команда должна указывать на ваш каталог репозитория.

`frontend-up` последовательно запускает PostgreSQL, применяет обычные миграции
схемы, применяет отдельную миграцию `frontend-v1` и запускает API. Повторный
запуск не создаёт дубликаты и не сбрасывает ваши изменения. Успех проверки
готовности — HTTP 200 и последняя миграция `000021_auth_audit`.

| Назначение | Адрес |
| --- | --- |
| API учебного стенда | `http://127.0.0.1:8081/api/v1` |
| Проверка готовности | `http://127.0.0.1:8081/health/ready` |
| PostgreSQL учебного стенда | `127.0.0.1:5433`, база `lidradar_frontend` |
| Прежний API и PostgreSQL | `8080` и `5432`; этот стенд их не меняет |

Контейнеры имеют префикс `lidradar-frontend-`, отдельную сеть и отдельный том
`lidradar-frontend_frontend-postgres`. Порты опубликованы только на локальном
компьютере. Пользователь и пароль **учебного PostgreSQL** — `lidradar` / `lidradar`;
это не пароли входа в приложение. Не публикуйте этот стенд в интернете.

## 2. Три пользователя

Каждый пользователь — `OWNER` своей организации. У них нет доступа к двум
другим организациям и нет прав администратора платформы.

| Вход | Сценарий | Точки | Переписки | Сообщения | Сделки | Риски: всего / активных |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `empty@lidradar.test` | Новый пустой кабинет | 0 | 0 | 0 | 0 | 0 / 0 |
| `small@lidradar.test` | Небольшая студия | 1 | 24 | 144 | 24 | 20 / 10 |
| `large@lidradar.test` | Сеть студий, проверка страниц списков | 3 | 240 | 1440 | 240 | 200 / 100 |

Общий пароль для этих **трёх учебных пользователей** создаётся случайно при
первом применении и записывается в файл с правами `0600`:

```text
runtime/frontend/password.txt
```

Посмотреть его самостоятельно:

```sh
cat runtime/frontend/password.txt
```

Не отправляйте пароль в Git, снимки экрана или журналы. Каталог `runtime`
исключён из Git и контекста Docker. В базе хранятся только Argon2id-хеши с
разными случайными солями. Команда миграции сам пароль не печатает.
Повторный `up` не меняет пароль, даже если вы отредактировали файл. Откат
сохраняет файл, чтобы следующий `up` использовал тот же пароль.

Постоянные идентификаторы организаций:

```text
empty: 01990000-0000-7000-8000-000000000201
small: 01990000-0000-7000-8000-000000000202
large: 01990000-0000-7000-8000-000000000203
```

В интерфейсе всё равно получайте выбранную организацию через `auth/me`, а не
зашивайте эти идентификаторы в рабочий код.

## 3. Что можно разрабатывать на этом наборе

- Первый вход, пустой радар, отсутствие точек, услуг, каналов и переписок.
- Радар: пять типов рисков, семь состояний, уровни `MEDIUM`, `HIGH`, `CRITICAL`,
  фильтры по точке, типу и важности, переходы по страницам.
- Карточка риска: рекомендация, действия, последний исход, переход в переписку.
- Переписки: входящие и исходящие сообщения, ответы на сообщения, удалённое
  сообщение, длинное имя, Unicode, буквальный текст с HTML-подобными символами.
  Этот текст нельзя вставлять через `innerHTML`.
- Вложение без текста: метаданные изображения есть, двоичного файла нет.
  Ключ `fixtures/not-uploaded/...` — заглушка; показывайте состояние
  недоступного вложения, не ожидайте настоящей фотографии.
- Каталог: точная цена, диапазон, отсутствие цены и неактивная услуга.
  У сделок без оценки потенциал равен `null`, а не нулю.
- Каналы: у большой организации `ACTIVE`, `DEGRADED`, `ERROR`, `DISCONNECTED`.
  Это `TEST`/`IMPORT`, не имитация подключённого настоящего Telegram.
- Выручка: у небольшой организации 14 000 ₽ подтверждено, из них 7 000 ₽
  возвращено; у большой — 140 000 ₽ и 70 000 ₽ соответственно. Для
  возвращённой выручки записана связная цепочка «риск → действие → исход → оплата».
- Аналитика за последние 30 дней, обратная связь и личные настройки уведомлений.
  Обратная связь намеренно неполная: можно показать недостаточное покрытие.

Времена рассчитываются относительно применения миграции. С течением недель
данные естественно выходят из окна аналитики; для свежих дат выполните откат
и повторное применение. Идентификаторы трёх пользователей/организаций сохранятся,
а идентификаторы вложенных сущностей будут новыми.

Все риски помечены `MANUAL`, `SYNTHETIC_FRONTEND_CASE`, `frontend-fixture/v1`:
это учебные состояния интерфейса, а не свидетельство срабатывания правил или
работы модели. AI-запуски, Telegram-привязки и согласие на обучение не создаются.
Очереди заданий и исходящих событий изначально пусты. Уведомления записаны как
локальные завершённые доставки `IN_APP`; отдельной HTTP-ленты уведомлений в
текущем API нет. Отсутствующие операции не подменяются новыми маршрутами.

## 4. Подключение фронтенда

API использует серверный сеанс в HttpOnly cookie `lidradar_session`, не JWT.

1. `POST /api/v1/auth/login` с JSON `email` и `password`.
2. `GET /api/v1/auth/me` — прочитать `memberships[].tenantId`.
3. Передавать `X-Tenant-ID` выбранной организации в запросах к её данным.
4. Сохранять cookie браузером; пароль и cookie не хранить в `localStorage`.
5. Для создания действий, исходов и выручки отправлять уникальный
   `Idempotency-Key`; при повторе того же запроса сохранять тот же ключ.

Для разработки с Vite используйте проксирование `/api` на бэкенд. Пример
фрагмента **вашего** `vite.config.ts` (параметры описаны в
[документации Vite](https://vite.dev/config/server-options#server-proxy)):

```ts
import { defineConfig } from "vite";

export default defineConfig({
  server: {
    host: "127.0.0.1",
    port: 5173,
    strictPort: true,
    proxy: {
      "/api": {
        target: "http://127.0.0.1:8081",
        changeOrigin: true,
      },
    },
  },
});
```

Из браузера обращайтесь к относительным адресам:

```ts
const login = await fetch("/api/v1/auth/login", {
  method: "POST",
  credentials: "include",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ email, password }), // значения из формы входа
});
if (!login.ok) throw new Error("Не удалось войти");

const me = await fetch("/api/v1/auth/me", {
  credentials: "include",
}).then(response => response.json());

const radar = await fetch("/api/v1/radar", {
  credentials: "include",
  headers: { "X-Tenant-ID": me.memberships[0].tenantId },
}).then(response => response.json());
```

Список разрешённых источников в Compose — защита от поддельных запросов,
**не настройка CORS**. Прямые обращения из браузера с `5173` на `8081` могут
не работать; используйте прокси и относительный `/api`. Не смешивайте
`localhost` и `127.0.0.1` в адресах страницы и запросов. Cookie не разделяются
по порту: для параллельной работы с прежним интерфейсом используйте отдельный
профиль браузера или разные имена хоста, чтобы сеансы не перезаписывали друг друга.

Для SSE используйте клиент, умеющий передавать `X-Tenant-ID` (например,
потоковый `fetch`): встроенный `EventSource` не умеет задавать этот заголовок.
Сигнал — повод перечитать REST-данные, не самостоятельная копия состояния.

Контракт: [OpenAPI](../../contracts/openapi/openapi.yaml). Основные точки чтения:
`/radar`, `/risks`, `/conversations`, `/analytics/summary`, `/organization`,
`/locations`, `/services`, `/integrations`, `/notifications/preferences`
с префиксом `/api/v1`. Списки используют `limit` и непрозрачный `cursor`,
а не произвольный номер страницы. Запрет чужой организации — 403;
чужой идентификатор внутри своей организации — 404.

## 5. Применение, состояние, откат

Из корня репозитория:

```sh
# Применить учебную миграцию к уже подготовленной базе.
make frontend-data-up

# Проверить факт применения и текущие числа записей.
make frontend-data-status

# Остановить только учебные процессы и откатить учебные кабинеты.
make frontend-data-down

# Заново заполнить базу и запустить API.
make frontend-up
```

**Откат удаляет три учебных кабинета целиком**, включая сообщения, настройки,
действия, исходы, оплаты и другие записи, созданные вами внутри них после
применения. Их сеансы перестанут действовать. При необходимости сначала сохраните
свой сценарий отдельно. Восстановление исходного набора — повторный `up`;
ручные изменения при этом не восстанавливаются.

Обычная схема, её `schema_migrations`, посторонние организации и пользователи
сохраняются. Миграция данных ведёт собственный журнал `frontend_data_migrations`
с контрольной суммой; одинаковый `up`/`down` не создаёт повторный эффект.
Применённые SQL-файлы не редактируйте: для нового набора нужна новая версия
либо сначала откат старой версией.

Откат выполняется одной транзакцией под блокировками. Только поимённые запреты
удаления неизменяемых журналов временно приостанавливаются и восстанавливаются
до фиксации; при любой ошибке PostgreSQL откатывает и данные, и эти изменения.
Внешние ключи, проверки и RLS остаются включены. В основной базе этот механизм
недоступен: команда принимает только `development`/`test`, владельца схемы,
базу `lidradar_frontend` и совместимую схему этапа 25.

Если учебный пользователь получил доступ к посторонней организации, стал
администратором, появились реальные реквизиты канала или внешняя ссылка на
удаляемый объект, откат остановится. Не удаляйте такие данные обходными командами:
сначала разберите, почему учебный стенд перестал быть изолированным.

## 6. Фоновая обработка и остановка

Для вёрстки и ручных команд достаточно API и PostgreSQL. Фоновые процессы
по умолчанию выключены, чтобы учебный снимок оставался стабильным.

```sh
# При необходимости проверять задания, события и пересчёт правил.
make frontend-background

# Остановить учебный стенд, сохранив данные и пароль.
make frontend-stop

# Посмотреть состояние и журнал учебного API.
docker compose --env-file /dev/null -f compose.frontend.yaml ps
docker compose --env-file /dev/null -f compose.frontend.yaml logs --tail=80 api
```

Фоновые процессы могут пересчитать ручные учебные состояния после ваших
изменений. Telegram не настроен; AI-задания, если они появились, будут ждать
узел. Для чтения готовых экранов AI-сервер поднимать не требуется. Эта инструкция
не подключает настоящие внешние сервисы и не создаёт фиктивный AI-допуск.

Для остановки **не используйте `down -v`**: это удаление всего учебного тома,
а не откат трёх кабинетов. Обычные миграции схемы в проекте направлены вперёд;
команда `dev-data down` откатывает только тестовые данные.

## 7. Запуск Go-команд без контейнера приложения

Необязательно: удобно для отладки в GoLand. Нужен Go 1.26.x.
PostgreSQL остаётся в отдельном контейнере:

```sh
cd /Users/aleksandrkisler/Develop/Lidradar
docker compose --env-file /dev/null -f compose.frontend.yaml up -d --wait postgres
docker compose --env-file /dev/null -f compose.frontend.yaml stop api worker scheduler

export LIDRADAR_ENV=development
export LIDRADAR_DATABASE_URL='postgres://lidradar:lidradar@127.0.0.1:5433/lidradar_frontend?sslmode=disable'
export LIDRADAR_HTTP_ADDRESS='127.0.0.1:8081'
export LIDRADAR_COOKIE_SECURE=false
export LIDRADAR_ALLOWED_ORIGINS='http://127.0.0.1:5173,http://localhost:5173'

go run ./backend/cmd/migrate
go run ./backend/cmd/dev-data up
go run ./backend/cmd/dev-data status
go run ./backend/cmd/api
```

Сначала остановите API через `Ctrl+C`, затем для отката:

```sh
go run ./backend/cmd/dev-data down -confirm frontend-v1
```

Go-команды сами не читают `.env`. Не подключайте его через `source` для этого
стенда. В настройках GoLand используйте указанные переменные, а не реквизиты
основного сервера. Для `worker` и `scheduler` задаются те же переменные базы.

## 8. Проверки и частые проблемы

Полный набор тестов с PostgreSQL (каждый интеграционный тест создаёт и удаляет
собственную временную схему; ваши три кабинета в `public` остаются):

```sh
export LIDRADAR_DATABASE_URL='postgres://lidradar:lidradar@127.0.0.1:5433/lidradar_frontend?sslmode=disable'
make test-db GO_TEST_FLAGS='-count=1'
go vet ./...
go run ./backend/tools/archcheck -root backend
```

Только учебная миграция и проверка её API:

```sh
go test -count=1 -v ./backend/internal/devdata ./backend/cmd/dev-data
go test -count=1 -run TestFrontendDataThroughRealAPI -v ./backend/internal/integration
```

- `503` на готовности: сборка и схема не совпали; повторите `make frontend-up`.
- Порт занят: проверьте `docker ps`; не останавливайте посторонний сервер.
  Штатно новый стенд использует `8081`/`5433`, а прежний — `8080`/`5432`.
- `401`: проверьте пароль, cookie и одинаковый хост. После отката войдите заново.
- `403 ORIGIN_NOT_ALLOWED`: проверьте адрес фронтенда и список источников в Compose.
- `429`: защита входа работает и на учебном стенде. Дождитесь `Retry-After`,
  не запускайте бесконечные повторы входа из интерфейса.
- PostgreSQL `23505`: занята почта или идентификатор; чужой аккаунт не перезаписан.
- PostgreSQL `23503`/`55000`: нарушена граница отката или защита журналов;
  вся операция отменена, данные не удалены частично.
- PostgreSQL `55P03`: таблицу держит другой процесс; остановите учебный API,
  `worker`, `scheduler` и повторите откат.
- Неизвестная новая версия схемы: набор рассчитан на миграции по
  `000021_auth_audit`; после будущих этапов понадобится проверенная новая версия
  набора, а не снятие предохранителя вручную.
