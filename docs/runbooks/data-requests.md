# Обращения о данных: выгрузка, закрытие и стирание

Редакция 2026-10-14, [ADR 0059](../adr/0059-data-export-and-account-closure.md). Описывает, что
оператор делает с обращениями людей о своих данных, пока канал приёма таких обращений,
срок ответа и подтверждение личности не определены владельцем и юристом
([ADR 0056](../adr/0056-data-retention-and-erasure.md), п. 7 таблицы решений). Это
**временный порядок**: он не заменяет юридическую процедуру и не обещает людям сроки.

Что человек делает сам, без оператора:

| Что нужно | Как | Кто |
|---|---|---|
| данные своей учётной записи | «Настройки → Аккаунт → Мои данные → Скачать мои данные…», пароль (без организации — страница «Аккаунт») | любой вошедший пользователь |
| закрыть свою учётную запись | «Настройки → Аккаунт → Удаление аккаунта → Удалить аккаунт…», пароль; через 30 суток обезличивание, до этого можно отменить | любой вошедший пользователь, кроме единственного владельца организации и платформенного администратора |
| данные организации (переписки, контакты, деньги, команда) | «Настройки → Данные → Выгрузка данных организации → Скачать архив» | владелец организации |

Оператор вмешивается, только если человек этого сделать не может: потерян пароль и ящик, нужно
стереть без ожидания 30 суток, организация одноместная, нужно закрыть организацию или стереть
данные конечного клиента. Последние два случая автоматизированы не полностью (см. «Что не
автоматизировано»).

## 1. Приём обращения

1. Заведите запись в журнале обращений **вне базы LidRadar** (таблица владельца проекта):
   номер, дата и время получения, что просят, откуда пришло обращение, итог и дата ответа.
   Адрес почты в журнале — только в той мере, в какой он нужен для ответа. Срок ответа
   определит юрист; до тех пор ведите журнал так, чтобы срок можно было проверить задним
   числом (дата получения обязательна).
2. Обращение принимается письменно. Устные просьбы и сообщения без обратного адреса
   фиксируются, но не исполняются.
3. Если человек может войти, предложите самообслуживание из таблицы выше и закройте обращение
   ответом. Оператор не просит пароль и не просит сообщать код из письма.

## 2. Подтверждение личности

Оператор не видит пароль и не может войти от имени пользователя. Стирание необратимо,
поэтому перед командой `erase-user` убедитесь двумя независимыми признаками:

- **Письмо пришло с адреса учётной записи**, и ответ на него вы отправили на тот же адрес
  (адрес берётся из письма, а не из текста обращения). Это не доказывает, что человек владеет
  учётной записью, если ящик взломан, — поэтому нужен ещё второй признак.
- **Сведения, которые знает только владелец:** название организации, роль, примерная дата
  регистрации или последнего входа. Оператор сверяет их в базе
  (`docker compose exec postgres psql -U postgres -d lidradar`, см.
  [production-deployment.md](production-deployment.md)), не называя человеку заранее.

Если признаков недостаточно, не исполняйте: ответьте, что требуется подтверждение, и оставьте
запись открытой. Для людей, которые могут войти, подтверждением служит сам вход: направляйте их в
интерфейс.

## 3. Стереть пользователя немедленно (`erase-user`)

Команда обезличивает пользователя тем же кодом, что и исполнитель по сроку, но без отсрочки
30 суток. Она не удаляет организацию, не передаёт владение и не стирает данные конечных
клиентов.

1. **Сухой запуск** (ничего не меняет, но исполняет весь путь и откатывает его; число строк
   совпадает с боевым запуском):

   ```bash
   cd /opt/lidradar/deploy/production
   docker compose run --rm platform-admin erase-user \
     --email person@example.com --note "обращение №17" --dry-run
   ```

   `--note` — номер обращения из журнала, **без персональных данных**: заметка попадает в
   `admin_audit_log` и остаётся там.
2. Разберите вывод:
   - `блокировка: единственный владелец организации «…»` — пока в организации есть другие
     участники, владение передаёт сам пользователь («Настройки → Команда»); если организация
     одноместная, её нужно закрывать (механизм 5 ADR 0056, ещё не реализован, см. ниже);
   - `блокировка: действующий администратор платформы` — сначала `platform-admin revoke`;
   - `пользователь с такой почтой не найден` — адрес уже обезличен или записан иначе.
   При блокировке ничего не изменено, код возврата ненулевой.
3. **Боевой запуск** — тот же адрес ещё раз в `--confirm-email`:

   ```bash
   docker compose run --rm platform-admin erase-user \
     --email person@example.com --note "обращение №17" --confirm-email person@example.com
   ```

   Команда печатает идентификатор пользователя и число затронутых строк по таблицам.
   **Запишите идентификатор в журнал обращений**: адрес после стирания в базе больше не найти,
   а идентификатор нужен для повтора после восстановления из копии (раздел 5).
4. Система сама отправляет на прежний адрес единственное письмо «Аккаунт LidRadar удалён»;
   дополнительно ответьте на обращение вручную (не раскрывая подробностей, которых человек не
   просил). В журнал воркера попадает событие `account.deletion.anonymized` с идентификатором
   и режимом, без адреса; в `admin_audit_log` — `USER_ERASED` (источник `CLI`, ваша заметка).

Что остаётся после стирания (скажите это человеку, если спросит): записи, которые он вносил в
организациях (действия, исходы, вердикты, подтверждения выручки), остаются в организации без
имени и адреса; IP прошлых входов остаётся в журнале безопасности до механизма 3 ADR 0056;
копии для восстановления хранят данные до 35 суток; письма, уже стоящие в очереди, уйдут или
истекут не позже чем через 7 суток.

## 4. Контроль закрытий по сроку

Самообслуживание исполняет воркер раз в минуту. Раз в минуту же он пишет
`lifecycle.deletions.status`:

```bash
docker compose logs --tail 200 worker | grep lifecycle.deletions.status
```

- `deletions_scheduled` — сколько закрытий ждут срока;
- `deletions_due` — срок наступил, но не исполнено (должно быть 0 в течение минуты);
- `deletions_overdue` — срок наступил больше часа назад: **это сигнал**.

Если `deletions_overdue > 0`:

```bash
docker compose logs --tail 500 worker | grep -E 'account.deletion.(failed|blocked)|lifecycle.deletion_failed'
```

Типичные причины: взаимное ожидание блокировок (`lock_timeout`, временно: пользователь
остаётся в очереди и обрабатывается на следующем проходе), недоступная база, остановленный
`worker`. Постоянный отказ на одном пользователе — ошибка кода: сохраните `user_id` из журнала,
не обходите защиту вручную, заведите задачу разработчику. Пока исполнитель не работает, люди,
запросившие закрытие, остаются с действующей учётной записью (фактически продолжают работать);
это безопасная сторона отказа, но срок, обещанный в письме, нарушен — сообщите им.

`account.deletion.blocked` означает: пока длился срок, пользователь стал единственным
владельцем организации (или администратором платформы). Запрос снят, ему ушло письмо. Ничего
делать не нужно, если он не обратится.

## 5. Повтор после восстановления из копии

Копия, снятая до обезличивания, возвращает человека в базу. Журнала стираний, который
переживает восстановление (механизм 7 ADR 0056), пока нет, поэтому оператор проверяет вручную
**до того, как стек откроется для трафика** (порядок восстановления —
[offhost-backup.md](offhost-backup.md) § 4, [backup-restore.md](backup-restore.md)).

Что вернётся само, а что нет:

| Случай | После восстановления |
|---|---|
| закрытие по сроку, запрос сделан до момента данных копии | назначение сохранено в копии; воркер обезличит пользователя сам в течение минуты после запуска |
| закрытие по сроку, запрос сделан **после** момента данных копии | запрос потерян вместе с данными после копии, пользователь не назначен; он должен запросить закрытие заново, либо оператор повторит стирание по обращению |
| пользователь отменил закрытие после момента данных копии | отмена потеряна, воркер обезличит его по срокам копии; при подозрении сверьте с журналом обращений и дождитесь ответа пользователя до запуска воркера |
| `erase-user` после момента данных копии | **вручную**, всегда |

Порядок:

1. Определите момент данных восстановленной копии (из манифеста, `lidradar-backup list`).
2. Найдите стирания после этого момента. Если сохранена испорченная база
   `lidradar_replaced_<время>` (сценарий порчи данных, [offhost-backup.md](offhost-backup.md) § 4.2),
   возьмите их из неё (под администратором по сокету):

   ```bash
   docker compose exec postgres psql -U postgres -d lidradar_replaced_<время> -At -c \
     "SELECT user_id, operation, created_at FROM auth_audit_log
      WHERE operation IN ('ACCOUNT_ANONYMIZED','ACCOUNT_DELETION_REQUESTED','ACCOUNT_DELETION_CANCELLED')
        AND created_at > '<момент данных копии>' ORDER BY created_at"
   docker compose exec postgres psql -U postgres -d lidradar_replaced_<время> -At -c \
     "SELECT entity_id, details ->> 'note', created_at FROM admin_audit_log
      WHERE operation = 'USER_ERASED' AND created_at > '<момент данных копии>' ORDER BY created_at"
   ```

   Если базы нет (потерян хост), источники — журнал обращений (идентификаторы из раздела 3) и,
   если сохранились, журналы воркера (`account.deletion.anonymized`); ротация журналов
   контейнеров 10 МБ × 5, поэтому на них не надейтесь.
3. Для каждого идентификатора в восстановленной базе найдите адрес и проверьте состояние:

   ```bash
   docker compose exec postgres psql -U postgres -d lidradar -At -c \
     "SELECT email, status, deletion_due_at, deleted_at FROM users WHERE id = '<идентификатор>'"
   ```

   Уже обезличен (`deleted_at` задан) — ничего. Назначен и срок наступил — исполнит воркер. Остальные —
   `erase-user` по их обращению (раздел 3), с заметкой «повтор после восстановления, обращение №…».
4. Запустите **сначала только воркер** и дождитесь `deletions_due = 0`
   (`docker compose up -d worker`; затем `docker compose logs worker | grep lifecycle.deletions.status`).
   Только после этого запускайте остальной стек.
5. Запишите в журнале обращений: сколько стираний повторено и какие не удалось сопоставить.

## Что не автоматизировано

- **Закрытие организации** (механизм 5 ADR 0056): команды нет. Владелец одноместной организации не
  может закрыть свою учётную запись (`SOLE_OWNER`), пока организация жива. Организацию нельзя
  удалить из базы штатными средствами (неизменяемые таблицы, ADR 0052 и 0056): не удаляйте
  строки вручную и не отключайте триггеры. Фиксируйте обращение, сообщите человеку, что закрытие
  организации пока выполняется отдельным решением, и передайте вопрос владельцу проекта.
- **Стирание по запросу конечного клиента организации** (механизм 6 ADR 0056): команды нет;
  переписки принадлежат организации, и первое решение — что обработчик по поручению организации, а
  не LidRadar, получает обращения от её клиентов (рабочее допущение п. 1 таблицы решений ADR 0056).
  Фиксируйте обращение и передайте организации.
- **Выгрузка за человека**: оператор выгрузку не делает. Человеку без доступа поможет сброс пароля
  («Забыли пароль?» на странице входа).

## Открытые решения (владелец и юрист)

- Канал приёма обращений, адрес поддержки для владельцев одноместных организаций, срок ответа.
- Подтверждение личности для людей без доступа к ящику.
- Достаточность состава личной выгрузки и формулировки писем/политики.
- Короче ли должен быть срок для людей без членств в организациях.

Эти пункты также перечислены в разделе «Открыто после принятия» ADR 0059.
