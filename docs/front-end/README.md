**Срез backend:** commit `f6ee61bbd5d3f2e9df2842edba1b7684c731e71c`, OpenAPI `1.0.0`  
**Срез макетов:** `LidRadar_Figma_Import_v0.2`, 3 сентября 2026 года

Этот раздел — единая точка входа для разработки web-интерфейса LidRadar. Он
описывает не только экраны, но и границы продукта, клиентскую архитектуру,
сущности, каждый доступный HTTP-запрос, последовательности, состояния,
права, тестирование, известные разрывы между API и макетами и готовую
декомпозицию работ.

Базовый frontend-проект, пакеты, развёртывание и собственная инструкция его
тестирования уже существуют и в этот backlog не включены. Здесь зафиксирован
контракт прикладной разработки поверх этой базы.

## Источники истины

При расхождении используйте следующий порядок:

1. Фактически подключённый runtime и тесты backend.
2. [OpenAPI-контракт](../../contracts/openapi/openapi.yaml) для формы HTTP.
3. [Backend HTTP API](../backend/04-api.md) и остальные документы
   [`docs/backend`](../backend/README.md) для семантики и ограничений.
4. [Архитектурный baseline](../architecture/ARCHITECTURE.md) и принятые
   [ADR](../adr/README.md).
5. Макеты v0.2 как источник композиции, текста и ожидаемых состояний, но не
   как доказательство существования API.

Если runtime, OpenAPI и документация расходятся, нельзя выбирать удобный
вариант молча. Разрыв добавляется в [реестр готовности](08-readiness-gaps.md),
а реализация блока ждёт согласованного контракта либо использует явно
описанный безопасный fallback.

## Границы продукта

Frontend помогает увидеть риск, понять контекст, перейти к действию и
зафиксировать результат. Он не является CRM или мессенджером и не должен:

- отправлять сообщения клиентам от имени пользователя;
- считать AI-вывод окончательным бизнес-решением;
- смешивать Conversation, Opportunity и Risk в одну сущность;
- трактовать `null`-цену как ноль;
- считать Outcome `PAID` подтверждением денег;
- считать неподтверждённую или неатрибутированную сумму возвращённой выручкой;
- использовать SSE как источник состояния;
- раскрывать существование чужого tenant или чужого объекта;
- показывать ошибку загрузки как пустой список или нулевые показатели;
- хранить пароль или cookie в JavaScript-хранилищах.

Полный backend value loop:

```text
сообщение → Conversation → Opportunity → Risk → Radar/уведомление
          → Recommendation → Action → Outcome → RevenueEvent
          → RevenueAttribution → Confirmed Recovered Revenue
```

Frontend входит в цикл начиная с авторизации и чтения уже сохранённых фактов.
Обработка webhook, фоновые очереди и AI выполняются асинхронно backend-ом.

## Текущая готовность

Поддержанные контрактом части: вход/регистрация, выбор организации,
организация и точки, график, услуги, подключения, личная Telegram-привязка,
личные настройки уведомлений, чтение переписок, чтение и команды Risk,
Opportunity, Action, Outcome, подтверждение выручки, агрегированная аналитика,
SSE-invalidation и platform-admin API.

Целевые экраны нельзя считать полностью готовыми к реализации без закрытия
разрывов. Наиболее важные:

- активная лента Radar не имеет корректного единого server-side фильтра;
- Risk read model не содержит имени контакта, услуги, автомобиля, полного
  времени ожидания и безопасной ссылки во внешний Telegram-контекст;
- список диалогов не содержит контакта, preview и признака риска, а также не
  поддерживает серверный поиск и фильтр «С риском»;
- analytics API не отдаёт временной ряд, последние оплаты и разбиение
  `RECOVERED` / `ORGANIC` / `UNKNOWN` из макета;
- HTTP API команды отсутствует;
- нет утверждённых макетов ряда обязательных маршрутов и mobile-состояний.

Точные последствия и номера prerequisite-задач приведены в
[08-readiness-gaps.md](08-readiness-gaps.md).

## Правило изменения документации

При изменении backend-контракта или макета в одном PR обновляются:

1. соответствующий блок сущностей/API;
2. последовательность и query invalidation;
3. карта экрана и статус готовности;
4. затронутые задачи и acceptance criteria.

Нельзя добавлять ручной DTO, локальный server-state store или временный
endpoint только для обхода несогласованности — сначала меняется нормативный
контракт.
