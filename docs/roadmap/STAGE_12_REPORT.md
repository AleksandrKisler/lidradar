# Отчёт этапа 12 — выручка и формальная атрибуция

Дата проверки: 2026-08-26.

## Итог

Задачи LR-BE-1201 — LR-BE-1209 реализованы в рабочем серверном контуре.
PostgreSQL является источником истины, маршруты подключены к `cmd/api`, а Radar
показывает подтверждённую возвращённую выручку без эвристики и без AI.

```text
NO_RESPONSE
  → MARK_CONTACTED
  → BOOKED
  → PAID 47 000 RUB
  → RECOVERED 47 000 RUB
```

## Соответствие задачам

| Задача | Реализация |
|---|---|
| LR-BE-1201 | `revenue_events` хранит точную положительную сумму, валюту, состояние, источник, автора и время. |
| LR-BE-1202 | `POST /api/v1/opportunities/{opportunityId}/revenue` требует `revenue.confirm` и `Idempotency-Key`. |
| LR-BE-1203 | `revenue_attributions` хранит `RECOVERED`, `ORGANIC` или `UNKNOWN` отдельным неизменяемым фактом. |
| LR-BE-1204 | Составные внешние ключи и повторное чтение фактов обеспечивают совпадение организации и Opportunity. |
| LR-BE-1205 | Новая цепочка ограничена единым окном 30 дней; точный поздний повтор возвращает сохранённый ответ. |
| LR-BE-1206 | `UNIQUE (tenant_id, revenue_event_id)` допускает одну атрибуцию события. |
| LR-BE-1207 | `GET /api/v1/revenue/confirmed-recovered?currency=...` считает только формальный возврат и не смешивает валюты. |
| LR-BE-1208 | Событие, атрибуция, ключ и `REVENUE_CONFIRMED` записываются одной транзакцией. |
| LR-BE-1209 | Сквозной HTTP/PostgreSQL-тест доказывает обязательную цепочку и сумму 47 000 RUB. |

## Схема хранения

Миграция `000012_revenue_attribution.sql` добавляет две неизменяемые таблицы:

```text
revenue_events
  1 ─── 1 revenue_attributions
              │
              ├── Risk
              ├── Action
              └── Outcome
```

Для `RECOVERED` все три ссылки обязательны. Для `ORGANIC` и `UNKNOWN` все три
ссылки должны отсутствовать. RevenueEvent и RevenueAttribution связаны с
Opportunity составными внешними ключами, включающими `tenant_id`. Триггер базы
повторно защищает совпадение Opportunity, порядок времени и 30-дневное окно.
Прямые `UPDATE` и `DELETE` обеих таблиц запрещены.

## Денежная точность

В API суммы представлены строками, а в PostgreSQL — `NUMERIC(14,2)`. Код не
использует двоичную плавающую точку. Подтверждение принимает не более 12 цифр
до точки и не более двух после неё, требует сумму больше нуля и нормализует
валюту к трём заглавным латинским буквам.

Показатель считается запросом к авторитетным таблицам:

```text
RevenueEvent.status = CONFIRMED
  AND RevenueAttribution.type = RECOVERED
  AND currency = запрошенная валюта
```

Органическая, неизвестная и предположительно связанная выручка не попадает в
сумму.

## Идемпотентность и атомарность

Для новой команды одна транзакция выполняет:

```text
зарезервировать Idempotency-Key
  → проверить Risk, Action, Outcome и окно
  → записать RevenueEvent
  → записать единственную RevenueAttribution
  → записать REVENUE_CONFIRMED в audit_log
  → COMMIT
```

Точный повтор возвращает прежний ответ с кодом `200`. Проверка ключа происходит
раньше повторной проверки временного окна, поэтому сохранённый запрос остаётся
идемпотентным и через 30 дней. Изменённое содержимое получает `409`. Ошибка
любого шага откатывает также ключ идемпотентности.

## Проекция Radar

Карточка Risk после подтверждения содержит валюту, потенциальную сумму и
формальную возвращённую сумму Opportunity. Сводка Radar считает возвращённую
выручку для подходящих активных Risk только в основной валюте организации.
Отдельный маршрут показателя возвращает общий формальный итог по явно
запрошенной валюте.

## Проверки

Автоматические проверки охватывают:

- точность и границы денежных значений;
- обязательную и запрещённую цепочку атрибуции;
- разрешения, строгий разбор JSON и безопасные ответы HTTP;
- точный повтор, изменённый повтор и повтор после истечения окна;
- другую организацию, другую Opportunity, будущие и просроченные факты;
- раздельный подсчёт валют и исключение `ORGANIC`;
- 20 одновременных подтверждений с одним ключом;
- откат события, атрибуции и ключа при ошибке аудита;
- ограничение одной атрибуции и запрет удаления на уровне PostgreSQL;
- полный путь от входящего сообщения до `RECOVERED 47 000` и перечитывания
  Radar.

Успешно выполнены:

```text
make test-db GO_TEST_FLAGS='-count=1'
make test-db GO_TEST_FLAGS='-race -count=1'
go vet ./...
go run honnef.co/go/tools/cmd/staticcheck@v0.6.1 ./...
go run ./backend/tools/archcheck -root backend
make build
npx --yes @redocly/cli@1.34.5 lint contracts/openapi/openapi.yaml
```

Локально пересобраны только `migrate` и `api`, без перезапуска Telegram-worker.
`GET /health/ready` возвращает `status: ready` и последнюю миграцию
`000012_revenue_attribution`.

## Граница этапа

Этап 12 не переподключает Telegram и не запускает настоящий локальный
AI-сервер. Они не участвуют в доказательстве выручки. По согласованному порядку
следом можно безопасно переподключить `LidRadarDevBot`, затем перейти к этапу 13
и подготовить локальный узел AI для последующих живых сценариев.
