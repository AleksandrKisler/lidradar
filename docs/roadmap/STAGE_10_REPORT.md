# Отчёт этапа 10 — уведомления Telegram

Дата проверки: 2026-08-26.

## Итог

Задачи LR-BE-1001 — LR-BE-1010 реализованы в рабочем серверном контуре. Код
использует PostgreSQL, подключён к `cmd/api` и `cmd/worker`, а локальная рабочая
база обновлена до `000010_notification_delivery`.

Живой выходной критерий остаётся частичным только в той части, для которой
нужен внешний пользователь: второй контролируемый Telegram-аккаунт ранее решено
не заводить, поэтому настоящий путь «клиент написал → бизнес ответил» не
подменяется синтетическим утверждением. Настоящий `sendMessage` самого бота был
подтверждён на этапе проверки применимости.

## Рабочий поток

```text
входящий webhook
  → RawEvent и исходящий журнал
  → каноническое Message
  → Opportunity
  → проверка NO_RESPONSE
  → Risk и risk.opened.v1 в одной транзакции
  → один Notification
  → NotificationDelivery PENDING
  → аренда worker
  → Telegram Bot API
  → SUCCEEDED либо отдельная следующая попытка
```

Radar и Notification читают один и тот же долговечный Risk, но Telegram не
владеет его состоянием. Поэтому внешний отказ не может подтвердить, закрыть или
удалить риск.

## Соответствие задачам

| Задача | Реализация |
|---|---|
| LR-BE-1001 | `notifications` хранит логический пользовательский факт. |
| LR-BE-1002 | `notification_deliveries` хранит отдельную попытку, снимок адресата и аренду. |
| LR-BE-1003 | `telegram_user_links` связывает организацию, Membership, Telegram user и личный chat. |
| LR-BE-1004 | API выпускает 256-битный одноразовый код на 15 минут; хранится только SHA-256. |
| LR-BE-1005 | `TelegramTransport` вызывает `sendMessage` и `answerCallbackQuery`. |
| LR-BE-1006 | Risk пишет `risk.opened.v1`; обработчик исходящего журнала создаёт намерение до внешнего вызова. |
| LR-BE-1007 | Повторы: 5 секунд, 30 секунд, 2 минуты, 10 минут; предел — пять попыток. |
| LR-BE-1008 | Уникальный ключ `risk:{risk_id}:opened` ограничен организацией. |
| LR-BE-1009 | Разрешены только `OPEN_RISK`, `ACKNOWLEDGE`, `SNOOZE`; Telegram callback ID идемпотентен. |
| LR-BE-1010 | Проверен отказ Telegram с сохранением одного Notification и Risk в `OPEN`. |

## Привязка Telegram

Действующие маршруты:

```text
POST   /api/v1/notifications/telegram-link-token
GET    /api/v1/notifications/telegram-link
DELETE /api/v1/notifications/telegram-link
```

Все маршруты требуют серверный сеанс и явный `X-Tenant-ID`. В ответе выпуска
возвращаются только `startUrl` и `expiresAt`. Telegram ID и chat ID в API не
раскрываются.

Команда `/start <код>` обрабатывается внутри уже существующего проверяемого
webhook Connector Core. Код принимается только из личного чата, только один раз
и только по пути организации, которой он принадлежит. Новый webhook для того же
бота не создаётся.

## Доставка и отказоустойчивость

- Notification и первая Delivery создаются одной транзакцией.
- Два worker не получают одну действующую аренду благодаря
  `FOR UPDATE SKIP LOCKED`.
- Адресат, заголовок и текст сохраняются снимком; изменение привязки не меняет
  уже созданную попытку.
- Ошибки 429, 5xx и сети считаются временными; прочие 4xx — постоянными.
- Повтор создаёт новую Delivery, но не новый Notification.
- Потерянная последняя аренда переводится в `DEAD`, чтобы запись не зависла в
  `PROCESSING` навсегда.
- Без `LIDAR_TELEGRAM_TOKEN` рабочий worker не отмечает заглушку как успех:
  Delivery остаётся `PENDING` до запуска с настроенным транспортом.
- Раз в минуту worker журналирует только безопасные количества `PENDING`,
  `PROCESSING`, `RETRY`, `DEAD`, просроченных аренд и готовых к отправке записей.

## Безопасные кнопки

- `OPEN_RISK` фиксирует навигационное намерение без изменения денег или Risk.
- `ACKNOWLEDGE` вызывает принадлежащую Risk идемпотентную команду и проверку
  `risks.manage`.
- `SNOOZE` помечает только текущее уведомление временем откладывания.

Перед выполнением проверяются организация, активный Membership, активная
Telegram-привязка, Telegram user/chat, Notification и Risk. Неизвестные и
денежные команды отбрасываются. Расписание тишины, сводки и длительность
откладывания принадлежат этапу 20 и на этапе 10 не имитируются.

Проверки охватывают повтор миграций, гонку создания Risk и `risk.opened.v1`,

tenant-изоляцию кода, отключение привязки, три кнопки, запрет неизвестной
команды, API-аутентификацию и полный автоматический поток от webhook до
доставки-заглушки.

## Оставшийся живой шаг

Существующее подключение бота было зарегистрировано до добавления служебных
видов обновлений. OWNER должен один раз явно отключить и снова подключить его,
после чего:

1. Выпустить `startUrl` через новый API.
2. Открыть ссылку тем же Telegram-аккаунтом — второй аккаунт не нужен.
3. Убедиться, что `GET .../telegram-link` возвращает `linked: true`.
4. При доступном контролируемом входящем сообщении подтвердить настоящий
   `NO_RESPONSE → Risk → Telegram alert` и обновить матрицу проверки.

Этот ручной шаг меняет внешний webhook и поэтому не выполняется сервером
скрытно или автоматически.
