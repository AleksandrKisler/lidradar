# Отчёт части 13B — натурная проверка домашнего AI-узла

Дата проверки: 1 сентября 2026 года.

## Итог

Выходной критерий этапа 13 пройден на физическом Ubuntu-сервере с RTX 4060.
Cloud Core работал на машине разработчика, а AI-узел обращался к нему по
локальной Wi‑Fi-сети. Проводное соединение в испытании не использовалось.

```text
Cloud Core + PostgreSQL на машине разработчика
        ↑ исходящие подписанные запросы по Wi‑Fi
Go AI Agent на Ubuntu
        ↓ закрытая сеть Docker
llama.cpp → Qwen3-4B-Q4_K_M → RTX 4060
```

Физический узел остаётся заменяемым вычислительным ресурсом. Источником истины
является PostgreSQL Cloud Core.

## Испытательный стенд

- Ubuntu 26.04.1 LTS, ядро `7.0.0-30-generic`;
- NVIDIA GeForce RTX 4060, 8 ГБ;
- драйвер NVIDIA `595.71.05`, CUDA `13.2`;
- NVIDIA Container Toolkit `1.20.0`;
- Docker Engine `29.7.2`, Docker Compose `5.5.0`;
- модель `Qwen3-4B-Q4_K_M.gguf`, размер `2 497 280 640` байт;
- версия модели в протоколе: `local-4b-8b-q4`;
- узел зарегистрирован как `AI-NODE-01`.

Реквизиты узла находятся в `/srv/lidradar/config/ai-node.json`, принадлежат
`root:root`, имеют режим `0600` и подключаются в контейнер только для чтения.
Содержимое файла и секрет в ходе проверки не выводились.

## Развёртывание

Отдельный `docker-compose.ai.yml` запускает:

- `llama-server` только во внутренней сети без опубликованного порта;
- `ai-agent` с отдельной исходящей сетью;
- файловую систему контейнеров только для чтения;
- удаление всех Linux capabilities;
- `no-new-privileges`;
- автоматический перезапуск `unless-stopped`;
- запуск агента только после успешной проверки `/health` модели.

Модель не доступна с машины разработчика напрямую: порт `8080` AI-узла не
публикуется. Снаружи узла доступен только SSH, ограниченный правилами UFW.

## Реальный анализ

Синтетический запрос без Telegram- и клиентских данных прошёл полный путь:

```text
PENDING
→ claim
→ RUNNING
→ llama.cpp/Qwen3
→ строгая проверка результата
→ SUCCEEDED/APPLIED
→ ConversationSummary в PostgreSQL
```

Результат первой физической попытки:

- задание `a3e02bad-90a1-4d80-b5e4-f76b7c62cd72`;
- одна попытка;
- итог `SUCCEEDED/APPLIED`;
- 255 входных и 370 выходных токенов;
- генерация около 4,71 секунды;
- скорость около 78,34 токена в секунду.

Журналы агента содержали только запуск и состояние конфигурации. Текст
переписки, ответ модели и реквизиты узла в журнал не попали.

## Перезагрузка Ubuntu

Выполнена настоящая перезагрузка сервера. SSH снова стал доступен примерно
через 18 секунд. После загрузки автоматически восстановились:

```text
Docker
→ llama.cpp healthy
→ AI Agent
→ heartbeat READY
```

Службы Docker, containerd и SSH остались включёнными и активными. Ручной запуск
контейнеров после перезагрузки не потребовался.

## Потеря связи и повторная обработка

Проверка выполнена управляемым отключением исходящей сети контейнера агента во
время обработки. Это имитация потери Wi‑Fi-связи AI-узла, а не физическое
выдёргивание сетевого кабеля.

- задание `7f812725-e984-439e-ab78-42307fd4b459`;
- первая попытка осталась `RUNNING` до истечения 120-секундной аренды;
- Cloud Core продолжал отвечать `ready`;
- после восстановления сети задание было повторно захвачено;
- первая попытка закрылась как `FAILED/REJECTED/LEASE_EXPIRED`;
- вторая попытка завершилась `SUCCEEDED/APPLIED`;
- узел вернулся в `READY` с одним свободным местом.

Прежний владелец аренды не смог применить поздний результат. Основной API,
правило `NO_RESPONSE` и денежный контур не зависели от доступности модели.

## Ограничения испытательного контура

- Cloud Core временно работал по HTTP внутри доверенной Wi‑Fi-сети и в режиме
  `development`. Для постоянной эксплуатации нужен устойчивый HTTPS-адрес.
- Проверка доказывает работоспособность инфраструктуры, но не фиксирует качество
  модели. Для этого этап 15 требует размеченный набор 300–500 случаев и
  утверждённые пороги качества и производительности.
- Использовались только синтетические организации и сообщения.
