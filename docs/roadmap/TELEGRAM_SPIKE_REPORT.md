# Отчёт проверки Telegram Connected Business Bot

Статус: **в работе**. Автоматизированная часть коннектора и производственный
контур уведомлений этапа 10 реализованы, настоящий bot webhook подключён и
первое живое событие принято. Полный путь сообщений, повтор, варианты файлов,
переподключение и `/start` ещё проверяются. Этот
документ нельзя переводить в состояние «пройдено» только по результатам
файлов-примеров или поддельного HTTP-клиента.

## Условия проверки

- бот разработки создан через BotFather и для него включён Business Mode;
- российский Telegram-аккаунт без Premium подключён к боту;
- API LidRadar доступен Telegram по постоянному или испытательному HTTPS-адресу;
- токен бота передан только через запрос подключения и не записан в репозиторий;
- для клиента, владельца и тестового получателя уведомления используются
  отдельные учётные записи там, где это требуется сценарием.

## Автоматизированная готовность

- `setWebhook`, `getWebhookInfo` и `deleteWebhook` проверяются без обращения в
  интернет через управляемый HTTP-клиент;
- секрет webhook передаётся Telegram как `secret_token`, а входящий заголовок
  проверяется до записи события;
- токен шифруется AES-256-GCM с привязкой к организации и подключению;
- переменная с открытым токеном не передаётся в окружение контейнера API;
- ответы и ошибки не содержат токен;
- обрабатываются `business_connection`, `business_message`,
  `edited_business_message`, `deleted_business_messages`, а единый webhook
  также принимает служебные `message` и `callback_query`;
- повтор `update_id` дедуплицируется ограничением PostgreSQL.
- миграция `000010` хранит логические уведомления, отдельные попытки доставки,
  одноразовые коды, Telegram-привязки и безопасные команды;
- автоматический сквозной тест проходит путь от входящего webhook до
  `NO_RESPONSE`, Radar, одного Notification и успешной доставки-заглушки;
- Bot API transport, отказ Telegram, сетка повторов и неизменность Risk при
  отказе проверены отдельно; эти проверки не выдаются за живой `/start`.

## Живое наблюдение 2026-08-25

В 11:04:38 UTC Telegram доставил настоящий `business_connection` через
публичный HTTPS webhook. API сохранил один `RawEvent`, фоновый обработчик перевёл
его в `PROCESSED`, ошибок нет. HTTP-приём ответил `202` за 15 мс, до фоновой
обработки. Подключение осталось `ACTIVE`, реквизиты в
PostgreSQL представлены 90 байтами шифротекста. Открытые права включают чтение
сообщений и ответы; само событие сообщает `can_reply=true`.

Повторная проверка `getWebhookInfo` подтвердила адрес LidRadar, ноль ожидающих
обновлений и отсутствие последней ошибки доставки. Используемый сейчас быстрый
туннель Cloudflare годится только для испытания и не является рабочим адресом с
гарантированной доступностью.

Обычный Bot API `sendMessage` доставил владельцу синтетическое тестовое
уведомление от `LidRadarDevBot`. Идентификатор чата был взят из живого
`business_connection` и не выводился. Это доказывает внешний путь Telegram, но
подтверждает доступность внешнего пути, но не заменяет живую проверку нового
производственного обработчика этапа 10 после одноразовой привязки.

После реализации этапа 10 локальные контейнеры пересобраны, рабочая база имеет
миграцию `000010_notification_delivery`, API готов. Существующий Telegram
webhook необходимо один раз явно переподключить, чтобы Telegram начал присылать
добавленные виды `message` и `callback_query`; это действие намеренно не
выполняется скрытно от владельца подключения.

Владелец проекта подтвердил отсутствие второго контролируемого Telegram-
аккаунта и решил не использовать для испытания чужие реальные диалоги. Поэтому
LR-BE-TG-004 и LR-BE-TG-005 намеренно оставлены неподтверждёнными.

В отчёте намеренно нет токена, полного идентификатора Business Connection,
Telegram user/chat ID и содержимого пользовательских диалогов. Для сравнения
устойчивости используется только сокращённый отпечаток.

## Итоговое решение

```text
P0 = Connected Business Bot
fallback = Standard Bot
```
