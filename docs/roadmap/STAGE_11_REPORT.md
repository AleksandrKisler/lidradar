# Отчёт этапа 11 — рекомендации, действия и исходы

Дата проверки: 2026-08-26.

## Итог

Задачи LR-BE-1101 — LR-BE-1108 реализованы в рабочем серверном контуре.
PostgreSQL является источником истины, маршруты подключены к `cmd/api`, а Radar
возвращает созданную рекомендацию, упорядоченные действия и последний исход
связанной Opportunity.

```text
Risk
  → POST recommendation
  → POST Action с Idempotency-Key
  → POST Outcome с Idempotency-Key
  → GET Risk с созданными фактами
```

Ни Telegram, ни AI в этом потоке не участвуют. Это сохраняет согласованный
порядок: этап 12 выполняется следующим, а переподключение бота и запуск
локального AI-сервера происходят после него.

## Соответствие задачам

| Задача | Реализация |
|---|---|
| LR-BE-1101 | Домен Recommendation хранит ID организации, Risk, текст, источник и время. |
| LR-BE-1102 | Тип Risk читается сервером; все пять объявленных типов имеют полезный шаблон без AI. |
| LR-BE-1103 | `actions` содержит tenant-aware связь с Risk и Membership; прямые изменение и удаление запрещены. |
| LR-BE-1104 | `POST /api/v1/risks/{riskId}/actions` подключён к рабочему API и требует `risks.manage`. |
| LR-BE-1105 | `outcomes` содержит tenant-aware связь с Opportunity и Membership; исправление создаётся новой записью. |
| LR-BE-1106 | `POST /api/v1/opportunities/{opportunityId}/outcomes` подключён к рабочему API. |
| LR-BE-1107 | `idempotency_keys` ограничен `(tenant_id, key, operation)`, хранит SHA-256 запроса и ответ. |
| LR-BE-1108 | `audit_log` записывается атомарно с новым Action или Outcome и защищён от изменения. |

## Схема хранения

Миграция `000011_corrective_facts.sql` добавляет:

- `recommendations` — один шаблон на Risk и источник;
- `actions` — неизменяемый журнал действий по Risk;
- `outcomes` — неизменяемый журнал исходов по Opportunity;
- `idempotency_keys` — сохранённые результаты критических команд;
- `audit_log` — неизменяемый журнал критических операций.

Критические связи используют составные внешние ключи с `tenant_id`. Знание UUID
чужой организации не позволяет прочитать Risk или Opportunity и создать рядом
с ними корректирующий факт.

## Транзакционные гарантии

Для нового Action одна транзакция выполняет четыре действия:

```text
зарезервировать ключ идемпотентности
  → вставить Action
  → перевести активный Risk в ACTED
  → добавить ACTION_RECORDED в audit_log
  → COMMIT
```

Для Outcome той же транзакцией записываются ключ, сам Outcome и
`OUTCOME_RECORDED`. Если любой шаг завершается ошибкой, не остаётся ни факта,
ни ключа, ни неполной записи аудита. Точный повтор возвращает прежний ответ с
кодом `200`; изменённый запрос с тем же ключом получает `409`.

## Поведение Radar

`GET /api/v1/risks` и `GET /api/v1/risks/{riskId}` дополняют базовую проекцию:

- одной созданной Recommendation;
- всеми Actions в порядке времени и ID;
- последним Outcome связанной Opportunity.

Списковая загрузка выполняется пакетными запросами, а не отдельным запросом на
каждый Risk. Revenue до этапа 12 по-прежнему не выдумывается.

## Проверки

Автоматические проверки охватывают:

- повторное применение миграций;
- полный API-путь от настоящего канонического сообщения до Risk, Recommendation,
  Action, Outcome и повторного чтения Radar;
- точный повтор и конфликт `Idempotency-Key`;
- 20 конкурентных одинаковых команд, создающих один Action и одну запись аудита;
- откат Action и ключа при намеренной ошибке записи аудита;
- запрет `DELETE` для Action, ключа и аудита на уровне PostgreSQL;
- append-only исправление Outcome;
- разрешение `risks.manage` и межорганизационную изоляцию;
- отклонение неизвестных полей и нескольких JSON-объектов в одном запросе.

Успешно выполнены:

```text
make test-db
GO_TEST_FLAGS='-race -count=1' make test-db
go vet ./...
go run ./backend/tools/archcheck -root backend
make build
npx --yes @redocly/cli@1.34.5 lint contracts/openapi/openapi.yaml
```

Локальные контейнеры пересобраны и запущены. `GET /health/ready` возвращает
`status: ready` и последнюю миграцию `000011_corrective_facts`.

## Граница этапа

Этап 11 не подтверждает выручку и не строит атрибуцию — это задачи этапа 12.
Он также не меняет Telegram webhook и не запускает AI. После этапа 12 можно
переподключить `LidRadarDevBot`, поднять локальный AI-сервер и выполнить живые
Telegram-сценарии в согласованном порядке.
