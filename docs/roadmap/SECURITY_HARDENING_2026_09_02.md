# Усиление защиты после этапа 16

Дата проверки: 2 сентября 2026 года.

## Закрытые замечания

### Ограничение частоты и защита от перебора

Публичные операции аутентификации теперь расходуют атомарные окна в PostgreSQL:

| Операция | Субъект | Граница |
|---|---|---|
| регистрация | сетевой адрес | 5 запросов в час |
| вход | сетевой адрес | 20 запросов в минуту |
| вход | нормализованная учётная запись | 5 попыток за 15 минут |
| обновление сеанса | сетевой адрес | 60 запросов в минуту |

Ограничение учётной записи действует сразу для всех адресов и экземпляров API,
что закрывает распределённый перебор одного пароля. Адресная граница сдерживает
перебор случайных имён и дорогие вычисления Argon2id. Успешный вход сбрасывает
только счётчик учётной записи. Ответ 429 содержит `RATE_LIMITED` и
`Retry-After`, но не сообщает, существует ли пользователь.

В `auth_rate_limits` сохраняются только SHA-256-отпечатки адреса и учётной
записи. Просроченные записи удаляются ограниченными пачками. Решение не доверяет
заголовкам `X-Forwarded-For`, которые внешний клиент способен подделать; перед
размещением за прокси потребуется явно настроить доверенную сетевую границу.

### Изоляция инструкций AI по организациям

Для узлов создан явный разрешительный список `ai_node_tenants`. Новый узел
регистрируется сразу для конкретной организации. Захват выбирает задание только
при одновременном совпадении:

1. организация задания явно разрешена узлу;
2. версия модели совпадает;
3. узел готов, недавно подтвердил состояние и имеет свободное место;
4. задание доступно либо его прежняя аренда истекла.

Проверка организации находится в SQL до возврата поля `payload`, поэтому чужая
инструкция не покидает PostgreSQL. Дополнительные составные внешние ключи
запрещают пару «узел одной организации — аренда/запуск другой организации» даже
при ошибочном прикладном запросе.

Миграция восстанавливает назначения из уже существующих запусков и активных
аренд. Узел без исторической связи остаётся без доступа. Для него назначение
выполняется явной командой:

```bash
go run ./backend/cmd/ai-node-manage allow-tenant \
  --node-id '<uuid-узла>' \
  --tenant-id '<uuid-организации>'
```

Новые узлы требуют `--tenant-id` при `ai-node-register`. Секрет узла для
назначения не читается и не выводится.

## Проверки

- 40 одновременных обращений к одному счётчику пропускают ровно 5;
- шестая попытка входа возвращает 429 и `Retry-After` даже с верным паролем;
- успешный вход после истечения окна сбрасывает счётчик учётной записи;
- узел организации A не получает задание и текст организации B;
- прямая межорганизационная запись аренды отклоняется PostgreSQL;
- после явного назначения то же задание становится доступно узлу;
- повторное применение миграций остаётся безопасным.

Архитектурные решения зафиксированы в ADR 0032 и ADR 0033. Изменения входят в
миграцию `000015_security_boundaries.sql`.
