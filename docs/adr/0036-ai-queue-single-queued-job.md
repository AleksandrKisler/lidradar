# 0036: Одно ожидающее AI-задание на переписку и дебаунс анализа

- Status: Accepted
- Date: 2026-09-02
- Baseline: Tasks.md v1.1, ЭТАП R (LR-BE-RM-006, LR-BE-RM-016); дополняет ADR 0031

## Контекст

Freshness guard (ADR 0031) переводит результат в `STALE` на каждое новое
сообщение и планирует новое задание. Без дедупликации активный диалог
порождал задание на каждое сообщение: при `max_inflight = 1` и одной
RTX 4060 четыре из пяти inference уходили впустую.

Скользящая аренда (§3.5) продлевается heartbeat, поэтому зависший inference с
живой heartbeat-горутиной удерживал задание бесконечно.

## Решение

1. Частичный уникальный индекс `ai_jobs_one_queued_per_entity_idx` на
   `(tenant_id, entity_type, entity_id) WHERE status IN ('PENDING', 'RETRY')`.
   Постановка задания идемпотентна: более свежий снимок переписки заменяет
   инструкцию, ревизию и последнее сообщение уже ожидающего задания, сохраняя
   его идентификатор и более ранний `available_at`; более старый снимок ничего
   не меняет.
2. Захваченное (`LEASED`) и выполняющееся (`RUNNING`) задание в индекс **не
   входит** — намеренное отступление от формулировки ТЗ. Узел получает
   инструкцию при захвате, а запуск копирует ревизию и последнее сообщение из
   строки задания при старте. Изменение снимка под захваченным заданием
   позволило бы устаревшему результату пройти проверку свежести как свежему.
   Пока задание выполняется, новое сообщение ставит отдельное ожидающее
   задание; результат выполняющегося становится `STALE` по ADR 0031.
3. Дебаунс `AnalysisDebounce = 60s`: каждое новое ожидающее задание доступно
   для захвата не раньше чем через минуту после постановки; всплеск сообщений
   обновляет снимок этого задания, не сдвигая срок. Повторное планирование
   после `STALE` использует ту же паузу.
4. Абсолютный потолок аренды `LeaseCap = 15m` от `leased_at`, который
   heartbeat не продлевает. Перехват по потолку помечает запуск
   `LEASE_CAP_EXCEEDED`, увеличивает `attempts` и отдаёт задание другому узлу;
   поздний ответ прежнего узла отбрасывается идемпотентно.

## Рассмотренные варианты

Отклонены: индекс на `PENDING/LEASED/RUNNING` с обновлением ревизии
захваченного задания (описано выше — нарушает инвариант свежести);
дебаунс от последнего сообщения (активный диалог откладывал бы анализ
бесконечно); дебаунс только на повторные задания (первое задание всё равно
захватывалось бы внутри всплеска и уходило впустую).

## Последствия

Пять сообщений за двадцать секунд дают одно задание с последней ревизией и
один inference. Первый анализ переписки начинается не раньше чем через
минуту после первого сообщения — заведомо меньше любого порога правил.
Испытания, которым нужен немедленный захват, явно выставляют нулевой дебаунс.

## Перенос и откат

Миграция помечает лишние ожидающие задания `DEAD` с кодом
`SUPERSEDED_BY_NEWER_SNAPSHOT`, оставляя по одному на переписку с наибольшей
ревизией, и заполняет `leased_at` для действующих аренд. Откат — удаление
индекса и столбца без потери результатов.
