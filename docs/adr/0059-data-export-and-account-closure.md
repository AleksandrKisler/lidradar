# 0059: Выгрузка данных и закрытие учётной записи

- Status: Accepted
- Date: 2026-10-14
- Approval: владелец проекта 2026-10-13 запросил функции («выгрузка и удаление данных он тоже нам нужен»), 2026-10-14 дал команду «начинай ADR 0059». Конкретные значения — льготный срок 30 суток (он уже записан в ADR 0056, строка 19), пароль как подтверждение, блокировка единственного владельца, состав и форматы выгрузок, право на выгрузку организации только у владельца, операторская команда стирания — рекомендации автора; подтвердить при коммите. Порядок приёма обращений на стирание, подтверждение личности и юридическая рамка остаются за владельцем и юристом (ADR 0056, п. 7 таблицы решений) и этим ADR не решаются.
- Связь: [ADR 0056](0056-data-retention-and-erasure.md) (строка 19 матрицы: «обезличить»; механизмы 5–7; «за пределами»: выгрузка и закрытие как пользовательские функции — это решение), [ADR 0058](0058-account-security-and-mail.md) (почта, токены, пределы, аудит в той же транзакции), [ADR 0057](0057-invitation-only-registration.md) (контракт модулей через узкий интерфейс, права на организации), [ADR 0045](0045-team-onboarding-and-secure-connect.md) (команда, защита последнего владельца), [ADR 0020](0020-opaque-session-auth.md) (сессии), [ADR 0034](0034-rls-roles-fail-closed.md), [ADR 0041](0041-rls-enforcement-and-hardening.md), [ADR 0052](0052-database-roles-owner-and-runtime.md) (роли, RLS, платформенный пул), [ADR 0039](0039-basic-analytics-raw-facts.md) и [ADR 0040](0040-platform-admin-observability.md) (прецеденты чтения чужих таблиц), [ADR 0049](0049-trusted-proxies-client-address.md) (адрес клиента).
- Scope: самообслуживание пользователя (выгрузка личных данных, закрытие учётной записи с отсрочкой), исполнитель обезличивания, выгрузка данных организации её владельцем, операторская команда немедленного обезличивания пользователя, реестр данных и проверки схемы, контракт API и интерфейс. Не решает закрытие организации (ADR 0056, механизм 5), стирание по запросу конечного клиента организации (механизм 6), юридическое основание и порядок приёма обращений, смену адреса почты, восстановление закрытой учётной записи.

## Контекст

Проверено по коду и схеме 2026-10-14:

- Ни выгрузки, ни закрытия нет. Строку пользователя нельзя удалить: `memberships` защищена триггером `memberships_no_delete`; на `users` и на членства ссылаются неизменяемые таблицы (`auth_audit_log`, `admin_audit_log`, `platform_admins`, `platform_invitations`, а через членства — `actions`, `outcomes`, `audit_log`, `revenue_events`, `risk_feedback`, `ml_consents`, `opportunity_stage_history`, `membership_invitations`). ADR 0056 (строка 19) уже решил форму: обезличить на месте — адрес по идентификатору, имя «Удалён», пароль непригоден для входа, связи и привязку Telegram удалить, срок 30 суток.
- На пользователя указывают 21 таблица по внешним ключам (`sessions`, `account_tokens`, `memberships`, `notifications`, `notification_preferences`, `notification_digest_items`, `telegram_user_links`, `telegram_link_tokens`, `telegram_callback_commands`, `actions`, `outcomes`, `audit_log`, `revenue_events`, `risk_feedback`, `ml_consents`, `opportunity_stage_history`, `membership_invitations`, `platform_admins`, `platform_invitations`, `admin_audit_log`, `auth_audit_log`) и ещё четыре хранят идентификатор администратора без ключа (`discarded_by` у `ai_jobs`, `jobs`, `notification_deliveries`, `outbox_events`). Таблиц с `tenant_id` 39: 23 несут содержимое и факты организации, остальные — очереди и служебное состояние, личное каждого пользователя и журнал оператора. Все три рабочие роли имеют полный DML на все таблицы (миграция 000020), поэтому полнота выгрузки и обезличивания держится на самом коде, а не на правах доступа.
- Секреты лежат в тех же таблицах, что и выгружаемые факты: `channel_connections.encrypted_credentials` и `verification_secret_hash`, `membership_invitations.code_hash`, `sessions.token_hash`, `account_tokens.token_hash`, `telegram_link_tokens.token_hash`, `users.password_hash`. Выгрузка «всех колонок» их бы унесла.
- Проверка пароля отвечает ошибкой на пустой или повреждённый хэш (`platform/crypto`, `ErrInvalidPasswordHash`): «пустой хэш» из матрицы ADR 0056 дал бы `500` при попытке входа под обезличенным адресом.
- Сервер ограничивает запись 30 секундами от начала запроса (`platform/http/server.go`). Поток событий уже обходит это продлением срока записи через `http.NewResponseController` (`risk/transport/sse.go`), обёртка журнала запросов (chi) эту возможность пропускает. Файлового хранилища нет (`platform/objectstorage` пуст), поэтому выгрузка может быть только потоковой.
- API и worker уже держат платформенный пул (ADR 0034, 0041): администрирование и AI-узлы читают через него все организации. Явный список платформенных запросов ведёт ADR 0041, п. 4.
- Роли по ADR 0056, п. 1 таблицы решений (рабочее допущение): для учётных записей, журналов безопасности и копий LidRadar — самостоятельный оператор; для переписок конечных клиентов — обработчик по поручению организации.

## Решение

1. **Модуль `lifecycle`** (`backend/internal/lifecycle`: `domain`, `application`, `infrastructure`, `transport`) владеет реестром данных (какие таблицы и колонки относятся к пользователю и к организации и что с ними происходит), выгрузками и исполнителем обезличивания. Таблиц у него нет: он читает и пишет таблицы других модулей по реестру, запись добавлена в карту (раздел 20 [03-modules.md](../backend/03-modules.md)) (основание — этот ADR, прецеденты ADR 0039 и 0040). Модуль `identity` владеет командами пользователя (запрос, отмена, выгрузка личных данных, подтверждение паролем) и узким контрактом `AccountData`, который реализует `lifecycle`; так же устроена связка `identity` ↔ `tenant` в ADR 0057 (`MemberInvitations`).
2. **Реестр данных — код, а не договорённость.** В `lifecycle/domain` лежат три таблицы: (а) карта ссылок на пользователя — для каждой колонки, указывающей на `users` или на членство, действие при обезличивании (`ERASE` — строки удаляются, `ANONYMIZE` — строка остаётся, личные поля заменяются, `REVOKE` — строка остаётся, доступ закрывается отметкой, `RETAIN` — остаётся идентификатор без личных данных) и место в личной выгрузке; (б) наборы выгрузки организации — таблица, файл, явный список колонок и порядок строк; (в) исключённые таблицы и колонки с причиной. Тест на живой схеме падает, если появилась колонка, указывающая на `users` или на членство, таблица с `tenant_id` или колонка выгружаемой таблицы, которых нет в реестре: новая таблица не может молча остаться вне выгрузки и обезличивания. Явный список колонок (а не «всё, кроме секретов») означает, что новая колонка по умолчанию не выгружается.
3. **Личная выгрузка.** `POST /api/v1/auth/account/export` `{password}` под сессией возвращает один JSON-файл (`Content-Disposition: attachment`, `Cache-Control: no-store`, формат `lidradar.account-export/1`): учётная запись (адрес, имя, статус, даты, признак отложенного удаления), членства (название организации, роль, статус, даты), сессии (даты, IP, user agent; без хэшей), события входа и безопасности (операция, IP, время), настройки уведомлений по организациям, привязки Telegram (идентификатор Telegram и чата), решения по согласию на наборы данных, принятые этим пользователем, и **число** внесённых им записей по организациям (действия, исходы, вердикты, подтверждения выручки, изменения стадий, приглашения, события аудита). Хэш пароля, хэши токенов, очереди и чужие данные не входят. Содержимое самих записей (заметки, вердикты, сделки) принадлежит организации и выгружается её владельцем (п. 6). Каждый список ограничен 50 000 строк, при превышении выгрузка помечает раздел `truncated: true`. Читается в одной транзакции `REPEATABLE READ` только по чтению. Пароль подтверждается тем же пределом `PASSWORD_CHANGE_ACCOUNT`, что и смена пароля (общий счётчик: подбор текущего пароля краденой сессией не получает лишних попыток), и отдельным пределом `ACCOUNT_EXPORT_ACCOUNT` (3 в час). Запись аудита `ACCOUNT_DATA_EXPORTED` делается до выдачи тела: выгрузки без следа не бывает.
4. **Закрытие учётной записи с отсрочкой.**
   - `POST /api/v1/auth/account/deletion` `{password}` под сессией назначает обезличивание через **30 суток** (константа политики `retention-v1`, строка 19 ADR 0056; от окружения не зависит). Ответ `200 {"deletionDueAt": …}`. Повтор при уже назначенном удалении возвращает прежний срок, не двигает его и не шлёт письма.
   - До срока учётная запись работает как обычно: вход, организации, уведомления. `GET /auth/me` отдаёт `user.deletionDueAt`; интерфейс показывает постоянное напоминание с кнопкой отмены. `DELETE /api/v1/auth/account/deletion` (`204`, идемпотентно) снимает назначение.
   - **Блокировки.** Запрос отклоняется `409 ACCOUNT_DELETION_BLOCKED` с причинами в `details.blockers`, если пользователь — единственный активный владелец (`OWNER`) организации в статусе `ACTIVE` или `SUSPENDED` (`SOLE_OWNER`, с названием организации и признаком `hasOtherMembers`: можно передать владение или нужно закрывать организацию) или действующий платформенный администратор (`PLATFORM_ADMIN`). Организацию автоматически не закрывают и владение не передают: это решение человека (закрытие организации — операторская процедура ADR 0056, механизм 5, вне этого ADR). Блокировки перепроверяются при исполнении.
   - Запрос, отмена и отклонённое исполнение пишут `auth_audit_log` (`ACCOUNT_DELETION_REQUESTED`, `ACCOUNT_DELETION_CANCELLED`, `ACCOUNT_DELETION_BLOCKED`) **в той же транзакции**, что и изменение. Пределы: пароль — общий `PASSWORD_CHANGE_ACCOUNT`; частота запросов и отмен — `ACCOUNT_DELETION_ACCOUNT` (5 в час на пользователя), потому что каждое действие отправляет письмо.
   - Письма (модуль `mail`, ADR 0058; обычный текст, без персональных данных в теме): при запросе (дата обезличивания, как отменить, что делать, если запрос не ваш), при отмене пользователем, при отмене системой из-за появившейся блокировки и после обезличивания (на прежний адрес). Сбой постановки письма не отменяет действие; без настроенной почты запрос работает без писем.
5. **Исполнитель обезличивания.** Отдельная цепочка `worker` (раз в минуту, пачка до 20 пользователей; не задерживает другие очереди, как цепочка писем в ADR 0058) под платформенным пулом. Для каждого пользователя с `deletion_due_at <= now()` и без `deleted_at` — одна транзакция с `SET LOCAL lock_timeout = '5s'`:
   1. блокировка строки пользователя (`FOR UPDATE SKIP LOCKED`: два воркера не берут одного);
   2. блокировка неиспользованных приглашений, выданных пользователем, затем всех членств каждой организации, где у пользователя есть членство (по возрастанию `tenant_id`, затем `id` — тот же порядок, что у `lockMemberships` модуля `tenant`: роли в этих организациях не меняются, пока идёт проверка и отзыв доступа), и перепроверка блокировок. Приём приглашения берёт строку принимающего, затем приглашение, затем его членство; порядок «приглашение раньше членства» общий, поэтому взаимного ожидания нет. При блокировке: назначение снимается, пишется `ACCOUNT_DELETION_BLOCKED`, после фиксации уходит письмо; учётная запись остаётся действующей;
   3. удаляются `telegram_callback_commands`, `telegram_link_tokens`, `telegram_user_links`, `notification_digest_items`, `notification_preferences`, `notifications` (доставки уходят каскадом), `sessions`, `account_tokens`; неиспользованные приглашения, созданные пользователем, отзываются; все его членства переводятся в `DISABLED` с `revoked_at`;
   4. `users`: адрес `<id>@deleted.invalid` (зарезервированная зона `.invalid`, RFC 2606: письмо не уйдёт и вход не подберут), имя «Удалён», пароль — хэш случайного секрета, который нигде не сохраняется (пустая строка заставила бы проверку пароля падать, см. Контекст), `status = DISABLED`, `email_verified_at` и `organization_rights` обнуляются, `deleted_at` ставится;
   5. запись `ACCOUNT_ANONYMIZED` в `auth_audit_log` в той же транзакции.
   После фиксации — письмо на прежний адрес и событие журнала `account.deletion.anonymized` (идентификатор пользователя и режим, без адреса). Повтор безопасен: после `deleted_at` пользователь исполнителю не попадается. **Гонки с входом и приглашениями.** Создание сессии, создание членства и приём приглашения (в том числе восстановление отозванного членства) берут строку пользователя `FOR SHARE` и действуют только для пользователя со статусом `ACTIVE`: начатые одновременно с обезличиванием, они ждут его конца и получают отказ (сессия и членство не создаются, отозванное членство остаётся отозванным), а исполнитель, застав приём в работе, пропускает пользователя (`SKIP LOCKED`) до следующего прохода. Записи, на которые ссылаются неизменяемые таблицы (действия, исходы, вердикты, выручка, аудит организации и входов, стадии, согласия), остаются: личного в них, кроме идентификатора, нет, а идентификатор после обезличивания не ведёт к человеку. Освобождённый адрес можно зарегистрировать заново.
6. **Выгрузка данных организации.** `POST /api/v1/organization/export` под сессией и `X-Tenant-ID` отдаёт ZIP (`application/zip`, вложение). Право — новое `organization.export`, **только у владельца**: в выгрузке переписки, контакты, деньги и команда всей организации. Внутри: `README.txt` (состав и формат, что не выгружается и почему), `organization.json`, файлы JSON Lines в `data/` по наборам реестра (команда, приглашения без кодов, точки и часы работы, услуги, каналы без реквизитов доступа, контакты и внешние идентификаторы, разговоры, сообщения, метаданные вложений, сводки, сделки и история стадий, риски, рекомендации, вердикты, действия, исходы, выручка и атрибуция, согласия ML, аудит организации) и `manifest.json` **последним** (число строк, размер и SHA-256 каждого файла, момент снимка): архив без манифеста считается оборванным. Не выгружаются секреты и реквизиты доступа, очереди и служебные таблицы AI и доставки, сырой буфер приёма вебхуков, ключи объектного хранилища, личные данные каждого участника (уведомления, настройки, привязки Telegram — они в личной выгрузке), журнал оператора. Мера читаемости: идентификатор организации в файлах не повторяется.
   - Все наборы читаются в одной транзакции `REPEATABLE READ` только по чтению под ролью приложения в контексте организации (RLS остаётся страховкой к условию `tenant_id`); строки отдаются потоком (`to_json` из явного списка колонок: порядок полей задан реестром, в отличие от `jsonb`; постоянная память), сжатие Deflate. Срок записи продлевается на каждый кусок (как в потоке событий), общий предел выгрузки — 15 минут, отключение клиента отменяет чтение.
   - Предел `ORGANIZATION_EXPORT_TENANT` — 3 в час на организацию, плюс не больше 2 одновременных выгрузок в процессе. Запись `ORGANIZATION_DATA_EXPORTED` в `audit_log` организации делается до первого байта; если записи нет, выгрузки нет.
7. **Операторская команда.** `platform-admin erase-user --email … --note … --confirm-email …` (флаг `--dry-run` показывает блокировки и число затрагиваемых строк по классам) немедленно обезличивает пользователя тем же исполнителем, минуя отсрочку; блокировки соблюдаются. Пишет `ACCOUNT_ANONYMIZED` и `USER_ERASED` в `admin_audit_log` (источник `CLI`, заметка с основанием) в одной транзакции. Это исполнимый путь для «стирания по запросу» сотрудника (ADR 0056, механизм 6), пока канал приёма не определён: до решения юриста запрос принимает владелец проекта письменно, личность подтверждается входом в учётную запись или письмом с адреса учётной записи, порядок записан в [runbook](../runbooks/data-requests.md). Закрытие организации и стирание контакта по-прежнему ждут механизмов ADR 0056.
8. **Контракт и данные.** Миграция `000026_account_lifecycle`: `users.deletion_requested_at`, `deletion_due_at`, `deleted_at` с CHECK (обе даты назначения заданы вместе и `due > requested`; `deleted_at` только у `DISABLED`), индекс по назначенным удалениям и три новых значения `auth_rate_limits.scope` (`ACCOUNT_EXPORT_ACCOUNT`, `ACCOUNT_DELETION_ACCOUNT`, `ORGANIZATION_EXPORT_TENANT`). Новых таблиц и переменных окружения нет. Платформенный пул используется исполнителем, проверкой блокировок и личной выгрузкой, всеми по идентификатору пользователя: список ADR 0041, п. 4, дополнен. OpenAPI получает три ручки раздела аккаунта, ручку выгрузки организации, поле `user.deletionDueAt` и коды `ACCOUNT_DELETION_BLOCKED`; веб-клиент обновляется в той же поставке.
9. **Члены обезличенных учётных записей в интерфейсе.** Список участников организации отдаёт для обезличенного пользователя пустой адрес и имя «Удалён»; отозванное членство остаётся в списке отозванных. В OpenAPI у `Member.email` поэтому нет `format: email`, а описание называет пустое значение признаком закрытой учётной записи.

## Рассмотренные альтернативы

- **Удалить строку пользователя.** Невозможно без нарушения неизменяемых таблиц и ключей; обезличивание решено ADR 0056.
- **Обезличить сразу, без отсрочки.** Опечатка или чужой сеанс с известным паролем необратимы. Отсрочка 30 суток с письмом и отменой дешёвая и совпадает со сроком ADR 0056.
- **Заблокировать вход на время отсрочки.** Пользователь не смог бы отменить запрос; сеансов бы пришлось отзывать. Принято: учётная запись работает, интерфейс напоминает.
- **Подтверждение закрытия письмом-ссылкой.** Почта подтверждена не у всех (ADR 0058, мягкое подтверждение), и зависимость от неё закрыла бы функцию тем, у кого письма не доходят. Пароль плюс письмо-уведомление и отмена достаточны.
- **Передавать владение или закрывать организацию автоматически при удалении единственного владельца.** Разрушительно и необратимо; решение за человеком, поэтому блокировка с понятной причиной.
- **Каскадно удалять всё, что пользователь внёс в организации.** Ломает факты организации, аналитику и неизменяемый аудит; ADR 0056 стирает содержимое, а не скелет.
- **Асинхронная выгрузка организации в хранилище с ссылкой в письме.** Хранилища файлов нет, а ссылка с данными организации в почте — новая поверхность утечки. Потоковая выгрузка под сессией владельца проще; когда появится объектное хранилище, выгрузку можно перевести на готовый файл без изменения состава.
- **Один JSON-файл на организацию.** Не помещается в память при больших переписках; JSON Lines читается построчно и сохраняет типы лучше CSV.
- **Каждый модуль реализует свой `Export`/`Erase` и оркестратор вызывает их.** Требует передачи транзакции между модулями и по реализации в десяти местах; общий реестр с проверкой схемы проще и надёжнее при том же уровне контроля. Цена — размытое владение таблицами, записанное в карте (раздел 20 [03-modules.md](../backend/03-modules.md)).
- **Выгрузка организации любым участником или менеджером.** Состав включает деньги и контакты всей организации; только владелец.
- **Подтверждение выгрузки организации паролем.** Владелец и так видит те же данные через интерфейс; пароль добавил бы только ещё одну точку подбора. Защита — право, пределы, аудит.
- **Случайный адрес вместо `<id>@deleted.invalid`.** Идентификатор уже есть у всех связанных записей, а зарезервированная зона `.invalid` гарантирует, что адрес не принадлежит реальному ящику.

## Последствия

- **Что остаётся после обезличивания, и это записано как остаточный риск.** IP-адреса прошлых входов в `auth_audit_log` и действия в неизменяемых таблицах: триггер запрета изменения снимается только контролируемыми функциями ADR 0056 (механизм 3), которых ещё нет. До них строки хранят идентификатор без связи с человеком, а IP остаётся до реализации стирания (срок 90 суток по матрице пока не исполняется). Резервные копии хранят данные до 35 суток, журнал стираний, переживающий восстановление (механизм 7), не реализован. До него закрытия по сроку, запрошенные до момента данных копии, воркер повторит сам (назначение лежит в копии), а стирания оператором и запросы, сделанные после копии, при восстановлении повторяют вручную по записям `ACCOUNT_ANONYMIZED` и `USER_ERASED` сохранённой испорченной базы или по журналу обращений ([runbook](../runbooks/data-requests.md)). Письма, уже стоящие в очереди на прежний адрес, уйдут или истекут по своему сроку (не больше 7 суток) и тогда стираются (ADR 0058). Гонка с параллельной выдачей уведомления может оставить служебную строку без личных данных.
- **Юридическое остаётся открытым.** Достаточность личной выгрузки по применимому праву, роль LidRadar для содержимого выгрузки организации, срок ответа и канал для запросов конечных клиентов, подтверждение личности — вопросы юристу (ADR 0056, п. 7). Формулировки политики конфиденциальности и текст письма пишет юрист.
- **Долгая транзакция выгрузки организации.** Чтение по снимку держит соединение пула, пока клиент принимает файл; защита — предел 15 минут, 2 одновременные выгрузки в процессе и предел на организацию. Вакуум не блокируется, писатели не ждут. Нагрузка на данных этапа 25 (500 тыс. сообщений) не измерена.
- **Недоставленная выгрузка.** Ошибка после первого байта не может изменить статус ответа: клиент получит оборванный архив без `manifest.json` и должен повторить; запись аудита фиксирует попытку, а не успех.
- **Единственный владелец не может уйти сам.** Пока нет закрытия организации, владелец одноместной организации обращается к оператору; интерфейс говорит об этом прямо.
- **Совместимость API.** Изменения аддитивны: три ручки раздела аккаунта, одна ручка организации, поле `user.deletionDueAt`, код `ACCOUNT_DELETION_BLOCKED`.
- **Сроки хранения.** Новых сроков нет: сессии и токены удаляются сразу при обезличивании, строка 20 и 23 ADR 0056 исполняются для этого пользователя досрочно.
- **Платформенный пул шире.** Личная выгрузка и проверка блокировок читают несколько организаций одним пулом без страховки RLS: изоляция проверяется тестом с двумя пользователями и организациями, а запросы всегда ограничены идентификатором пользователя.

## Миграция и откат

Миграция `000026_account_lifecycle` аддитивна: три колонки без значения по умолчанию (у существующих пользователей удаление не назначено), CHECK и индекс, расширенный CHECK предела. Откат поведения: остановить цепочку исполнителя (удаления перестанут исполняться, назначенные сроки останутся) и убрать ручки; необратимо только само обезличивание, восстановить его можно лишь из копии (до 35 суток). Откат миграции вручную: удалить три колонки и вернуть прежний CHECK предела.

## Вне этого ADR

Закрытие организации и её каскадное удаление (ADR 0056, механизм 5), стирание контакта конечного клиента по запросу (механизм 6), журнал стираний, переживающий восстановление (механизм 7), контролируемое стирание в таблицах с запретом изменения (механизм 3), смена адреса почты, восстановление закрытой учётной записи, выгрузка наборов для обучения (ADR 0038, H-11), автоматическая выгрузка по расписанию, письма со ссылкой на файл.

## Открыто после принятия

- Канал приёма обращений на стирание, срок ответа и подтверждение личности (владелец и юрист); до решения действует временный порядок из runbook.
- Нужен ли короче льготный срок для пользователей без членств в организациях (в этой поставке один срок для всех).
- Адрес поддержки для владельцев одноместных организаций (в интерфейсе пока нейтральная формулировка).
- Формулировки юриста: письмо о закрытии, политика конфиденциальности, состав личной выгрузки.
