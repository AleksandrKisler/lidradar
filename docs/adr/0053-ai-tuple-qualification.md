# 0053: Квалификация AI tuple: выбор до GOLDEN, пороги, привязка к серверу и оборудованию

- Status: Proposed
- Date: 2026-10-10
- Approval: владелец проекта поручил довести инструкцию v9 до квалификации в текущем обсуждении («идем дальше: AI-промпт v9») и выбрал подъём контекста узла до 8192 (п. 8). Остальное предложено вместе с реализацией и принимается при коммите; пункты 9–10 ждут отдельного решения владельца. Квалификация v9 завершена 2026-10-10 (манифест `FROZEN`); принятие ADR остаётся решением владельца при коммите.
- Scope: порядок, пороги и средства квалификации связки «инструкция, схема генерации, валидаторы, параметры, веса, сервер, наборы, оборудование» (AI tuple); поведение инструкции v9. Контракт `analyze-conversation.v2`, границы модулей, ADR 0047/0048 и правила доверия к фактам не меняются.

## Контекст

На начало работы рабочая инструкция — v9 (`CurrentAnalysisPrompt`), а манифест `lidradar-main-v1`, отчёты и пороги в документах относились к v6 и контракту v1. GOLDEN открывали для v5 и v6; для v7–v9 не открывали ни разу. Пакет v6 собран вручную, и его разбор (`lidradar-main-v1-prompt-v6-provenance-review.json`) перечисляет то, чего не хватает: сборка llama.cpp, версии CUDA и драйвера, происхождение валидатора на момент прогона. Фраза «выбор сделан до открытия GOLDEN» держалась на примечании, а не на проверке.

v9 — не просто текст инструкции. Это гибрид: система подсказок v8/v6, примеры, которые выбираются по составу переписки, схема генерации, которая по словарям разрешает модели только правдоподобные типы фактов, идентификаторы доказательств и якоря договорённостей, замена идентификаторов сообщений короткими псевдонимами и серверная проверка ответа. Любая из этих частей меняет результат, поэтому квалифицируется вся связка.

Наборы данных покрывают её неравномерно. GOLDEN и DEV v1 — до трёх сообщений, четыре типа фактов, без договорённостей и без `PURCHASE_INTENT`; оба построены генератором из одних и тех же шаблонных фраз, так что это регрессия разбора фактов, а не проверка обобщения. Смыслы контракта v2 (договорённости, покупка, длинный контекст) покрывают только три небольших набора DEV (27, 21 и 6 случаев), по которым инструкцию настраивали.

Первый замер v9 на DEV v1 в формате v2 прошёл общие пороги, но показал полноту `BUSINESS_COMMITMENT` 0,73 (у v6 — 1,0): на четырёх простых обещаниях («Сформирую счёт и пришлю его сюда») модель записывала `COMMITMENT` в `agreements` и пропускала факт. Факт читает PROMISE_NOT_FULFILLED, поэтому пропуск молча отключает контроль обещаний, а общие доли его не показывают.

Чем ограничена полнота и предел запроса, выяснилось при первом замере:

- Словарь признаков. Грамматика facts и серверная проверка v2 принимают `BUSINESS_COMMITMENT` только для сообщений, которые узнаёт `explicitAgreementTrigger(COMMITMENT)`. Часть обычных обещаний (3 из 20 шаблонных фраз генератора, а в живой речи — любой глагол вне списка: «Оформлю заявку и подтвержу по телефону») факта не получит никогда. Словарь генерации договорённостей короче словаря проверки («передам», «сообщу», «напишу» есть только во втором).
- Порядок полей. Модель пишет ответ подряд. Перестановка `[summary, agreements, facts]` возвращает факт, но стабильно ломает два случая жизненного цикла договорённостей (3 прогона из 3); резюме в конце (`[agreements, facts, summary]`, `[facts, agreements, summary]`) резко ухудшает факты (полнота намерения записаться 0,45–0,55, `BUSINESS_COMMITMENT` 0,0–0,71): резюме в начале работает как рассуждение. Подсказка «обещания найдены в сообщениях m2» и правило в инструкции доводят простые обещания только до 5 из 7.
- Контекст. Узел работает с контекстом 4096 токенов на запрос вместе с ответом, а продукт собирает до 20 сообщений и 12 000 рун. По 21 замеру (отклонение до 51 токена) запрос по самому тяжёлому пути занимает около `2557 + 0,362 · руны + 13,4 · сообщения` токенов, ответ — до 250 токенов и больше. В контекст помещается 2,1–3,2 тыс. рун переписки; более длинная получит отказ сервера (`PROVIDER_INFERENCE_FAILED`, повторы, мёртвое задание). Зонд на живом узле позднее подтвердил оценку (п. 11).

## Решение

1. **Tuple и выбор до GOLDEN.** Tuple — файлы, формирующие запрос и разбирающие ответ (`scripts/ai-selection.py`: инструкции, примеры, схема генерации, поставщик, валидаторы, runner, контракты), параметры, веса, сборка и настройки сервера, наборы, оборудование. До открытия GOLDEN `ai-selection.py write` записывает SHA-256 каждого файла, наборов и отчётов DEV, по которым принято решение, и отказывается записывать выбор по непройденному отчёту. `make ai-benchmark-golden` сначала проверяет выбор (`verify`) и не запускается, если файл tuple изменился. GOLDEN запускают один раз; повторный прогон допустим только как доказательство оборудования.
2. **Пороги.** Прежние (`precision ≥ 0,90`, точность типа ≥ 0,85, `recall ≥ 0,90`, `F1 ≥ 0,90`, exact ≥ 0,85, valid ≥ 0,99, evidence ≥ 0,90, p95 ≤ 8000 мс) плюс полнота каждого представленного типа факта ≥ 0,85 (`-minimum-fact-recall`): общие доли пропустили падение `BUSINESS_COMMITMENT` до 0,73. Оборудование: пик видеопамяти ≤ 7500 МиБ, нет OOM и перезапусков, скорость ≥ 20 токенов/с, ни одного ответа, оборванного по длине, ни одного отказа сервера, запрос вместе с ответом не больше контекста.
3. **Отчёт привязан к серверу.** `ai-benchmark` читает запросами GET сборку llama.cpp, файл и размер модели, контекст, число слотов и параметры последнего запроса (включая режим рассуждений) и пишет их в `server`; `performance` содержит токены, скорость, коды ответов, ответы, оборванные по длине, и окно прогона; у отказов есть причина (`detail`, с причиной сервера). Адреса узла в отчёт не попадают. `-schema-version` подменяет контракт после проверки суммы, несовместимая пара отклоняется. `-trace` пишет измерения и сырой ответ каждого обращения (рабочий материал, не часть репозитория).
4. **Оборудование измеряется на узле.** `scripts/ai-node-sample.sh` снимает на узле видеопамять и состояние контейнера во время прогона, `scripts/ai-hardware-report.py` сводит снимки с `performance` отчётов и проверяет, что снимки покрывают время прогонов. Зонд длинного контекста (`models/datasets/context_probe_v1.jsonl`, `scripts/ai-context-probe.py`) строится из пределов `analysis.go`.
5. **Манифест собирается из отчётов.** `scripts/ai-manifest.py` берёт числа из отчётов и сверяет версии, сумму GOLDEN, параметры, которые видел сервер, контекст и слоты, а сами числа отчётов (доли, полнота и точность по типам, p95) сравнивает с порогами манифеста независимо от флага `passed`. `FROZEN` — только при полном комплекте, включая оборудование и пересчёт хэша весов; иначе `CANDIDATE` со списком недостающего. Прежний манифест сохраняется как отчёт и указан в `previousQualification`.
6. **Достройка факта обещания в поставщике v9.** Если ответ содержит доверенное соглашение `COMMITMENT` компании, а фактов `BUSINESS_COMMITMENT` нет вовсе, поставщик добавляет факт с уверенностью соглашения и доказательством в виде основания самого позднего такого соглашения. Условия: основание — исходящее обещание, которое принимает серверная проверка, без отрицания; явное решение модели (в том числе `value=false`) не переопределяется; дополненный ответ обязан пройти ту же проверку, иначе возвращается исходный. Причина: во всех 4 пропусках DEV v1 соглашение было, факта не было, а ограничение формата надёжнее просьбы в инструкции. Контракт, роли и правила доверия не меняются; в `ai_runs.raw_output` попадает восстановленный и дополненный ответ, как и раньше восстановленный, а не буквальный вывод модели.
7. **Порядок полей v9 остаётся прежним** (`summary`, `facts`, `agreements`): перестановка ухудшает жизненный цикл договорённостей, а резюме в начале нужно фактам.
8. **Бюджет контекста: контекст узла поднимается до 8192 (решение владельца 2026-10-10).** Бюджет продукта (20 сообщений, 12 000 рун) не меняется: при 8192 он помещается (около 7,7 тыс. токенов вместе с ответом по подгонке выше). `docker-compose.ai.yml` берёт значение из `LIDRADAR_AI_CTX_SIZE` (по умолчанию 8192), манифест фиксирует `contextSize` явным аргументом `ai-manifest.py --context-size 8192` и сверяет его с тем, что отдаёт сервер. Оценка роста KV-кэша — около 0,6 ГиБ при пике 5360 МиБ на контексте 4096, то есть около 6,0 ГиБ при пределе 7500 МиБ; это оценка. Подтверждают её зонд длинного контекста и отчёт об оборудовании, до них tuple v9 не получает `FROZEN`. Отвергнуты: уменьшение `MaxContextRunes` до 2000–2400 (теряется контекст длинных разговоров) и сокращение базового запроса (повторная настройка инструкции).
9. **Открыто: словари признаков.** Расширять списки обещаний можно только вместе с новой независимой выборкой: нынешние слова и глаголы генератора принадлежат и DEV, и GOLDEN, и подгонка под фразы GOLDEN обесценила бы контрольную выборку.
10. **Открыто: независимая выборка для контракта v2.** GOLDEN и DEV v1 — регрессия разбора фактов на одном пуле шаблонов (до трёх сообщений, без договорённостей и покупки); договорённости, покупку и длинный контекст покрывают только наборы DEV, по которым инструкцию настраивали. Нужен новый набор, написанный независимо и зафиксированный суммой до первого прогона.
11. **Страховка на плотный текст.** Бюджет продукта задан в рунах, а контекст сервера — в токенах; эмодзи, цифры и латиница занимают больше кириллической прозы. Зонд на узле с контекстом 4096 подтвердил расчёт: переписка в 6000 рун (половина предела) получила отказ `exceed_context_size_error`, а в 3000 рун и в типичные 1500 — прошла ([отчёт](../../models/reports/lidradar-main-v1-prompt-v9-context-probe-4096.json)). Поэтому поставщик v9 при таком отказе (HTTP 400, тип `exceed_context_size_error`, числа токенов берутся из ответа сервера) повторяет запрос по более короткому окну: отбрасывает самые старые сообщения (оценка веса — 0,45 токена на руну и 14 на сообщение, запас под ответ 600 токенов, не больше 4 повторов), последнее сообщение и граница анализа остаются, доказательства ответа остаются внутри исходного снимка, серверная проверка не меняется. Другие ошибки и более ранние версии инструкции не повторяются. Это деградация анализа вместо мёртвого задания, согласованная с тем, что окно и так обрезает старые сообщения по бюджету; в бенчмарке каждый такой повтор виден в `performance` как отказ сервера и проваливает отчёт об оборудовании, поэтому зонд при контексте 8192 обязан проходить без повторов.
12. **Противоречивые факты одного типа.** Модель изредка пишет два факта одного типа с разным значением (например, `BOOKING_INTENT` и `true`, и `false`). Серверная проверка отвергает такой ответ целиком, и вместе со спорным фактом пропадают верные остальные: на DEV v1 так терялся один случай из ста, а порог валидных ответов 0,99 допускает на GOLDEN не больше четырёх отказов из 400. Поставщик v9 до разбора убирает факты только тех типов, по которым ответ противоречит сам себе, остальное остаётся (`application.ConflictingFactTypes` сравнивает так же, как серверная проверка: сумма приводится к каноническому виду, одинаковые повторы противоречием не считаются). При сомнении модель молчит: правило инструкции «ложное срабатывание опаснее пропуска». Серверная проверка остаётся строгой для всех ответов, для ранних версий инструкции поставщик ничего не убирает. Если убраны все факты `BUSINESS_COMMITMENT`, п. 6 может достроить факт из доверенного соглашения того же ответа: соглашение — отдельное решение модели, а не часть спорного факта.

## Альтернативы

- **Порядок `[summary, agreements, facts]`.** Лучше на фактах (DEV v1 exact 0,99), хуже на договорённостях (18 из 21): ошибка переносится из одного поля в другое.
- **Только подсказка и правило в инструкции.** Дала 5 из 7 простых обещаний; модель игнорирует прямую подсказку.
- **Принудительный факт в грамматике при любом совпадении словаря.** Убрал бы решение модели и увеличил бы ложные срабатывания на фразах вроде «Не обещаю…».
- **Расширить словари сейчас.** Недостающие фразы известны из шаблонов генератора, то есть из контрольной выборки: подгонка под GOLDEN.
- **Просить владельца утвердить v9 как есть.** Общие пороги проходятся, но полнота `BUSINESS_COMMITMENT` 0,73 и предел контекста нарушают смысл допуска.

## Последствия

- Квалификация воспроизводима и проверяема: выбор, GOLDEN, оборудование и манифест связаны хэшами и временем, а числа манифеста нельзя ввести руками; сборщик манифеста сверяет их с порогами независимо от флага `passed`.
- **Результат квалификации v9 (2026-10-10).** GOLDEN, единственный прогон после записи выбора: precision 0,9075, recall 0,9619, F1 0,9339, exact 0,92 (368 из 400), valid 1,0, evidence exact 1,0, p95 4,4 с; полнота по типам 0,979 (`BOOKING_INTENT`), 0,909 (`BUSINESS_COMMITMENT`), 0,893 (`FOLLOW_UP_CANDIDATE`), 1,0 (`PRICE_MENTIONED`). Все пороги пройдены, манифест `FROZEN`. Запас по точности мал (0,9075 при 0,90; `BOOKING_INTENT` 0,869 при 0,85); относительно v6 точность (0,954) и F1 (0,957) ниже, полнота выше (0,959 → 0,962). Из 36 лишних фактов 28 — отрицательные (`value=false`): продукт их не использует (запросы риска и возможностей берут только `value = true`), но строгая разметка считает их ложными. Метрика и разметка после просмотра результата не менялись. Пять пропусков `BUSINESS_COMMITMENT`: в ответе нет соглашения `COMMITMENT`, достраивать факт (п. 6) не из чего.
- На DEV достройка факта и снятие противоречий дали 100 из 100 точных (до них — exact 0,94, полнота `BUSINESS_COMMITMENT` 0,73); наборы намерений, договорённостей и независимых обещаний — 27/27, 21/21, 6/6. DEV и GOLDEN из одного пула шаблонов: разрыв между 100 из 100 на DEV и 0,92 на GOLDEN показывает, как мало DEV говорит об обобщении.
- Риск контекста закрыт замером: на узле с контекстом 8192 самая длинная переписка бюджета продукта (6 606 токенов вместе с ответом) обработана без отказов, пик видеопамяти 5 844 МиБ (оценка в п. 8 была около 6,0 ГиБ), запас по контексту около 1,6 тыс. токенов; плотный текст покрывает п. 11. Самая долгая обработка такой переписки — около 11 с (вне порога p95 набора GOLDEN, он про типичные переписки).
- Отчёт GOLDEN просмотрен: любая следующая правка tuple (инструкция, примеры, схема, поставщик, словари, пороги, метрика) требует новой контрольной выборки, а не повторного прогона этой.
- Остаётся открытым: независимая выборка для смыслов контракта v2 (п. 10); словари признаков (п. 9); политика отрицательных фактов (убирать `value=false` в поставщике или учитывать их в метрике) — только вместе с новой выборкой; сверки tuple при запуске узла с манифестом нет, допуск проверяет `make ai-selection-verify`.
- Достройка факта увеличивает долю `BUSINESS_COMMITMENT`, но не создаёт обещаний там, где нет доверенного соглашения. Замер на DEV (узел с контекстом 4096, до снятия противоречий): полнота `BUSINESS_COMMITMENT` на DEV v1 0,73 → 1,0 (15 из 15), exact 0,94 → 0,98.
- Для узла остаются ручные шаги: запуск `ai-node-sample.sh` (нужен sudo) во время прогонов и пересчёт хэша весов (`ai-model-hash.py`); оба выполнены 2026-10-10 и повторяются при смене tuple.

## Миграция и откат

Изменения не требуют миграции базы. Достройка факта действует только для `analyze-conversation.prompt.v9`; откат — удаление вызова `ensureCommitmentFact` в `LlamaProvider.Infer`. Новые флаги `ai-benchmark` необязательны, старые команды работают. Цель `make ai-benchmark-golden` теперь требует записанного выбора; для исторических запусков v6 задайте `AI_BENCHMARK_SCHEMA_VERSION` и `AI_BENCHMARK_PROMPT_VERSION` и свой `AI_SELECTION`.
