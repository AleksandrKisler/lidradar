# 0037: Политика уведомлений: получатели, тихие часы и сводки

- Status: Accepted
- Date: 2026-09-03
- Baseline: Tasks.md v1.1, ЭТАП 20 (LR-BE-2001…2010), §3.7, §45–§47, LR-BE-RM-015/020

## Контекст

До этапа 20 единственным получателем был владелец с Telegram-привязкой, а
типы `DIGEST` (R2, R5) не доставлялись вовсе. ТЗ §3.7 задаёт настройку на
пользователя и тип риска, §46 — режимы `IMMEDIATE | DIGEST | DISABLED` и тихие
часы, §47 — детерминированный ключ дедупликации. LR-BE-RM-020 требует, чтобы
уведомление, попавшее в тихие часы, пришло в их конец одним сообщением с
актуальным состоянием риска. Нужно было решить, кто получатель, как хранить
отложенные уведомления и как в это вписывается канал `IN_APP`.

## Решение

1. **Получатель — каждый активный участник организации** по собственной
   настройке; отсутствующая строка означает значение по умолчанию §46.
   Ключ немедленного уведомления персональный:
   `risk:{risk_id}:opened:user:{user_id}`.
2. **Отложенная доставка — очередь `notification_digest_items`** с
   уникальностью `(tenant_id, user_id, risk_id)`: риск попадает в очередь
   получателя один раз. Элемент знает слот `YYYY-MM-DDTHH:MM` в часовом поясе
   организации и причину (`DIGEST` или `QUIET_HOURS`). Слот — обычная
   проверка по расписанию `NOTIFICATION_DIGEST_DUE`, отдельного процесса нет.
3. **Тихие часы = тот же механизм сводки.** Немедленное уведомление внутри
   тихих часов становится элементом слота `end`; в `end` все элементы слота
   уходят одним сообщением `RISK_DIGEST` с актуальным состоянием рисков —
   закрытые выпадают, пустая сводка не отправляется. Сводка не привязана к
   одному риску, поэтому не получает кнопок и не принимает команд Telegram.
4. **`IN_APP` — локальный канал.** Попытка завершается без внешнего
   провайдера; логический факт в `notifications` и есть in-app уведомление.
   Лента in-app уведомлений как API появится отдельно.
5. **Эскалация владельцу — под флагом конфигурации**
   `LIDRADAR_NOTIFICATIONS_OWNER_ESCALATION` (выключен), пока таблица
   `feature_flags` не создана этапом 26 (LR-BE-RM-003). Механизм готов:
   проверка `NOTIFICATION_ESCALATION_DUE` и уведомление `RISK_ESCALATED`.
6. Тихие часы по умолчанию 22:00–08:00 заполнены, но **выключены**: §46
   требует их поддержать, а не навязать; иначе ночные риски R1/R3/R4 ждали бы
   утра у всех организаций без явного решения владельца.

## Рассмотренные варианты

- Оставить получателем только владельца — противоречит настройке на
  пользователя §3.7 и основе эскалации «менеджер → владелец».
- Отдельная таблица тихих часов и отдельный планировщик сводок — два
  механизма для одной семантики «доставить позже одним сообщением».
- Хранить in-app уведомления в другой таблице — дублирует `notifications`,
  которая уже хранит логический факт с персональным ключом.
- Создать `feature_flags` досрочно — размывает границу этапа 26; источник
  флага меняется без изменения механизма.

## Последствия

Каждый открытый риск проходит через настройки всех участников; число
уведомлений растёт с числом участников, но ограничено персональными ключами.
Изменение настройки действует на новые риски: уже поставленные в очередь
элементы сохраняют свой слот. Смена часового пояса организации не ломает
очередь — слот хранится строкой, а проверка на тот же слот не дублируется.

## Перенос и откат

Миграция `000017_notification_policy` создаёт таблицы, расширяет `kind`
уведомлений, делает `risk_id` необязательным только для сводок и
переписывает существующие ключи в персональную форму. Откат — удаление
настроек и очереди; уведомления и доставки остаются читаемыми.
