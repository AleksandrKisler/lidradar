# 0038: Обратная связь по рискам, окно точности и граница ML-согласия

- Status: Accepted
- Date: 2026-09-03
- Baseline: Tasks.md v1.1, ЭТАП 21 (LR-BE-2101…2107), §70, LR-BE-RM-019

## Контекст

Этап 21 должен дать реальные данные о precision по каждому типу риска.
Задачи заданы заголовками: вердикт, причины, коррекция «не лид», неизменяемый
исторический контекст, разрешения, метрики и граница ML-согласия. LR-BE-RM-019
требует считать последний вердикт на риск и возвращать покрытие, а §70
запрещает автоматически добавлять реальные переписки в наборы данных без
явного, активного и отзываемого согласия.

## Решение

1. **`risk_feedback` — append-only факт со снимком.** Запись хранит тип,
   важность, статус, источник, версию правила, AI-прогон, сообщение-основание,
   стадию сделки и время обнаружения на момент вердикта. Несколько записей на
   риск допустимы; ключ идемпотентности не требуется, потому что каждая
   запись — самостоятельное наблюдение, а метрика читает последнюю.
2. **`FALSE_POSITIVE` закрывает активный риск** статусом `FALSE_POSITIVE`;
   уже закрытый риск не переписывается. **Причина `NOT_A_LEAD` закрывает
   сделку как `LOST`** через сервис Opportunity с источником `USER`: по машине
   этапов §26 `ARCHIVED` достижим только из `WON`/`LOST`, а закрытая сделка не
   меняется. Остальные причины остаются объяснением вердикта.
3. **Окно метрики — по времени обнаружения риска.** Precision, доля ложных и
   покрытие считаются по рискам, обнаруженным в `[from, to)`, каждый риск —
   один раз по последнему вердикту. Так числитель покрытия всегда часть
   знаменателя. Порог надёжности `0,5` возвращается в отчёте как
   `minimumCoverage`, а `reliable` вычисляется на сервере.
4. **Разрешения.** Вердикт требует `risks.manage` (владелец и менеджер),
   метрики — `analytics.read` (только владелец).
5. **ML-согласие — сущность организации** (`ml_consents`): одно действующее
   на область `DATASETS`, отзыв не удаляет строку, история выдач сохраняется,
   выдача и отзыв пишут аудит. Каждая запись обратной связи фиксирует
   `dataset_eligible` — действовало ли согласие в момент вердикта; инструменты
   наборов данных обязаны фильтровать по этому признаку. Без согласия данные
   служат только оказанию услуги.

## Рассмотренные варианты

- Идемпотентный ключ на обратную связь — противоречит нескольким записям
  на риск и не нужен: повтор запроса даёт ещё одно наблюдение с тем же
  вердиктом, метрика не меняется.
- Окно по времени записи обратной связи (как в примере LR-BE-RM-019) —
  покрытие становится неопределённым: риски окна и записи окна не совпадают.
- Коррекция «не лид» через исход `NOT_A_LEAD` модуля Corrective — исход не
  закрывает сделку, и остальные правила продолжали бы порождать риски.
- Флаг согласия в `organizations` — теряет историю выдач и автора.

## Последствия

Radar получает событие `risk.false_positive`; сделка, закрытая по «не лид»,
освобождает переписку для новой возможности. Аналитика этапа 22 читает
`risks_false_positive` из статусов, а precision — из обратной связи.

## Перенос и откат

Миграция `000018_risk_feedback` создаёт обе таблицы с триггерами
неизменяемости. Откат — удаление таблиц; статусы рисков остаются валидными.
