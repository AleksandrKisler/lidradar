# 0049: Доверенные proxy и адрес клиента

- Status: Accepted
- Date: 2026-10-10
- Approval: владелец проекта поручил закрыть H-10 в текущем обсуждении; схема доверия выбрана при реализации и подлежит его подтверждению при коммите.
- Scope: источник сетевого адреса клиента для ограничителей частоты, учёта сеансов и журнала входа. Уточняет 0032 и 0041; обработка `Origin`, TLS, схема данных и границы модулей не меняются.

## Контекст

API слушает обычный HTTP и работает за proxy, который завершает TLS (cookie `Secure`, ADR 0020 и 0041). Адресом клиента считался адрес соединения, то есть адрес proxy. Замер 2026-10-10 на запущенном API, когда все запросы приходили с одного адреса соединения: предел входа 20 в минуту исчерпывается за минуту, после чего верный пароль любого пользователя получает `429`; регистрация прекращается после 5 попыток в час на всю платформу; вебхуки всех организаций делят предел 1200 в минуту; в `sessions.ip` и журнал входа попадает адрес proxy. Заголовок `X-Forwarded-For` при этом не читался намеренно: ADR 0032 отверг доверие произвольному значению, потому что клиент подделывает его свободно, а значит, обходит предел сменой значения либо переносит его на постороннего.

## Решение

1. Настройка `LIDRADAR_TRUSTED_PROXIES` — список адресов и сетей через запятую (`10.0.0.5`, `172.16.0.0/12`, `fd00::/8`). Это узлы, которые завершают TLS перед API и вправе сообщать адрес клиента. Пустой список означает прежнее поведение: адрес соединения. Сеть `/0` и записи с битами узла (`10.0.0.1/8`) отвергаются при загрузке, чтобы опечатка не расширила доверие молча.
2. Заголовок `X-Forwarded-For` читается, только если адрес соединения входит в список. Записи обходятся справа налево: каждый proxy дописывает адрес своего соседа в конец, поэтому правый край честен. Доверенные узлы пропускаются, первый недоверенный адрес и есть клиент; всё левее него подконтрольно клиенту и не читается. Если все записи — доверенные узлы, клиентом считается самый дальний из них. Если запись не адрес или цепочка длиннее 64 узлов, клиентом остаётся ближайший к API доверенный узел: предел не обходится, а лишь становится общим. Несколько строк заголовка — одна цепочка в порядке получения. Допускаются порт и IPv6 в скобках; IPv4 внутри IPv6 приводится к IPv4, зона IPv6 отбрасывается.
3. Другие заголовки (`X-Real-IP`, `Forwarded`, `CF-Connecting-IP` и подобные) не читаются: порядок разбора остаётся единственным и однозначным.
4. Адрес определяется один раз на запрос промежуточным слоем роутера и передаётся в контексте (`httpplatform.ClientAddress`). Им пользуются все потребители: ограничитель частоты по префиксам, постоянные ограничители входа, регистрации и обновления сеанса, запись сеанса и журнал входа. Прямой вызов обработчика без роутера по-прежнему даёт адрес соединения.
5. В `staging` и `production` процесс `api` не запускается без списка (событие `runtime.configuration_invalid`): API слушает только HTTP, поэтому там он всегда за proxy, и без списка все пользователи делили бы один адрес. Остальные процессы список не требуют.
6. Если заголовок пришёл, но не принят (список пуст либо сосед не в списке), API пишет предупреждение `http.forwarded_header_ignored` с причиной `no_trusted_proxies` или `peer_not_trusted` не чаще раза в минуту. Адреса и значения заголовка в журнал не попадают.
7. Требования к edge: добавлять адрес своего соседа в конец `X-Forwarded-For` или заменять значение этим адресом (передавать присланное клиентом значение как есть нельзя, правый край цепочки должен принадлежать proxy), закрыть прямой доступ к API мимо proxy и держать в списке только proxy, а не сети клиентов: клиент из доверенной сети может назвать любой адрес.

## Альтернативы

- Доверять `X-Forwarded-For` от любого соседа: отвергнуто (ADR 0032), заголовок подделывается.
- Брать самую левую запись: её выбирает клиент.
- Протокол PROXY: сохраняет адрес на транспортном уровне, но требует поддержки у каждого ingress, изменения слушателя и новой зависимости. Для первого выпуска отвергнут; позднее его можно добавить, не меняя потребителей `ClientAddress`.
- Читать несколько заголовков (`X-Real-IP`, `Forwarded`, заголовки CDN): несколько механизмов нарушают требование однозначного порядка разбора.
- Доверять всем частным сетям по умолчанию: доверие остаётся неявным, а в сети Docker или Kubernetes рядом с proxy могут оказаться другие сервисы. Список явный.
- Ограничивать только на edge: не заменяет пределы по учётной записи и правила приложения.

## Последствия

- Появляется обязательная настройка окружения. Состав списка — часть конфигурации выпуска; смена сети proxy требует обновить список.
- Предел по адресу остаётся счётчиком в памяти процесса для маршрутов `/api/v1/auth/*`, вебхуков и AI-узла, а постоянные пределы входа и регистрации общие для экземпляров через PostgreSQL. Суммарный предел нескольких экземпляров по-прежнему нужно измерять.
- IPv6 учитывается по полному адресу: клиент со своей сетью /64 меняет адрес внутри неё и обходит предел по адресу; предел по учётной записи остаётся. Группировка по /64 этим решением не вводится.
- Провайдеры вебхуков приходят с нескольких общих адресов, поэтому организации по-прежнему делят предел вебхука этого адреса; теперь это адрес провайдера, а не proxy.
- В `sessions.ip` и `auth_audit_log.ip_address` хранится адрес клиента. Сроки хранения этих данных остаются предметом H-12.
- Проверка на настоящем edge (прямой обход закрыт, суммарный предел, несколько экземпляров, `429` и `Retry-After` через proxy) остаётся обязательной по [RG-DEPLOY](../engineering/RELEASE_GATES.md#rg-deploy); этот ADR её не заменяет.

## Проверка

Таблица разбора цепочки (подделка слева, несколько строк, порт, IPv6, повреждённые записи, длинная цепочка), роутер с ограничителем (клиенты за proxy не делят предел, подмена заголовка недоверенным узлом не обходит его и не переносит на постороннего), разбор и отказы конфигурации, обязательность списка для `api`, а также тест на настоящем стенде с постоянными ограничителями PostgreSQL и проверкой адреса в сеансе и журнале входа. Дополнительно проведён сквозной прогон запущенных API и proxy-заглушки.

## Миграция и откат

Схема данных не меняется. Пустое значение возвращает прежнее поведение, но в `staging` и `production` `api` с пустым списком не стартует, поэтому откат на старую сборку без списка допустим только вместе с отказом от proxy либо с пограничным ограничением, эквивалентным прежнему (см. ADR 0032, раздел о переносе и откате). Ограничения не отключаются.
