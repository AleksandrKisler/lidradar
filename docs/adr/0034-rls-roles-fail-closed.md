# 0034: Роли PostgreSQL и fail-closed контекст для RLS

- Status: Accepted (реализация уточнена ADR 0041)
- Date: 2026-09-02
- Baseline: Tasks.md v1.1, ЭТАП R (LR-BE-RM-018); уточняет ADR 0019

## Примечание о реализации (2026-09-03)

Реализация этапа 24 отличается от таблицы ниже в двух деталях, закреплённых
ADR 0041: контекст `lidradar.tenant_id`/`lidradar.user_id` ставится
`set_config(..., false)` в хуке пула перед каждой выдачей соединения, а не
`SET LOCAL` на транзакцию (репозитории работают без явных транзакций); роль
`lidradar_platform` обходит политики предикатом
`pg_has_role(current_user, 'lidradar_platform', 'MEMBER')` внутри самой
политики, а не атрибутом `BYPASSRLS`, поэтому миграциям не нужен
суперпользователь. Fail-closed семантика и набор ролей сохранены.

## Контекст

ТЗ §12 требует RLS до первого пилота, а ADR 0019 закрепляет его как второй
уровень защиты. Политика строится на `current_setting('lidradar.tenant_id')`,
но три сценария работают вне контекста организации: захват заданий общей
очереди, диспетчер исходящего журнала и административные модели чтения.
Включение RLS без явного решения сломало бы этапы 6, 13 и 23.

## Решение

Три роли PostgreSQL с разной дисциплиной контекста:

| Роль | Процессы | RLS | Контекст |
|---|---|---|---|
| `lidradar_app` | `cmd/api` | `FORCE ROW LEVEL SECURITY` | `SET LOCAL lidradar.tenant_id` из `X-Tenant-ID` на каждую транзакцию |
| `lidradar_worker` | `cmd/worker`, `cmd/scheduler` | `FORCE ROW LEVEL SECURITY` | `SET LOCAL` из `tenant_id` захваченного задания или события |
| `lidradar_platform` | захват, диспетчер, административные чтения | `BYPASSRLS` | не устанавливается |

Политика на каждой tenant-таблице:

```sql
CREATE POLICY tenant_isolation ON <table>
    USING (tenant_id = current_setting('lidradar.tenant_id', true)::uuid);
ALTER TABLE <table> FORCE ROW LEVEL SECURITY;
```

Второй аргумент `true` возвращает NULL при незаданной переменной, и сравнение
не совпадает ни с одной строкой: запрос без контекста видит пустую таблицу
(fail-closed), а не всю базу.

Круг запросов под `lidradar_platform` держится явным списком:
`jobs.claim`, `ai_jobs.claim`, `reclaim-expired-*`, `outbox.dispatch`,
`admin.*`. Любой новый запрос вне списка выполняется под ролью с RLS.

AI-узел в список не входит: у него нет доступа к PostgreSQL вообще, только к
HTTP API (ТЗ §48, ADR 0030).

## Рассмотренные варианты

Отклонены: единая роль владельца без RLS (текущее состояние, единственная
линия защиты — приложение); RLS только на `cmd/api` (worker читает те же
таблицы по идентификаторам из заданий); политика с `current_setting` без
`true` (ошибка вместо пустого результата ломает фоновые процессы неожиданно).

## Последствия

Каждая транзакция приложения обязана начинаться с установки контекста;
репозитории, работающие через пул без транзакции, переводятся на
транзакции или на явные `SET LOCAL`. Это цена, которую этап 24 оплачивает
целиком.

## Перенос и откат

Роли и политики создаются миграцией этапа 24 (LR-BE-2401); настоящая запись
фиксирует контракт заранее, чтобы код этапов 17–23 не полагался на чтение
без контекста. Откат — `DISABLE ROW LEVEL SECURITY` на таблицах без потери
данных; проверки приложения при этом остаются обязательными (ADR 0019).
