# 0057: Регистрация по приглашениям

- Status: Accepted
- Date: 2026-10-13
- Approval: владелец проекта 2026-10-13: регистрация первое время только по приглашениям; для новых организаций принята рекомендация — код платформы даёт право зарегистрироваться и самому создать одну организацию. ADR принят по этому поручению, подтвердить при коммите.
- Связь: [ADR 0020](0020-opaque-session-auth.md), [ADR 0032](0032-persistent-auth-throttling.md), [ADR 0045](0045-team-onboarding-and-secure-connect.md) (коды сотрудников), [ADR 0049](0049-trusted-proxies-client-address.md) (адрес клиента для лимита). Первая из трёх поставок жизненного цикла учётной записи; сброс и смена пароля, подтверждение почты, выгрузка и удаление данных — отдельные ADR.
- Scope: условия создания учётной записи и организации, коды платформы, режим регистрации, публичный признак режима, команды оператора. Не затрагивает пароли, почту, выгрузку и удаление данных.

## Контекст

Проверено по коду и контракту 2026-10-13:

- `POST /auth/register` открыт: создаёт учётную запись и сразу сессию, без кода и без подтверждения почты; ограничен только числом попыток с адреса (5 в час).
- `POST /organizations` не имеет ограничений: любой вошедший пользователь создаёт сколько угодно организаций. Поэтому закрыть одну регистрацию недостаточно.
- Приглашения сотрудников есть ([ADR 0045](0045-team-onboarding-and-secure-connect.md)): одноразовый 256-битный код, 7 суток, не привязан к почте; принять его можно только из уже созданной сессии (`POST /invitations/accept`).
- У закрытого API не было бы первого пользователя: `platform-admin` умеет только выдавать и отзывать право администратора и требует существующего пользователя.
- Почтовой инфраструктуры нет, поэтому коды передаются людьми.

## Решение

1. **Режим регистрации.** `LIDRADAR_REGISTRATION_MODE` принимает `open` и `invite_only`. По умолчанию `open` в `development` и `test`, `invite_only` в `staging` и `production`; любое другое значение — ошибка загрузки конфигурации. Явный `open` в `staging` и `production` допустим, API при старте пишет предупреждение `registration.open`. Режим читает только процесс `api`.
2. **Два вида кодов, один формат** (256 бит, 43 символа `base64url`, в базе только SHA-256, показывается один раз). Регистрация принимает любой из них в необязательном поле `inviteCode`:
   - **код сотрудника** (из ADR 0045): при регистрации пользователь создаётся и сразу получает членство с ролью приглашения;
   - **код платформы** (новый): выпускает оператор командой `platform-admin invite`; срок 14 суток по умолчанию (флаг `--days`, 1…60), одноразовый; при регистрации создаёт пользователя и даёт ему **право создать одну организацию** (`users.organization_rights = 1`).
3. **Правила режима.** В `invite_only` регистрация без кода получает `403 INVITATION_REQUIRED`. Код, который нельзя принять (неизвестный, просроченный, использованный, отозванный), получает один и тот же ответ `403 INVITATION_INVALID`: различие состояний выдавало бы лишнее. В `open` код не обязателен, но указанный код обрабатывается так же, и неверный получает `403 INVITATION_INVALID`. Все попытки, включая неверные коды, расходуют предел `REGISTER_IP`.
4. **Создание организации.** В `invite_only` `POST /organizations` требует право: транзакция создания организации уменьшает `users.organization_rights` на единицу условным `UPDATE … WHERE organization_rights > 0`; если права нет — `403 ORGANIZATION_CREATION_NOT_ALLOWED`, организация не создаётся. В `open` право не проверяется. У существующих пользователей право равно нулю: в закрытом режиме им новых организаций не создать, пока оператор не выдаст право командой `platform-admin allow-organization --email`.
5. **Погашение кода и создание пользователя атомарны.** Код платформы гасится в той же транзакции, что и вставка пользователя и сессии: `UPDATE platform_invitations … WHERE code_hash = $1 AND consumed_at IS NULL AND revoked_at IS NULL AND expires_at > now()` обязан затронуть ровно одну строку, иначе транзакция откатывается и регистрация получает `INVITATION_INVALID`. Занятая почта (`409 EMAIL_ALREADY_REGISTERED`) код не расходует. Код сотрудника сначала проверяется без расхода (узкий контракт модуля `tenant`), затем создаётся пользователь, затем код принимается существующей командой; если приём не удался из-за гонки, только что созданный пользователь и его сессия удаляются, регистрация получает `INVITATION_INVALID`.
6. **Бутстрап и команды оператора.** Первый код выдаёт сервер, а не API: `platform-admin invite [--note текст] [--days N]` печатает код один раз; `platform-admin invitations` показывает идентификатор, состояние (`PENDING`, `USED`, `EXPIRED`, `REVOKED`), срок и заметку без кодов; `platform-admin revoke-invitation --id UUID` отзывает ожидающий код; `platform-admin allow-organization --email адрес` добавляет единицу права существующему пользователю. Все четыре записываются в `admin_audit_log` (источник `CLI`) в той же транзакции: `PLATFORM_INVITATION_ISSUED`, `PLATFORM_INVITATION_REVOKED`, `ORGANIZATION_RIGHT_GRANTED`. Заметка в журнал не попадает (может содержать имя клиента).
7. **Публичные признаки для интерфейса.** `GET /api/v1/auth/registration` без сессии отдаёт `{ "mode": "open" | "invite_only" }`; `GET /api/v1/auth/me` получает аддитивное поле `canCreateOrganization` (`true` в `open`, иначе `organization_rights > 0`). Интерфейс показывает поле кода по режиму, а пользователя без членств и без права направляет к вводу кода сотрудника, а не к созданию организации.
8. **Данные и границы модулей.** Таблицу `platform_invitations` (`id`, `code_hash`, `note`, `created_at`, `expires_at`, `revoked_at`, `consumed_at`, `consumed_by_user_id`) владеет `admin`: выпускает, отзывает и перечисляет. Колонку `users.organization_rights` владеет `identity`. Прямые обращения к чужим данным, на которых держится решение, внесены в карту ([03-modules.md](../backend/03-modules.md), раздел 18): `identity` читает и погашает `platform_invitations` при регистрации; `tenant` уменьшает `users.organization_rights` в транзакции создания организации; `admin` увеличивает `users.organization_rights` командой `allow-organization`. Миграция `000024_platform_invitations`.

## Рассмотренные альтернативы

- **Оператор сам создаёт организацию и выдаёт владельцу код сотрудника с ролью `OWNER`.** Проще для сервера, но убирает шаг «создайте организацию» после регистрации и привязывает каждую организацию к ручной операции; владелец выбрал вариант с правом создать организацию самому.
- **Приглашение по адресу почты.** Нужна почтовая инфраструктура, которой нет; её решает отдельный ADR. Код без адреса не даёт поверхности для перебора учётных записей.
- **Список разрешённых адресов вместо кодов.** Требует заранее знать адреса и открывает проверку «этот адрес разрешён?» без секрета.
- **Оставить регистрацию открытой за ограничением частоты или капчей.** Не отвечает требованию «только по приглашениям» и не закрывает создание организаций.
- **Счётчик права в отдельной таблице.** Условное уменьшение одной колонки в транзакции создания организации проще и атомарно без новой таблицы; цена — одна документированная запись в чужую таблицу.
- **Погашение кода платформы авторизованным пользователем через `POST /invitations/accept`.** Полезно, но меняет ответ контракта; пока право выдаёт оператор командой, приём кода из приложения можно добавить позже без изменения этого решения.

## Последствия

- В production без выданного кода никто не зарегистрируется, включая оператора. Порядок первого запуска: `platform-admin invite`, регистрация по коду, создание организации, `platform-admin grant`. Он описан в [runbook](../runbooks/production-deployment.md).
- Существующие пользователи не теряют доступ, но не создают новых организаций в закрытом режиме без `allow-organization`.
- Код сотрудника, переданный не тому человеку, регистрирует чужую учётную запись в организации: ответственность на владельце, как и в ADR 0045; срок и одноразовость ограничивают ущерб.
- Ответы на неверный код однотипны, но `EMAIL_ALREADY_REGISTERED` остаётся у владельца действующего кода; он доступен только после проверки кода.
- Контракт получает аддитивные изменения: поле `inviteCode`, коды `INVITATION_REQUIRED`, `INVITATION_INVALID`, `ORGANIZATION_CREATION_NOT_ALLOWED`, ручку режима и поле `canCreateOrganization`; веб-клиент обновляется в той же поставке.
- Код платформы в ссылке (`/register?code=…`) попадает в историю браузера: интерфейс читает его и сразу убирает из адреса. Журналы API пишут путь без запроса, журнала запросов на краю нет.
- Рост таблицы `platform_invitations` мал; сроки хранения кодов определит политика [ADR 0056](0056-data-retention-and-erasure.md) при следующем пересмотре классов.

## Миграция и откат

Миграция `000024_platform_invitations` аддитивна: новая таблица и колонка с `DEFAULT 0`. Откат поведения — `LIDRADAR_REGISTRATION_MODE=open`: код режима не читает таблицу и право, схема остаётся. Таблицы не удаляются ([DOCS_GOVERNANCE](../engineering/DOCS_GOVERNANCE.md)). Старая сборка при новой схеме возвращает `503` из-за строгой проверки журнала миграций, поэтому откат бинарей требует проверенной матрицы совместимости ([runbook](../runbooks/backup-restore.md)).
