# 0039: Базовая аналитика читает необработанные факты модулей

- Status: Accepted
- Date: 2026-09-03
- Baseline: Tasks.md v1.1, ЭТАП 22 (LR-BE-2201…2209), §26, §39, §67, чек-лист пилота «Analytics совпадает с raw domain data»

## Контекст

Этап 22 должен показать бизнесу реальные деньги, а не оценку AI. Правила
архитектуры относят доступ к PostgreSQL к владеющему модулю, а чтение чужих
таблиц называют архитектурным решением. Чек-лист пилота требует, чтобы
аналитика совпадала с необработанными данными; денежные показатели уже
определены Radar (этап 9) и модулем Revenue (этап 12).

## Решение

1. **Модуль `analytics` читает таблицы других модулей только для чтения**
   (`messages`, `conversations`, `opportunities`, `opportunity_stage_history`,
   `risk_signals`, `outcomes`, `revenue_events`, `revenue_attributions`,
   `organizations`) и не хранит собственных агрегатов. Все запросы одной
   сводки выполняются в одной транзакции `REPEATABLE READ` только для чтения:
   показатели ответа берутся из одного снимка.
2. **Окно — календарные даты в часовом поясе организации** (LR-BE-2202),
   включительно, переводятся в `[from, to)` UTC один раз; по умолчанию 30
   дней, включая сегодняшний; не длиннее 366 дней.
3. **Определения совпадают с существующими KPI.** Подтверждённая выручка —
   события `CONFIRMED` в валюте организации, подтверждённые в окне;
   возвращённая — их часть с атрибуцией `RECOVERED` (ТЗ §39, как в Radar и
   `GET /api/v1/revenue/confirmed-recovered`). Потенциал — оценка ещё
   открытых сделок, открытых в окне, в валюте организации: оценка, а не
   выручка (ТЗ §26). События в других валютах не конвертируются и не
   учитываются.
4. **Счётчики берутся из фактов, а не из статусов на «сейчас», где есть
   история:** сделки — открытые в окне, а `BOOKED`/`WON`/`LOST` — переходы в
   окне по неизменяемой истории этапов; риски — обнаруженные, с действием,
   закрытые как `RESOLVED` и как `FALSE_POSITIVE` по временным отметкам;
   исходы — записи в окне.
5. Сводка доступна только по `analytics.read` (владелец) через
   `GET /api/v1/analytics/summary`.

## Рассмотренные варианты

- Материализованные счётчики или таблица агрегатов — расходятся с фактами
  при повторах и исправлениях, требуют пересчёта и противоречат чек-листу.
- Окно по UTC — границы суток не совпадают с рабочим днём организации.
- Потенциал по всем сделкам с оценкой, включая закрытые как `LOST` — завышает
  ожидания; Radar считает потенциал только по сделкам с активными рисками, и
  обе величины сознательно различаются назначением.

## Последствия

Стоимость запроса растёт с объёмом фактов за окно; индексы по `tenant_id` и
временным отметкам уже существуют, окно ограничено годом. Изменение
определения KPI в Radar или Revenue обязано синхронно менять аналитику.

## Перенос и откат

Схема не меняется; модуль можно отключить снятием маршрута без потери данных.
