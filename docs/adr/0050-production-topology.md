# 0050: Production-топология пилота

- Status: Accepted
- Date: 2026-10-10
- Approval: владелец проекта поручил перейти к production-топологии в текущем обсуждении (аудит готовности к деплою, блокер P0 №1); состав решения выбран при реализации и подлежит его подтверждению при коммите.
- Scope: способ запуска LidRadar в `production` и `staging` пилота: образы выпуска, состав сервисов, сети, edge (TLS, маршрутизация, поток событий, адрес клиента), секреты, пределы ресурсов и порядок обновления. Уточняет 0011 (Docker Compose был только средой разработки) и 0049 (конкретный edge и закреплённый адрес proxy). Схема данных, границы модулей и контракт API не меняются.

## Контекст

До этого решения production-контура не было. `compose.yaml` предназначен для разработки: учётная запись базы `lidradar`/`lidradar`, порты PostgreSQL `5432` и API `8080` опубликованы на всех интерфейсах (аудит 2026-10-10 подтвердил доступность по адресу локальной сети). Образы собирал сам compose с ревизией `unknown` и без меток, а базовый образ Go был плавающим тегом `golang:1.26-alpine`: на машине разработчика стояла 1.26.6 с достижимыми уязвимостями stdlib, исправленными в 1.26.9. Веб-клиент отдавал `503` на `/api/`, пока не написан ingress. TLS, маршрутизация потока событий, проверка здоровья снаружи и политика перезапуска отсутствовали. ADR 0011 фиксирует Docker Compose для локальной разработки и не выбирает платформу production; ADR 0049 требует proxy с известным адресом, но не описывает его.

## Решение

1. **Платформа.** Один хост, Docker Compose v2, файл `deploy/production/compose.yaml`, проект `lidradar-prod`. Оркестратора нет, `api` в одном экземпляре. Это ограничение закрытого пилота: отказоустойчивость хоста и масштабирование по горизонтали решением не вводятся.
2. **Образы неизменяемы.** `scripts/build-images.sh` собирает `lidradar-<команда>:<тег>` для `api`, `worker`, `scheduler`, `migrate`, `ai-agent`, `platform-admin`, `ai-node-register`, `ai-node-manage` и `lidradar-web:<тег>`. Тег — первые 12 символов git sha коммита; сборка из изменённого дерева отвергается (для проб есть `--allow-dirty`, он добавляет суффикс `-dirty`). `build:` в production-файле нет: версия выпуска — `LIDRADAR_VERSION`, и `/health/ready` показывает ту же версию и ревизию. Версия Go закреплена (`ARG GO_VERSION=1.26.9`), у образов есть метки OCI, общий кэш сборки делает пересборку остальных команд выпуска быстрой.
3. **Состав.** `edge` (Caddy 2.11.7), `web` (образ веб-клиента), `api`, `worker`, `scheduler`, одноразовый `migrate`, `postgres:18-alpine` и `backup` (копии вне хоста, [ADR 0051](0051-offhost-backups.md)). Операторские команды `platform-admin`, `ai-node-register`, `ai-node-manage` описаны под профилем `tools` и запускаются `docker compose run --rm`.
4. **Сети и порты.** Наружу публикуются только порты edge `80` и `443` (UDP не публикуется, HTTP/3 выключен). Сеть `edge` объединяет edge, web и api; `egress` даёт worker выход к Telegram Bot API; `data` объявлена `internal` и не имеет маршрута наружу: в ней база, migrate, scheduler, инструменты, а также api и worker. `api` состоит в `edge` (входящий путь и выход к Telegram) и в `data`, worker — в `egress` и `data`. `scheduler` и база выхода наружу не имеют.
5. **Edge.** Caddy выпускает и продлевает сертификат для `LIDRADAR_DOMAIN`, перенаправляет HTTP на HTTPS и отдаёт HSTS ровно один раз (`?Strict-Transport-Security` задаёт значение по умолчанию, API отдаёт свой). Маршруты: `/api/*` и `/internal/v1/ai/*` — в api (`flush_interval -1` для SSE, без сжатия, тело не более 2 МБ, ожидание заголовков ответа 60 с, соединение 5 с); `/health/live` — в api; остальное под `/health/*` отвечает `404`, потому что `/health/ready` раскрывает ревизию сборки и версии миграций; всё остальное — в web со сжатием. Заголовок `Server` удалён.
6. **Адрес клиента.** Caddy стоит первым на пути запроса и не получает заголовков от вышестоящего proxy, поэтому перезаписывает присланные клиентом `X-Forwarded-*`. Адрес edge закреплён в сети edge (`LIDRADAR_EDGE_IP`, по умолчанию `172.29.88.2` в `172.29.88.0/24`), остальным контейнерам адреса выдаются из верхней половины подсети (`ip_range`), чтобы Docker не отдал закреплённый адрес соседу. API получает `LIDRADAR_TRUSTED_PROXIES=<адрес edge>/32` и доверяет `X-Forwarded-For` только от него (ADR 0049). Подсеть и адрес настраиваются вместе, если подсеть пересекается с сетями хоста.
7. **Конфигурация и секреты.** Единственный файл `deploy/production/.env` вне git (права `600`), `.env.example` перечисляет все переменные. Обязательные значения проверяет сам compose: без них запуск отказывает с названием переменной. Каждый секрет передаётся только тому сервису, которому он нужен: токен Telegram — worker, ключ шифрования — api, пароли базы — по ADR 0052 (администратор — только базе, владелец — базе и одноразовому `migrate`, рабочий логин — базе и процессам с доступом к ней); web не получает окружения, edge получает домен и почту. Открытое соединение с базой допустимо только внутри сети `data` и только как явное решение оператора (`LIDRADAR_DATABASE_ALLOW_PLAINTEXT=true` в `.env`, по умолчанию `false`; ADR 0049 и fail-fast конфигурации). Для внешней базы задают `LIDRADAR_DATABASE_URL` с `sslmode=verify-full`.
8. **Усиление контейнеров.** У всех сервисов, кроме базы, корневая файловая система только для чтения (`tmpfs` на `/tmp`) и `cap_drop: ALL` (у edge остаётся `NET_BIND_SERVICE`); у всех — `no-new-privileges` и предел памяти, включая инструменты; журнал `json-file` с ротацией 10 МБ × 5; `restart: unless-stopped` у долгоживущих сервисов и `"no"` у одноразовых; проверки здоровья у edge, web, api и базы; `stop_grace_period: 30s` у api.
9. **Обновление.** Остановка всего приложения, миграция, запуск (stop-the-world): миграции идут только вперёд, а старая сборка с новой схемой отвечает `503` на готовности (строгая проверка журнала). Перед обновлением снимается копия; откат схемы — восстановление копии по `docs/runbooks/backup-restore.md`, откат одного образа безопасным не считается. Порядок и проверки — `docs/runbooks/production-deployment.md`.
10. **Приёмка.** `scripts/smoke-production.sh` проверяет развёрнутый стек снаружи (страница и маршрутизация, заголовки, единственный HSTS, закрытая готовность, редирект, закрытые порты) и изнутри (версия сборки и миграции). Инварианты файла compose и Caddyfile закреплены тестами `scripts/tests/test_production_compose.py`, сборка — `test_build_images.py`, приёмка — `test_smoke_production.py`; они входят в обязательный CI.
11. **Staging.** Тот же файл под другим именем проекта (`-p`), отдельным `.env`, доменом и данными, без клиентских данных. Отдельный хост предпочтителен: на хосте production порты `80` и `443` и сертификат заняты, а подсеть edge и закреплённый адрес пришлось бы менять; на нестандартных портах сертификат HTTP-01 и TLS-ALPN-01 не выпускается.

## Альтернативы

- Kubernetes, Nomad или управляемая платформа приложений: для одного хоста и закрытого пилота избыточны. Образы и набор переменных окружения переносимы, поэтому решение можно пересмотреть без изменения приложения.
- nginx как edge: образ web уже использует nginx, но выпуск и продление сертификатов потребовали бы отдельного клиента ACME и перезагрузок. Caddy делает это одной строкой конфигурации. nginx остаётся раздатчиком статики внутри образа web.
- Traefik: динамическая конфигурация через сокет Docker даёт edge-процессу, смотрящему в интернет, управление всем хостом. Caddy сокет не получает.
- Сборка образов на хосте (`build:` в compose): выпуск перестаёт быть воспроизводимым, тег не связан с коммитом.
- Один образ со всеми командами: образ на команду уже принят в Dockerfile (меньше поверхность и размер).
- Секреты через Docker secrets или суффикс `_FILE`: потребовали бы изменить загрузчик конфигурации во всех процессах. Отложено; сейчас секреты в окружении процессов и видны членам группы `docker`.
- CDN или балансировщик облака вместо Caddy: допустимо позднее; тогда его сети добавляются в `trusted_proxies` Caddy и в `LIDRADAR_TRUSTED_PROXIES`, а прямой путь к api остаётся закрытым.
- Внешняя управляемая база сразу: даёт восстановление на момент времени, недостижимое логическими копиями, но делает пилот зависимым от поставщика и внешнего канала. Встроенная база выбрана ради самодостаточности; путь с внешней базой оставлен открытым настройкой `LIDRADAR_DATABASE_URL`.

## Последствия

- Порты `80` и `443` хоста должны быть свободны и достижимы из интернета (выпуск сертификата); том `caddy-data` хранит ключи и сертификаты, его потеря означает новый выпуск с лимитами центра сертификации.
- Docker публикует порты в обход `ufw` и `firewalld`. Защита держится на том, что публикуются только `80` и `443`; тест compose отвергает любую другую публикацию.
- Хост — единая точка отказа. После перезагрузки хоста контейнеры поднимаются сами; процессы без базы завершаются с `runtime.failed` и перезапускаются политикой до её готовности.
- Образы не публикуются в реестр. Перенос на хост — `docker save | ssh | docker load` либо сборка на хосте тем же скриптом; реестр и конвейер выпуска остаются отдельным решением. Манифест выпуска (RG-DEPLOY) этим решением не создаётся.
- Внутренний трафик «edge → api» идёт по HTTP внутри сети Docker. Любой контейнер в сети edge способен обратиться к api напрямую, минуя ограничения Caddy на тело и `/health/*`; клиентский адрес он подделать не может, потому что его адрес вне списка доверенных.
- Первоначально владельцем встроенной базы был суперпользователь контейнера (`POSTGRES_USER`). Это закрыто [ADR 0052](0052-database-roles-owner-and-runtime.md): администратор `postgres` только по сокету, владелец `lidradar` без суперправ, рабочий логин `lidradar_runtime` без владения; стек, запущенный по этой схеме, переносят восстановлением копии в новый том.
- Окно недоступности api при выпуске без новых миграций около 10 секунд на пустой базе; миграции с долгими блокировками увеличат его. Статика веб-клиента отвечает и пока api остановлен, а запросы к API получают `502`.
- Расписание копий и копия вне хоста вводятся отдельным решением ([ADR 0051](0051-offhost-backups.md)) и службой `backup` в этом же стеке. Журналы за пределами хоста, внешний мониторинг (кроме сигналов копии), реестр образов и автоматическая доставка выпуска не вводятся.
- Секреты хранятся на хосте открытым текстом в `.env`; ротация ключа шифрования остаётся отдельным процессом.

## Проверка

2026-10-10 на Docker Engine 28.1.1 и Compose 2.35.1 (Docker Desktop, macOS, arm64) со сборкой образов `scripts/build-images.sh --allow-dirty` и доменом `localhost` с внутренним центром сертификации Caddy:

- запуск с нуля: `migrate` завершается кодом 0, `api`, `web`, `edge` и `postgres` становятся здоровыми; `scripts/smoke-production.sh` с проверкой внутренней готовности даёт 18 успешных проверок без замечаний;
- границы: снаружи слушают только порты edge; контейнер только в сети edge не разрешает имя базы, контейнер только в сети `data` не видит `web` и `edge`; к Telegram выходят api и worker, а scheduler и база — нет; сосед по сети edge с чужим адресом не получает доверия к `X-Forwarded-For` (API пишет `http.forwarded_header_ignored`), а запрос через edge записывает в сеанс адрес клиента; `Origin` и флаги cookie корректны;
- поток событий: соединение SSE через edge живёт 55 с с проверками активности на 20-й и 40-й секундах (до исправления write-deadline обрывалось на 40-й); штатный поток веб-клиента в настоящем Chrome (Playwright, `channel: chrome`) открывается один раз и держится 70 с без переподключения; ограничение тела 2 МБ даёт `413`;
- веб-клиент в Chrome за edge: страница `/radar` открывается с сеансом, нарушений CSP нет, cookie сеанса недоступна скрипту страницы, индикатор «Обновления онлайн» горит;
- обновление: остановка api/worker/scheduler, `migrate`, запуск — окно около 9 с, статика отвечает всё время, запросы к API получают `502`, после запуска edge восстанавливается сам, сеанс, созданный до остановки, действует;
- сбой и перезагрузка: `SIGKILL` процессу api снаружи контейнера — перезапуск политикой и готовность через 6 с; одновременный запуск всех контейнеров без учёта зависимостей, как после перезагрузки хоста — стек здоров через 7 с, api завершается с `runtime.failed: connect to PostgreSQL` и перезапускается политикой (в прогоне дважды за полсекунды), worker и scheduler дождались базы сами; `docker kill` Docker считает ручной остановкой и политику перезапуска не вызывает, поэтому сбой имитируется сигналом снаружи;
- операторские команды: `platform-admin grant` выдаёт право, и `/api/v1/admin/me` через edge отвечает `200`; `ai-node-register` пишет файл реквизитов с правами `0600` на хост; `backup.sh`, `restore-drill.sh` и `restore.sh` с `bootstrap-roles.sh` работают против базы стека без опубликованного порта.

Не проверено: выпуск настоящего сертификата (нужны публичный домен и открытые порты), поведение за облачным брандмауэром и балансировщиком, нагрузка стека целиком, внешняя база по `LIDRADAR_DATABASE_URL`, обновление с миграциями, меняющими схему, сборка и запуск на Linux-хосте (проверка шла на Docker Desktop). Эти проверки обязательны на целевом хосте по [RG-DEPLOY](../engineering/RELEASE_GATES.md#rg-deploy); решение их не заменяет.

## Миграция и откат

Схема данных не меняется. Решение добавляет файлы (`deploy/production/`, скрипты сборки и приёмки) и закрепляет версию Go в `Dockerfile`; разработка по-прежнему идёт на `compose.yaml` корня. Откат решения — отказ от этих файлов: образы остаются обычными образами OCI, а набор переменных окружения соответствует контракту `docs/backend/10-operations.md`, поэтому тот же выпуск запускается на другой платформе. Откат выпуска внутри топологии — восстановление копии, сделанной перед обновлением (см. runbook).
