# 0045: Команда по одноразовым кодам, статус онбординга и безопасное подключение каналов

- Status: Accepted
- Date: 2026-09-18
- Baseline: Tasks.md v1.1 §10–§12, §65; `docs/front-end/08-readiness-gaps.md`
  (GAP-API-008, GAP-API-009, GAP-API-010, GAP-CONTRACT-019); ADR 0018,
  0019, 0020, 0034, 0041

## Контекст

Экран «Команда» не имел HTTP API: приложение умело только добавлять
участника по идентификатору пользователя из тестов. Онбординг не имел
авторитетного состояния: клиент не мог понять, что обязательно, что можно
пропустить и с какого шага продолжать на другом устройстве. Подключение
канала требовало от браузера придумать секрет webhook и отправить токен
бота, а «Проверить связь» в макете предполагало живую проверку, тогда как
`GET …/health` читал сохранённое состояние. Отдельно поле `active` при
создании точки принималось и молча игнорировалось.

У MVP нет почтовой инфраструктуры и отдельного контура для выпуска
реквизитов; RLS включён для всех таблиц с `tenant_id` (ADR 0034/0041), а
пользователь, принимающий приглашение, ещё не состоит в организации.

## Решение

1. **Приглашения — одноразовые коды, а не письма.** `POST
   /organization/invitations` (`member.manage`) выпускает 256-битный код
   (`base64url`, 43 символа), показывает его владельцу один раз и хранит
   только SHA-256 в новой таблице `membership_invitations` (миграция
   `000022`). Срок действия 7 дней. Приглашение не привязано к адресу
   почты, поэтому поверхности для перебора адресов нет; код передаёт сам
   владелец. Состояние выводится из отметок: `PENDING`, `ACCEPTED`,
   `REVOKED`, `EXPIRED`. Отзыв — `DELETE …/invitations/{id}`, идемпотентный;
   принятое приглашение отозвать нельзя.
2. **Приём кода не требует организации в запросе.** `POST
   /invitations/accept` доступен сеансу без `X-Tenant-ID`: организацию
   определяет приглашение. Под ролью `lidradar_app` строка находится
   политикой `invitation_by_code`, которая открывает ровно одну строку с
   хешем, заданным на время транзакции (`set_config('lidradar.
   invitation_code_hash', …, true)`); затем транзакция задаёт локальный
   контекст организации и создаёт членство, либо восстанавливает
   отозванное (`DISABLED → ACTIVE`, роль из приглашения, `revoked_at =
   NULL`). Активный участник получает `409 ALREADY_MEMBER`. Аудит
   `INVITATION_ACCEPTED` записывается от имени нового участника в той же
   транзакции. Платформенная роль для этого не используется.
3. **Состав команды.** `GET /organization/members` (`member.manage`)
   отдаёт членства вместе с почтой и именем из таблицы `users` модуля
   `identity` — прямое чтение только для этого списка. `PATCH
   …/members/{userId}` меняет роль активного участника, `DELETE` переводит
   членство в `DISABLED` (строка сохраняется, LR-BE-RM-009). Обе команды
   блокируют все членства организации на время транзакции и отклоняют
   понижение или отзыв последнего активного владельца (`409 LAST_OWNER`),
   включая собственное. Аудит: `MEMBER_INVITED`, `INVITATION_REVOKED`,
   `INVITATION_ACCEPTED`, `MEMBER_ROLE_CHANGED`, `MEMBER_REVOKED`.
4. **Статус онбординга выводится из данных, сервер ничего не хранит.**
   `GET /organization/onboarding` (любой активный участник) считает факты
   одним запросом: активные точки, точки с полным недельным графиком,
   активные услуги, подключения и не отключённые подключения, личная
   привязка Telegram текущего пользователя. Обязательные шаги:
   `ORGANIZATION`, `LOCATION` (активная точка с графиком на семь дней),
   `SERVICES` (активная услуга), `CHANNEL` (подключение не в
   `DISCONNECTED`); `TELEGRAM_LINK` необязателен. `complete` — все
   обязательные выполнены; `nextStep` — первый невыполненный обязательный,
   затем первый невыполненный необязательный. Существующие организации
   получают статус без миграции данных.
5. **Секрет webhook выпускает сервер.** Если `webhookSecret` в запросе
   подключения опущен, сервер создаёт 256-битный `base64url`-секрет,
   сохраняет только его SHA-256 и возвращает открытое значение один раз в
   ответе `201` (`webhookSecret`) для поставщиков, у которых отправителя
   настраивает оператор (`TEST`, `IMPORT`, `GENERIC_WEBHOOK`). Для
   `CONNECTED_BUSINESS_BOT` сервер сам передаёт секрет в `setWebhook` и
   клиенту его не возвращает. Клиентский секрет по-прежнему принимается
   (16…256 символов).
6. **Одноразовая передача токена бота из браузера принята для MVP.**
   Токен передаётся один раз по TLS в теле запроса, шифруется AES-GCM с
   привязкой к организации, поставщику и идентификатору подключения
   (`LIDRADAR_INTEGRATIONS_CREDENTIAL_KEY`), не логируется и никогда не
   возвращается; в интерфейсе поле — write-only и очищается после
   отправки. Серверный OAuth/provisioning-контур для Telegram Business
   недоступен, а перенос ввода токена в CLI переложил бы настройку с
   владельца на оператора. Рекомендация владельцу — выпускать отдельного
   бота для LidRadar и отзывать токен через BotFather при компрометации.
7. **Живая проверка связи — отдельная команда.** `POST
   …/integrations/{id}/health/check` (`integration.manage`) для Telegram
   вызывает `getWebhookInfo`, сравнивает адрес с адресом подключения и
   сохраняет результат: `ACTIVE`, `ERROR/TELEGRAM_WEBHOOK_MISMATCH` или
   `ERROR/TELEGRAM_WEBHOOK_CHECK_FAILED` (`verification: REMOTE`). Для
   поставщиков без удалённой регистрации и отключённых подключений
   возвращается сохранённое состояние (`verification: LOCAL`).
   `GET …/health` остаётся чтением сохранённого состояния.
8. **`active` при создании точки отклоняется.** Новая точка всегда
   активна; поле принимается только в `PATCH`. Запрос с `active` в `POST
   /locations` получает `400 INVALID_ARGUMENT`.

## Consequences

- Появляется таблица `membership_invitations` с RLS и дополнительной
  политикой `invitation_by_code`; CI ожидает последнюю миграцию
  `000022_membership_invitations`.
- Модуль `tenant` читает `users` (список команды), `service_catalog_items`,
  `channel_connections` и `telegram_user_links` (факты онбординга) —
  только для чтения, зафиксировано в карте прямых чтений.
- Приглашение без адреса почты не защищает от передачи кода не тому
  человеку: ответственность на владельце, срок действия ограничен, код
  одноразовый, отзыв мгновенный.
- Восстановление отозванного членства через код возвращает участнику
  доступ к прежней истории его действий; это ожидаемо, так как история
  принадлежит организации.
- Выпущенный сервером секрет виден один раз; потеря секрета означает
  переподключение канала (новое подключение и отключение старого).

## Migration and rollback

Миграция `000022` только добавляет таблицу, индекс и политики; откат кода
оставляет таблицу неиспользуемой. Существующие подключения и членства не
меняются.
