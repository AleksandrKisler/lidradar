# 0040: Платформенное администрирование читает все модули и правит очереди

- Status: Accepted
- Date: 2026-09-03
- Baseline: Tasks.md v1.1, ЭТАП 23 (LR-BE-2301…2310), §64–§67, LR-BE-RM-008, чек-лист пилота

## Контекст

Этап 23 требует диагностировать сломанный контур без SQL и SSH: видеть
организации, каналы, очереди, мёртвые элементы, AI-узлы и прогоны,
потребление, восстанавливать цепочку от сообщения до выручки и повторять
или откладывать мёртвые элементы с аудитом. Правила архитектуры относят
доступ к таблицам к владеющему модулю; право `PLATFORM_ADMIN` по ТЗ —
системная роль пользователя, а не членства; аудит организаций требует
членства актора, которого у платформенного администратора нет.

## Решение

1. **Модуль `admin` читает таблицы всех модулей только для чтения** и не
   имеет собственных агрегатов; единственные записи — `platform_admins`,
   `admin_audit_log` и признак `discarded_at`/`discarded_by` в четырёх
   очередях (`jobs`, `outbox_events`, `ai_jobs`, `notification_deliveries`).
2. **`PLATFORM_ADMIN` — строка `platform_admins` на пользователя** с
   историей выдач: отзыв не удаляет строку, повторная выдача создаёт новую,
   активная не более одной (LR-BE-RM-008). Первый администратор появляется
   через команду `platform-admin grant`; у API нет пользователя, который мог
   бы его выдать. Проверка права не зависит от заголовка организации.
3. **Аудит администратора отделён от аудита организации.**
   `admin_audit_log` append-only, хранит источник `API`/`CLI`, актора для
   API, операцию, объект и организацию объекта; команды выполняются в одной
   транзакции с аудитом.
4. **Повтор возвращает мёртвый элемент в очередь** тем же путём, каким его
   берёт worker: статус `PENDING`, ноль попыток, свободная аренда; повтор
   AI-задания подчиняется правилу «одно ожидающее на переписку» и даёт
   конфликт, если новее задание уже стоит. **Откладывание** ставит
   `discarded_at`, элемент уходит из панели, строка остаётся.
5. **Модели чтения не раскрывают текст сообщений, промпты и сырой вывод
   модели** (§64): трасса содержит идентификаторы, статусы, коды ошибок и
   суммы; семантический результат — факты с признаком доверия без текста
   резюме.
6. Логи заданий и исходящего журнала получают корреляционные поля §66
   (`job_id`, `job_type`, `tenant_id`, `event_id`, `attempt`, `error_code`,
   `duration_ms`); текст ошибки целиком не пишется.

## Рассмотренные варианты

- Роль `PLATFORM_ADMIN` в `memberships` — привязала бы платформенное право к
  организации и потребовала фиктивного членства.
- Отдельный статус `DISCARDED` в очередях — расширил бы жизненные циклы,
  проверяемые схемой и worker'ами; признак на строке проще и обратим.
- Prometheus-экспозиция метрик — переносится на инфраструктурный этап; все
  счётчики §67 для очередей и продукта уже доступны JSON-панелью.

## Последствия

Административные запросы обходят границы модулей и должны меняться вместе с
их схемами. При включении RLS (этап 24) эти запросы выполняются ролью
`lidradar_platform` (ADR 0034). Токены в `ai_runs` не хранятся, поэтому
потребление считается по числу и длительности прогонов, а не по токенам.

## Перенос и откат

Миграция `000019_platform_admin` создаёт две таблицы и добавляет колонки
признака; откат — удаление таблиц и колонок без потери данных очередей.
