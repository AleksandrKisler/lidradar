# 0044: Обогащённые модели чтения Radar и переписок для интерфейса

- Status: Accepted
- Date: 2026-09-18
- Baseline: Tasks.md v1.1 §26, §36, §39; `docs/front-end/08-readiness-gaps.md`
  (GAP-CONTRACT-001/002, GAP-API-003/004/005/006/012/016,
  GAP-RELIABILITY-020, GAP-CONTRACT-021); ADR 0007, 0014, 0018, 0028, 0039

## Контекст

Аудит готовности интерфейса показал, что карточка риска и список переписок
нельзя собрать из существующих ответов API без запросов на каждую строку:
`RiskDetail` содержал только `contactId`, сокращённую сделку без услуги и
не давал имени контакта, канала, превью и внешней ссылки; список переписок
возвращал только `Conversation[]` без контакта, превью и признака риска и не
поддерживал поиск и фильтр «С риском». Менеджер (`risks.read`) не мог
получить имя услуги, потому что `GET /services` требует `service.manage`, а
политика видимости денег для него не была закреплена. Активную ленту нельзя
было запросить одним вызовом: `GET /risks` принимал один статус. Схема
OpenAPI расходилась с runtime (`MANUAL` в `Risk.source`, обязательность
связей, отсутствие `X-Tenant-ID` у путей Radar), а SSE молча терял сигналы
при переполнении буфера подписчика.

Правила архитектуры относят чтение таблиц другого модуля к архитектурному
решению (ADR 0014, карта прямых чтений в `docs/backend/03-modules.md`).

## Решение

1. **Модель чтения Radar обогащается в модуле `risk` одним запросом.**
   `RiskDetail` получает `contact {id, displayName}`, `service {id, name,
   active}`, `channel {connectionId, provider, name, status}`,
   `opportunity.serviceId`, `conversation.lastMessage {id, direction, type,
   preview ≤ 140 символов, sentAt}` и `externalLink`. Хранилище `risk`
   читает для этого `contacts`, `channel_connections`,
   `service_catalog_items`, `messages` и `external_identities`
   (дополнение к ADR 0007/0038). Ранжирование и курсор считаются только по
   `risk_signals` и `opportunities`; обогащение выполняется для строк уже
   отобранной страницы, поэтому стоимость не зависит от числа рисков
   организации. Корректирующие факты по-прежнему подгружаются пакетно.
2. **Контракт nullability закреплён.** Все ключи `RiskDetail`
   присутствуют всегда; `null` означает отсутствие связи (услуга, последнее
   сообщение) либо ещё не созданную владеющим модулем запись (рекомендация,
   исход, выручка). `nextCursor` во всех страницах — `string | null`.
   `Risk.source` включает `MANUAL`. Пути Radar и SSE объявляют общий
   параметр `X-Tenant-ID`.
3. **Фильтр статусов общий для списка и сводки.** `GET /risks` и
   `GET /radar` принимают повторяющийся `status` (или список через запятую)
   и краткую запись `active=true|false` (активные —
   `OPEN, ACKNOWLEDGED, ACTED`; терминальные — остальные четыре). `status`
   и `active` вместе отклоняются `400`. Набор статусов нормализуется
   (сортировка, дедупликация) и входит в ключ курсора: курсор с другим
   набором фильтров отвергается.
4. **Деньги в Radar видны любому обладателю `risks.read`.** Потенциал
   сделки и подтверждённо возвращённая выручка карточки и сводки — рабочие
   показатели приоритизации менеджера (§26, §39). Права `revenue.read` и
   `analytics.read` по-прежнему охраняют только организационные итоги
   (`GET /revenue/confirmed-recovered`, `/analytics/*`). Услуга в карточке
   — снимок каталога для чтения; управление каталогом остаётся за
   `service.manage`, отдельное право `service.read` не вводится.
5. **Список переписок — собственная модель чтения `ConversationListItem`.**
   Строка несёт `contact {id, displayName}`, `channel`, `lastMessage`,
   `activeRisks {count, maxSeverity}` и `externalLink`; серверные фильтры:
   `search` (имя, телефон по цифрам, почта; без учёта регистра; до 100
   символов; метасимволы `ILIKE` экранируются), `withRisk`, `locationId`,
   `connectionId`, `status`. Порядок остаётся `updated_at DESC, id DESC`;
   курсор несёт отпечаток фильтров и с другими фильтрами отвергается.
   Модуль `conversation` читает для этого `risk_signals`, `opportunities`,
   `channel_connections` и `external_identities`. Детали переписки получают
   `channel` и `externalLink`; каноническая `Conversation` остаётся
   независимой от канала.
6. **Внешняя ссылка строится только сервером.** Модуль `connector` владеет
   правилом `ContactDeepLink(provider, contactExternalID)`: единственная
   разрешённая схема — `tg://user?id=<число>` для
   `CONNECTED_BUSINESS_BOT`, где число — внешний идентификатор контакта в
   этом канале. Иначе `url = null` и `unavailableReason` —
   `PROVIDER_UNSUPPORTED` или `IDENTITY_UNKNOWN`. Клиент никогда не собирает
   URL из `externalId`. Переход по ссылке клиент фиксирует явно командой
   действия `OPEN_CONVERSATION` (`POST /risks/{riskId}/actions`); сервер по
   факту показа ссылки ничего не записывает.
7. **SSE получает маркер ресинхронизации.** Буфер подписчика остаётся 16
   сигналов; при переполнении сервер отбрасывает накопленные сигналы и
   посылает одно событие `resync.required` с телом
   `{"reason":"BUFFER_OVERFLOW"}`, после которого клиент перечитывает
   сводку и открытые списки целиком. Повтор событий и `Last-Event-ID`
   по-прежнему не вводятся (ADR 0028). Ответ `503 UNAVAILABLE` при
   неинициализированной шине описан в контракте.
8. **Именованные права корректирующих команд стали фактическими
   ограничениями.** `POST /risks/{riskId}/actions` требует `action.manage`,
   `POST /opportunities/{opportunityId}/outcomes` — `outcome.manage`,
   рекомендация — `risks.manage`. Карта ролей не меняется: у OWNER и MANAGER
   есть все три права.

## Consequences

- Интерфейс собирает Radar, карточку риска и список переписок из одного
  ответа без N+1; неизвестные для клиента поля не требуются.
- Появляются новые прямые чтения чужих таблиц: `risk` → `contacts`,
  `channel_connections`, `service_catalog_items`, `messages`,
  `external_identities`; `conversation` → `risk_signals`, `opportunities`,
  `channel_connections`, `external_identities`. Они только для чтения и
  зафиксированы в карте `docs/backend/03-modules.md`.
- Поиск переписок по подстроке не использует индекс; для объёмов MVP
  (тысячи переписок на организацию) это приемлемо, при росте потребуется
  `pg_trgm` или отдельный индекс — отдельное решение.
- Клиенты, ожидавшие `items: Conversation[]`, обновляют адаптер на
  `ConversationListItem`; старые курсоры списка переписок и рисков
  недействительны (ответ `400`, клиент начинает с первой страницы).
- Будущая роль с `risks.read` без `action.manage` не сможет записывать
  действия — это желаемое поведение карты ролей.

## Migration and rollback

Схема базы не меняется. Откат — возврат предыдущих обработчиков; данные не
затрагиваются.
