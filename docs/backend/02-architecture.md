# Архитектура

Документ описывает форму системы, слои и правила зависимостей, состав
процессов и контрактов. Он не привязан к этапам разработки: здесь то, что
верно для текущего кода и закреплено принятыми ADR.

## 1. Форма системы

LidRadar — **модульный монолит на Go** (ADR 0001). Один репозиторий и один
Go-модуль `lidradar` собираются в несколько независимых исполняемых процессов
(ADR 0002), которые делят код модулей, но не делят память: всё долговременное
состояние, очереди, расписания, идемпотентность и исходящий журнал событий
живут в **PostgreSQL — единственном источнике истины** (ADR 0003).

```text
                         ┌──────────────────────────────┐
  браузер / фронт ──────►│ cmd/api  (HTTP, SSE)          │
  провайдеры (webhook) ─►│  роль lidradar_app + platform │
  домашний AI-узел ─────►│  /internal/v1/ai (pull)       │
                         └──────────────┬───────────────┘
                                        │ SQL
        ┌───────────────────────────────▼───────────────────────────────┐
        │ PostgreSQL 18: таблицы модулей, jobs, scheduled_checks,        │
        │ outbox_events, notification_deliveries, ai_jobs, RLS-политики  │
        └───────▲───────────────────────────────▲───────────────────────┘
                │ SQL                           │ SQL
   ┌────────────┴─────────────┐    ┌────────────┴─────────────┐
   │ cmd/worker               │    │ cmd/scheduler            │
   │ outbox → jobs → handlers │    │ scheduled_checks → jobs  │
   │ доставка уведомлений     │    │ роль lidradar_platform   │
   │ роль lidradar_worker     │    └──────────────────────────┘
   └──────────────┬───────────┘
                  │ HTTPS (Bot API)
            Telegram
```

Внешние системы: Telegram (Connected Business Bot как источник сообщений и
отдельный транспорт уведомлений), llama.cpp на домашнем GPU-узле (вывод
модели), S3-совместимое хранилище вложений (пока не подключено: пакет
`platform/objectstorage` пуст, хранятся только метаданные вложений).

Явные запреты MVP (`docs/architecture/NON_GOALS.md`): GraphQL, WebSocket,
Redis, Kafka, NATS, Kubernetes, Elasticsearch, ClickHouse, микросервисы,
Telegram-userbot и MTProto-сессии, автономные AI-продажи и автоответы клиенту,
полноценные CRM/BI/биллинг, иерархия прав по филиалам, отдельное мобильное
приложение. Обязательные альтернативы: REST + OpenAPI, SSE только как сигнал
инвалидации, PostgreSQL для очередей и outbox, модули вместо сервисов,
Connected Business Bot вместо userbot, асинхронный AI, ограниченный
семантическими фактами.

## 2. Технологический базис

| Область | Выбор | Закреплено |
|---|---|---|
| Язык и рантайм | Go 1.26.x, `CGO_ENABLED=0`, статические бинарники в `alpine` | ADR 0011 |
| HTTP | `net/http` + `github.com/go-chi/chi/v5` | ADR 0012 |
| База | PostgreSQL 18.x, драйвер `github.com/jackc/pgx/v5` (pgxpool), SQL без ORM | ADR 0013 |
| Деньги | `github.com/shopspring/decimal`, суммы передаются десятичными строками | ADR 0016 |
| Идентификаторы и время | UUIDv7-совместимые идентификаторы (`platform/ids`), `TIMESTAMPTZ`, всё в UTC | ADR 0015 |
| JSONB | только для расширяемых данных (metadata, сырые события, факты), не для бизнес-полей | ADR 0017 |
| Хеширование паролей | Argon2id (`golang.org/x/crypto`) | ADR 0020 |
| Логи | `log/slog`, структурированные записи с корреляцией | ADR 0011 |
| Контракт API | OpenAPI 3.1 (`contracts/openapi/openapi.yaml`), проверяется Redocly в CI | ADR 0022 |
| Развёртывание | Docker Compose, один `Dockerfile` с аргументом `COMMAND` | ADR 0002 |

Внешних зависимостей всего четыре прямых (`go.mod`): chi, pgx, decimal,
x/crypto. Всё остальное — стандартная библиотека. Prometheus-совместимые
метрики и OpenTelemetry-трассировка входят в базис `ARCHITECTURE.md` как
допустимые технологии, но отдельный экспортёр метрик в коде не реализован:
наблюдаемость сейчас строится на структурированных логах, событии состояния
очередей и административной панели (см. [10-operations.md](10-operations.md)).

## 3. Слои модуля и правила зависимостей

Каждый бизнес-модуль в `backend/internal/<module>` состоит из четырёх пакетов:

```text
transport ──► application ──► domain ◄── infrastructure
   HTTP,          сценарии,      правила,        PostgreSQL,
   CLI, DTO       права,         инварианты,     внешние
                  транзакции     порты           адаптеры
```

- `domain` — сущности, статусы, инварианты, интерфейсы-порты хранилищ. Не
  знает ни о HTTP, ни о PostgreSQL, ни о других модулях.
- `application` — сценарии использования (сервисы): проверка прав,
  идемпотентность, порядок операций, публикация событий и заданий, аудит.
- `infrastructure` — реализации портов: PostgreSQL-хранилища, адаптеры
  Telegram, llama.cpp, in-memory реализации для тестов.
- `transport` — HTTP-обработчики chi, разбор запросов, маппинг ошибок в коды,
  SSE.

Правила проверяются инструментом `backend/tools/archcheck` (обязателен в CI,
`.github/workflows/architecture.yml` и `backend.yml`). Ровно то, что он
запрещает:

| Слой | Запрещено импортировать | Сообщение проверки |
|---|---|---|
| `domain` | `lidradar/backend/platform`, `net/http` | domain must not depend on transport or persistence technology |
| `domain` | любой слой другого модуля | domain must not depend on another module layer |
| `domain` | любой внешний пакет, кроме `github.com/shopspring/decimal` | domain must not depend on an external SDK or adapter |
| `application` | `infrastructure`, `transport` | application may depend on domain, not adapters |
| `infrastructure` | `transport` | infrastructure must not depend on transport |
| любая команда `backend/cmd/*` | конструкторы `NewMemory*`, `NewTestMemory*`, типы `MemoryStore`, `MemoryRepository` | runtime command references … (in-memory adapters are test-only) |

Следствия: бизнес-правила живут в `domain` и тестируются без базы; адаптеры
заменяемы; рабочие процессы никогда не запускаются на in-memory заглушках.

## 4. Границы модулей и общение между ними

Полный разбор ответственности каждого модуля — в
[03-modules.md](03-modules.md). Карта:

| Модуль | Владеет | Публичный контракт для других модулей |
|---|---|---|
| `identity` | пользователи, пароли, сессии, вход/выход, троттлинг входа | разбор сессии для `transport` (principal), события аудита входа |
| `tenant` | организации, членства и роли, точки, часы работы, ML-согласие | проверка разрешений (`Allowed(ctx, actor, tenant, permission)`), часовой пояс и валюта организации, часы работы точки |
| `catalog` | каталог услуг организации | список активных услуг для распознавания коммерческого намерения |
| `connector` | подключения каналов, приём и проверка вебхуков, сырые события, нормализация в канонические события | канонические события `CanonicalEvent` для `conversation` |
| `conversation` | контакты, переписки, сообщения, вложения, ревизии | событие `conversation.changed.v1`, чтение переписки/сообщений по портам |
| `opportunity` | коммерческие возможности, этапы, история переходов | события `opportunity.created.v1`, чтение возможности |
| `risk` | сигналы риска, правила и расписания проверок, Radar, SSE, обратная связь и точность | события `risk.opened.v1`/сигналы `risk.changed`, чтение рисков |
| `corrective` | рекомендации, действия, исходы, идемпотентность команд | последний исход и действия для Radar и выручки |
| `revenue` | события выручки и атрибуция к рискам | подтверждённая возвращённая выручка |
| `notification` | логические уведомления, попытки доставки, Telegram-привязки, политика получателей, сводки | доставка по `risk.opened.v1`, обработка `/start` и кнопок |
| `ai` | AI-узлы, AI-задания и прогоны, семантические сводки переписок, допуски узлов | семантические факты для правил риска, событие `ai.analysis.applied.v1` |
| `events` | транзакционный outbox и диспетчер | запись события в той же транзакции, реестр обработчиков |
| `jobs` | очередь заданий с арендой, отложенные проверки, worker и scheduler | постановка задания/проверки, реестр обработчиков |
| `analytics` | сводка показателей за окно календарных дат | — (только чтение) |
| `admin` | платформенные администраторы, панели очередей, мёртвые элементы, трасса | — (только для `PLATFORM_ADMIN`) |
| `audit` | журналы `audit_log` и `auth_audit_log` | `Recorder` для сервисов |

Правило `ARCHITECTURE.md`: прямое чтение или запись данных другого модуля —
архитектурное решение, а не сокращение пути. Действующие исключения, каждое с
ADR:

- `risk` читает таблицы переписок, сделок, точек, расписаний, фактов AI,
  исходов, действий и выручки только для чтения (ADR 0007, 0038);
- `corrective` читает `risk_signals`, `opportunities`, `memberships` и
  единственный из модулей **пишет** в чужую таблицу — переводит
  `risk_signals.status` в `ACTED` в транзакции действия (спецификация
  «Рекомендации, действия и исходы»);
- `revenue` читает риски, действия, исходы и сделки для проверки цепочки
  атрибуции; `conversation` блокирует `channel_connections` при приёме
  (ADR 0025); `opportunity` читает `conversation_summaries` и `messages` для
  доверенных фактов (ADR 0008); `ai` строит контекст промпта из организаций,
  точек, переписок и сообщений (ADR 0008); `notification` читает
  организации, членства, риски, сделки, переписки и контакты для политики и
  текста сводки (ADR 0029, 0037);
- `analytics` читает необработанные таблицы модулей в одной read-only
  транзакции REPEATABLE READ (ADR 0039);
- `admin` читает таблицы всех модулей только для чтения и правит статусы
  очередей (`jobs`, `outbox_events`, `ai_jobs`, `notification_deliveries`)
  через собственные команды с аудитом (ADR 0040);
- `loadgen` (инструмент испытаний и staging) пишет строки всех модулей
  напрямую, соблюдая ограничения схемы (ADR 0042).

Полная карта прямых чтений и записей — [03-modules.md](03-modules.md) § 18.

Остальное общение — через события outbox и задания очереди с версионированными
именами (`<domain>.<event>.v1`) и через интерфейсы уровня `application`,
которые внедряются в композиционных корнях `backend/cmd/*`.

## 5. Процессы

| Команда | Роль в системе | Пул и роль PostgreSQL | Что запускает |
|---|---|---|---|
| `cmd/api` | HTTP API, вебхуки, SSE, API AI-узла, административный API | `lidradar_app` для запросов организаций; `lidradar_platform` для API узла и админки | маршрутизатор с middleware, ретранслятор сигналов `LISTEN/NOTIFY` для SSE |
| `cmd/worker` | обработка outbox и заданий, доставка уведомлений, ежеминутное событие состояния очередей | `lidradar_worker` для обработчиков; `lidradar_platform` для захвата заданий, диспетчера и доставок | циклы диспетчера и worker с арендами |
| `cmd/scheduler` | перенос просроченных `scheduled_checks` в `jobs` | `lidradar_platform` | цикл планировщика |
| `cmd/migrate` | применение встроенных миграций с контрольными суммами | владелец схемы (пользователь подключения) | однократный запуск, `restart: "no"` |
| `cmd/ai-agent` | домашний AI-узел: pull заданий, вызов llama.cpp, отправка результата | не имеет доступа к базе; только HTTPS к API | цикл heartbeat/claim/complete |
| `cmd/ai-node-register`, `cmd/ai-node-manage` | регистрация узла и управление допусками организаций | владелец | CLI |
| `cmd/platform-admin` | выдача первого права `PLATFORM_ADMIN` | владелец | CLI |
| `cmd/load-generate` | синтетический набор для staging | владелец | CLI, запрещён в `production` |
| `cmd/ai-benchmark`, `cmd/ai-dataset-generate`, `cmd/ai-dataset-audit` | измерение и фиксация модели | без базы | CLI |

Все процессы читают типизированную конфигурацию из переменных окружения
(`platform/config`), обязательна `LIDRADAR_ENV ∈ {development, test, staging,
production}`; при отсутствии обязательной настройки процесс завершается с
ненулевым кодом. Долгоживущие процессы обрабатывают `SIGINT`/`SIGTERM` и
останавливаются плавно в пределах `LIDRADAR_SHUTDOWN_TIMEOUT`.

## 6. Платформенные пакеты

`backend/platform` — технические средства без бизнес-правил:

| Пакет | Назначение |
|---|---|
| `config` | загрузка и валидация всех `LIDRADAR_*` переменных |
| `http` | общий маршрутизатор, цепочка middleware, конверт ошибок, JSON-помощники, заголовки безопасности, ограничитель частоты |
| `postgres` | открытие пулов (`Open`, `OpenAs` с ролью), хуки контекста организации, встроенные миграции, проверка готовности схемы |
| `tenantctx` | перенос идентификаторов организации и актора в `context.Context` |
| `ids` | генерация UUIDv7-совместимых идентификаторов, проверка формата |
| `crypto` | симметричное шифрование реквизитов интеграций, хеши секретов |
| `observability` | логгер `slog`, корреляционные идентификаторы в контексте |
| `health` | интерфейс проверки готовности |
| `buildinfo` | версия и ревизия сборки (через `-ldflags`) |
| `bootstrap` | загрузка конфигурации, логгер, коды выхода и штатная остановка для команд |
| `objectstorage` | место для хранилища вложений; пакет пуст (только `.gitkeep`), двоичные вложения пока не хранятся |

Домен модулей не импортирует `platform` (правило archcheck): платформа
подключается только в `application`/`infrastructure`/`transport` и в
композиционных корнях.

## 7. Контракты

- **REST:** `contracts/openapi/openapi.yaml` (OpenAPI 3.1, `info.version 1.0.0`).
  Все описанные пути подключены к рабочему API; маршрут будущего этапа
  помечался бы расширением `x-lidradar-runtime-status: planned`, сейчас таких
  нет. Схемы безопасности: `sessionCookie` (браузерная сессия) и
  `aiNodeBearer` (секрет узла).
- **AI:** `contracts/ai/analyze_conversation_v1.schema.json` — строгая JSON-схема
  результата анализа переписки; тот же валидатор используется рабочим агентом и
  бенчмарком.
- **События и задания:** версионированные строковые типы, например
  `conversation.changed.v1`, `risk.opened.v1`, `connector.normalize-raw-event.v1`,
  `risk.evaluate-no-response.v1`, `notification.digest.v1`. Изменение формы
  события — новая версия, а не правка старой.

## 8. Ключевые архитектурные решения (ADR)

Полный индекс — `docs/adr/README.md`. Группировка по темам:

- **Форма и платформа:** 0001 модульный монолит; 0002 отдельные процессы из
  одного репозитория; 0003 PostgreSQL как источник истины; 0011 платформа Go;
  0012 REST на net/http и chi; 0013 pgx и SQL без ORM; 0014 направление
  зависимостей внутрь; 0015 UUIDv7 и UTC; 0016 точные деньги; 0017 JSONB
  только для расширяемых данных.
- **Организации и доступ:** 0018 организация — граница арендатора; 0019
  целостность арендатора в PostgreSQL; 0020 непрозрачные серверные сессии;
  0021 авторизация через разрешения членства; 0032 троттлинг входа в
  PostgreSQL; 0034 роли PostgreSQL и fail-closed контекст RLS; 0041
  реализация RLS через роли пула и усиление периметра (уточняет 0034:
  контекст ставится `set_config` хуком пула, а не `SET LOCAL`; платформенный
  обход — предикатом политики, а не атрибутом `BYPASSRLS`).
- **Приём данных и переписки:** 0004 сначала сохранить внешнее событие; 0005
  сырые данные отдельно от интерпретации; 0006 переписки отдельно от
  возможностей; 0024 канало-независимые коннекторы; 0025 короткая атомарная
  транзакция вебхука.
- **Фоновая обработка:** 0023 записи идемпотентности; 0026 очередь заданий с
  арендой; 0027 транзакционный outbox; 0028 SSE только как сигнал
  инвалидации; 0029 уведомления отдельно от попыток доставки; 0037 политика
  уведомлений.
- **Риски и деньги:** 0007 этап возможности отдельно от риска; 0035 явная
  единица порога риска (заменён ADR 0043); 0043 пороги правил — константы
  бизнес-времени, порог `NO_RESPONSE` — поле точки, таблица конфигурации
  отложена до измеренной потребности; 0038 обратная связь, окно точности и
  ML-согласие; 0039 базовая аналитика по необработанным фактам.
- **AI:** 0008 AI ограничен семантическими фактами; 0009 асинхронный вывод;
  0010 одноразовые неавторитетные узлы; 0030 исходящая pull-модель; 0031
  проверка результата и свежесть; 0033 явный список организаций для узла;
  0036 одно ожидающее задание на переписку.
- **Эксплуатация:** 0040 платформенное администрирование; 0042 нагрузочное
  испытание в процессе.

## 9. Политика изменений

Изменение формы системы, границ модулей, направления зависимостей, политики
источника истины или способа общения модулей требует принятого ADR до
реализации (`ARCHITECTURE.md`, «Change policy»). Технологии из списка
запретов не вводятся «временно». Новый модуль, новое прямое чтение чужой
таблицы, новый процесс — всегда через ADR с описанием измеренной
потребности, альтернатив, эксплуатационной цены и плана отката.
