# LidRadar: исправление High-проблем документации

Редакция: 2026-10-05. Работа выполнена по 20 High из предыдущего аудита:
исправлены противоречивые инструкции, правила готовности и схема сопровождения.
Это изменение документации, не исправление отсутствующего в комплекте
продуктового кода и не разрешение на production.

## Уточнение после подключения репозиториев, 2026-10-06

Исходные выводы ниже относятся к документационному snapshot. В рабочем
репозитории доступны код, OpenAPI, CI, manifest и реальные v6-отчёты;
текст об их отсутствии не описывает нынешнее окружение. Проверка выявила,
что ожидаемые функции нового Notion-сборщика не были перенесены: все 10
тестов сначала падали. Сборщик восстановлен и проверен в текущем цикле.
SLA Radar 30 секунд утверждён владельцем; H-04 оставлен открытым по его
явному решению. Полная матрица релевантности и исправлений:
[техническая сверка H-01…H-20](HIGH_REVIEW_2026_10_06.md).

## Граница результата

- **Исправленный комплект:** действующий вход, единый канон, согласованные
  денежные/API/AI/эксплуатационные правила, полный реестр зависимостей,
  воспроизводимые производные страницы и пакеты.
- **История:** первоначальный аудит и результаты старых прогонов сохранены;
  их числа не выдаются за новые проверки. Опасные эксплуатационные примеры
  исправлены с датированной оговоркой.
- **Техническое закрытие:** все применимые продуктовые проверки требуют
  отдельного доказательства по [release gates](RELEASE_GATES.md).
  Backend/frontend runtime, мигратор, CI и машинный OpenAPI в переданном
  комплекте отсутствуют.
- **Не принятые решения:** сроки retention и численный freshness SLA нельзя
  безопасно придумать редакторской правкой. Для них установлен
  `BLOCKED_DECISION`, а для проверки реализации `REQUIRED_NOT_VERIFIED`.
- **Notion:** исправлена локальная подготовка. Рабочее пространство не
  создано, страницы не импортированы, доступы не изменены.

Исходный аудит относится к source snapshot
`0e4b67ab6e780e1756f577379d885ff8be3b7342`; исправления начаты от
документационного commit `31a1f83ead544d8f40972c3caad9635c46e1a8d4`.
Идентификаторы относятся к репозиторию документации, не к build приложения.

## Денежные факты и аудит

<a id="h-01"></a>
### H-01: ключ идемпотентности и неизвестный результат

- **Исправлено:** удалена рекомендация автоматически повторять конфликт
  новым ключом. После отправки body/key неизменяемы; timeout, reload,
  cancel и logout не отменяют возможный commit. Потерянный draft не
  разрешает слепую повторную запись, а `ORGANIC` не служит обходом конфликта.
- **Согласовано:** [критические команды](../backend/12-critical-commands.md),
  backend API, frontend architecture/API/entities/sequence/quality и основное ТЗ.
- **Остаётся:** backend/frontend/QA подтверждают lost response после commit,
  replay, reload и отсутствие двойной выручки в RG-MONEY.

<a id="h-02"></a>
### H-02: Action закрытого Risk

- **Исправлено:** одна матрица: новый Action терминального Risk возвращает
  `409 RISK_CLOSED`, точный replay успешного запроса возвращает `200`
  даже после закрытия; несовпадающий body остаётся конфликтом.
- **Согласовано:** спецификация, модули, backend/frontend API, ТЗ,
  последовательности и исторический QA. Проверка статуса проводится с
  блокировкой, без повторной записи Action и аудита.
- **Остаётся:** runtime, машинный OpenAPI и гонка Action/close в обоих
  порядках требуют проверки; текст QA не объявляет дефект исправленным в коде.

<a id="h-03"></a>
### H-03: двойной submit

- **Исправлено:** [QA](../front-end/09-qa-adversarial-2026-09-25.md) больше
  не теряет открытый High среди завершённых работ. Требуется synchronous
  in-flight guard до первого `await`, а не только disabled после запроса.
- **Приёмка:** double click во время async validation, Enter+click,
  задержка 1,5 с, один объект на намерение; денежный путь дополнительно
  защищён серверной идемпотентностью.
- **Остаётся:** исправление приложения и повторный E2E. Новое ограничение
  уникальности имени услуги не выдумывается как замена исправлению submit.

<a id="h-04"></a>
### H-04: post-commit аудит

- **Исправлено:** вместо общей гарантии введена
  [матрица атомарности](../backend/12-critical-commands.md#audit).
  Денежные факты, consent и admin-команды отделены от исторического
  post-commit компромисса остальных критических операций.
- **Согласовано:** модули, безопасность, надёжность, спецификация, ТЗ,
  глоссарий и датированное уточнение ADR 0041.
- **Остаётся:** fault injection и доказательство устойчивого следа по
  каждому классу. Новый технический способ аудита не считается принятым ADR.

## Восстановление и защищённое развёртывание

<a id="h-05"></a>
### H-05: резервное копирование и RPO

- **Исправлено:** пример ежедневного production-backup вместо RPO 15 минут
  удалён. Учитывается возраст пригодной независимой точки, включая время
  создания, передачи и неуспешные попытки.
- **Согласовано:** [полный DR runbook](../runbooks/backup-restore.md),
  эксплуатация, надёжность и ТЗ.
- **Остаётся:** выбор и измерение пригодного механизма, алерты и реальный
  restore drill по RG-DR; расписание само по себе RPO не доказывает.

<a id="h-06"></a>
### H-06: восстановление на чистом хосте

- **Исправлено:** recovery set включает данные, global roles/grants,
  ключи, конфигурацию, совместимые образы и состояние удаления.
  Роли готовятся до восстановления зависимых объектов; старый migration
  journal не создаёт отсутствующие роли автоматически.
- **Приёмка:** новый кластер, проверка ключей/decrypt, RLS и tenant reuse,
  money loop, фоновые процессы и интеграции; schema/count smoke недостаточен.
- **Остаётся:** реальное учение. При отсутствии прежнего ключа используется
  `RESTORE_BLOCKED`, а не генерация замены для существующего ciphertext.

<a id="h-07"></a>
### H-07: откат и строгая схема

- **Исправлено:** аддитивная миграция не объявляется достаточным условием
  rollback к старому binary. Нужна проверенная матрица build/schema,
  иначе forward-fix либо восстановление совместимого recovery set.
- **Согласовано:** DR, эксплуатация, модель данных, ADR 0045 и общие
  правила чтения rollback-разделов ADR.
- **Остаётся:** тест совместимости и времени восстановления. Удаление
  migration journal, подмена checksum и обход readiness запрещены.

<a id="h-08"></a>
### H-08: RLS при аварии

- **Исправлено:** опасный rollback через снятие RLS исключён из
  production-инструкций ADR 0034 и ADR 0041. Прикладные проверки не подменяют
  обязательную изоляцию строк.
- **Дополнительно:** старый recipe RLS в ТЗ согласован с pool hooks и
  role predicate ADR 0041, без неподтверждённого `BYPASSRLS`.
- **Остаётся:** матрица tenant attacks и restore под реальными ролями;
  диагностика в изолированной копии не считается восстановлением production.

<a id="h-09"></a>
### H-09: ключ интеграций и передача токена

- **Исправлено:** каноническое имя `LIDRADAR_INTEGRATION_ENCRYPTION_KEY`
  согласовано в ADR, безопасности и эксплуатации; старое альтернативное
  имя не объявляется alias. Secure-connect flow и операторский helper
  больше не представлены взаимоисключающими инструкциями.
- **Приёмка:** config loader, чистая установка, write-only токен, отсутствие
  секретов в логах/хранилищах клиента, decrypt после restore прежним ключом.
- **Остаётся:** проверка конкретного build по RG-DEPLOY.

<a id="h-10"></a>
### H-10: reverse proxy и IP

- **Исправлено:** добавлен [deployment-контракт proxy](../runbooks/proxy-deployment.md):
  доверенная цепочка, закрытый прямой доступ, anti-spoof, независимость
  клиентских IP и работа лимитов.
- **Согласовано:** backend API, безопасность, эксплуатация, load runbook.
  Не выдумана отсутствующая env-переменная доверенных прокси.
- **Остаётся:** сверка механизма приложения/edge и реальные bypass,
  shared-IP, multi-instance и rate-limit тесты.

## Данные, AI и правила риска

<a id="h-11"></a>
### H-11: отзыв ML-согласия

- **Исправлено:** историческая `dataset_eligible` отделена от действующего
  разрешения на новую партию. Перед передачей повторно проверяются consent,
  цель, сроки и отсутствие отзыва/удаления; ещё не переданные партии отменяются.
- **Согласовано:** [жизненный цикл](../backend/13-data-lifecycle.md),
  ADR 0038, спецификация, ТЗ, модули, безопасность, frontend и глоссарий.
- **Остаётся:** grant → feedback → revoke → export и гонка отзыва с передачей.
  Документы не заявляют, что реальные данные уже экспортировались.

<a id="h-12"></a>
### H-12: retention

- **Исправлено:** создана единая матрица классов данных, начала отсчёта,
  purge/обезличивания, связей, backup, offboarding и повторного удаления
  после восстановления. Пустое значение не означает бесконечность или ноль.
- **Не закрыто:** конкретные сроки и исключения имеют `NOT_APPROVED`;
  владелец данных должен утвердить значения. Логические config keys не
  выдаются за реализованные env-переменные.
- **Остаётся:** решение, реализация purge и тесты RG-DATA. Эта High
  не может быть полностью устранена редакторской правкой.

<a id="h-13"></a>
### H-13: freeze модели

- **Исправлено:** текущий кандидат v6/400 GOLDEN + 100 DEV больше не
  называется подтверждённым `FROZEN`. Prompt v6, temperature 0.2 и
  presence penalty 0 согласованы с действующей спецификацией; остальные
  параметры берутся из того же проверенного manifest, не наследуются из v5.
- **История:** v5/60 golden, прежние latency/VRAM/quality сохранены в
  [датированном отчёте](../roadmap/STAGE_15_REPORT.md), не перенесены на v6.
- **Остаётся:** полный tuple, машинный manifest/report, dataset audit и
  новый benchmark с текущим validator на целевом оборудовании.

<a id="h-14"></a>
### H-14: неизменяемый AI snapshot

- **Исправлено:** LR-BE-RM-006 согласован с ADR 0036. Уникальность действует
  для `PENDING/RETRY`, не для `LEASED/RUNNING`; queued update переносит
  цельный более новый snapshot, не только revision.
- **Приёмка:** claim 5 → enqueue 7 → complete 5, out-of-order enqueue,
  retry и starvation; выданная инструкция не перезаписывается.
- **Остаётся:** DB/concurrency tests того же build в RG-AI.

<a id="h-15"></a>
### H-15: таблица порогов риска

- **Исправлено:** обязательный DDL отменённой `risk_policy_configs`
  удалён из RM-002/RM-014, deferred schema в спецификации согласована.
  Все пять правил используют business time по ADR 0043.
- **Приёмка:** настройки Location для NO_RESPONSE, versioned constants
  остальных правил, конец дня, выходные и timezone/DST; новая таблица
  или calendar-time требуют нового решения.
- **Остаётся:** соответствие кода и тестов; старый Proposed/Superseded
  рецепт не возвращается в реализацию автоматически.

## Актуальность, доказательства и публикация

<a id="h-16"></a>
### H-16: потеря NOTIFY при живом SSE

- **Исправлено:** статус полного закрытия заменён на `PARTIALLY_CLOSED`.
  Описанное восстановление buffer overflow не покрывает потерю до хаба.
  Каталог событий ТЗ согласован с Risk invalidation и `resync.required`.
- **Не закрыто:** численный freshness SLA остаётся `BLOCKED_DECISION`,
  автоматическое восстановление в его пределах требует реализации/проверки.
  Heartbeat, focus и ручной refetch не объявлены этой гарантией.
- **Остаётся:** RG-SSE, включая несколько API, LISTEN recovery, stale UI
  и ограничение нагрузки. Backend/frontend readme, API, reliability,
  sequence/backlog и ADR 0044 согласованы по этой границе.

<a id="h-17"></a>
### H-17: пропущенные DB-тесты

- **Исправлено:** обязательный режим должен падать при missing/unreachable
  PostgreSQL, setup failure или неожиданном skip. Проверка наличия URL и
  поздний migration smoke не заменяют выполненные сценарии.
- **Согласовано:** testing, Codex rules и Definition of Done; обязательны
  machine-readable test events, counts и причины skips.
- **Остаётся:** исправление/проверка helper и CI, отрицательный запуск с
  недоступной БД, затем успешный прогон полного обязательного набора.

<a id="h-18"></a>
### H-18: необоснованная ёмкость

- **Исправлено:** отозваны выводы «запас > 100×», проценты GPU и суточная
  ёмкость из обратных p50/p95; исторические измеренные числа сохранены.
  Inline-описание webhook согласовано с persist-first; старая измерительная
  граница помечена требующей сверки по коду.
- **Согласовано:** отчёт этапа 25, эксплуатация, надёжность, спецификация
  и [нагрузочный runbook](../runbooks/capacity-test.md).
- **Остаётся:** текущий mixed-workload через edge с реальным AI, actual
  throughput, skew, soak, burst/recovery, DB budget и утверждёнными SLO.

<a id="h-19"></a>
### H-19: воспроизводимая готовность выпуска

- **Исправлено:** введены [точка входа](../README.md), единые статусы,
  владельцы по ролям, release manifest и обязательные gates. Битые переходы
  к пяти отсутствующим целям заменены явными записями
  [реестра зависимостей](EXTERNAL_ARTIFACTS.md), без фиктивных контрактов.
- **Не закрыто:** реальные OpenAPI, model manifest/report, код и новые
  продуктовые проверки не предоставлены. Недостающая живая Telegram-матрица
  явно блокирует готовность общего выпуска.
- **Остаётся:** связать фактические артефакты одного release и пройти gates.
  Рабочая навигация не означает самодостаточность продуктового комплекта.

<a id="h-20"></a>
### H-20: полнота и единый канон миграции

- **Исправлено:** расширенный глоссарий перенесён в канон; 14 старых
  Notion-представлений генерируются односторонне из актуальных источников.
  Полные ADR, frontend, runbooks, ТЗ и история учитываются в manifest,
  а не заменяются кратким backend-обзором.
- **Сборка:** сохраняет происхождение всех 193 исходных материалов,
  различает страницы, вложения, инструменты, историю и производные версии;
  проверяет ссылки, anchors, LFS, hashes и повторную генерацию.
  Старый 18-элементный архив сохранён отдельно как исторический.
- **Не выполнено:** реальный импорт, map page IDs, проверка Notion links,
  Mermaid, прав и обратного экспорта. Переимпорт с удалением старых страниц
  запрещён как штатная синхронизация; правила в
  [инструкции переноса](../notion/README.md).

## Проверка и дальнейшее закрытие

### Локальная приёмка

Проверка выполнена на исправленном комплекте, а не только на выбранных
страницах. Результаты документируются отдельно от продуктовых gates:

| Проверка | Результат |
|---|---|
| Текущий корпус | 119 Markdown-документов, 207 исходных материалов с учётом новых правил, истории и инструментов |
| Локальные ссылки | 743 проверены, ошибок нет |
| Ссылки на разделы | 178 anchors проверены, ошибок нет |
| Исходный аудит | Все 193 исходных материала имеют disposition и цель в manifest |
| LFS | Неполученных указателей вместо исходных данных нет |
| Производные представления | 14 страниц, повторная генерация даёт zero diff |
| Импортируемые страницы | 105 канонических/исторических страниц; 105 постоянных source IDs, без выдуманных Notion page IDs |
| Import payload | 183 материала в двух партиях, каждый включён ровно один раз; служебные manifest повторяются намеренно |
| Source handover | 209 ZIP entries: 207 исходных материалов и два служебных отчёта; SHA-256 всех исходных payload проверены |
| Тесты сборщика | 10 тестов пройдены, включая отрицательные случаи битой ссылки/anchor, незакрытого code fence и stale output |
| Переносимость | Сборка из распакованного source-пакета без Git и внешних библиотек успешна; все пять архивов побайтно совпали |
| Чистота diff | `git diff --check` без ошибок |

Рендер Mermaid в Notion и фактический перенос в workspace не проверялись.
Прежние схемы производного издания сохранены в историческом архиве, а
действующие Markdown-диаграммы остаются в канонических источниках.
Полные source/import ZIP превышают настроенный лимит одиночной загрузки;
для пилота подготовлены отдельные партии, но не выполнен их upload.

### Что ещё требуется

Локальные проверки относятся только к документам и инструменту упаковки.
Продуктовые тесты, DR, нагрузка и GPU benchmark не запускались из этого
комплекта; результаты сборки не переводят соответствующие gates в `PASS`.

Для продолжения техническому владельцу нужны две группы входов:

- **Решения:** сроки и исключения retention, численный freshness SLA,
  ответственные за приёмку и согласованный workload.
- **Артефакты:** репозиторий и build приложения, OpenAPI, миграции/CI,
  AI manifest и dataset/report, стенд и контролируемые Telegram-аккаунты.

Следующий технический шаг: пройти RG-MONEY, RG-DR, RG-DEPLOY, RG-DATA,
RG-AI, RG-SSE, RG-TESTS, RG-CAPACITY и RG-EXTERNAL на одном versioned
release. Миграцию в Notion принимать отдельно, только после пилотного импорта.
