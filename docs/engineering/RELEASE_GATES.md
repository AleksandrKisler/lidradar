# Обязательные проверки перед выпуском

Исходное состояние на 2026-10-05: `NOT_VERIFIED`.
Техническая сверка 2026-10-06 и доказательства: [HIGH_REVIEW](HIGH_REVIEW_2026_10_06.md). Исправление документации не означает
нового прохождения перечисленных проверок; пустое доказательство не считается успехом.

## Manifest выпуска

До допуска должны быть заполнены: backend commit/image digest, frontend commit/build,
версия и hash миграций, OpenAPI hash, AI release tuple при включённом AI,
версия конфигурации без секретов, среда, дата и ответственные за проверки.
Каждый результат ниже связывается с этим manifest.

Для заполнения предоставлен [шаблон manifest](RELEASE_MANIFEST.template.json).
Значения `null`, пустые evidence и `NOT_RUN` намеренно не заменены выдуманными
версиями: шаблон не является разрешением на deploy и не считается заполненным
release-артефактом.

<a id="rg-money"></a>
## Денежные факты и действия

Связанные High: H-01, H-02, H-03, H-04. Владелец: backend/frontend/QA;
статус: `REQUIRED_NOT_VERIFIED`.

- Потеря ответа после commit, двойная отправка, reload и изменение формы
  не превращают одно намерение в два RevenueEvent.
- Новый Action запрещён в терминальных статусах; точный replay успешного
  Action возвращает сохранённый результат, в том числе после закрытия.
- Гонка Action/close проходит в обоих порядках, без лишних ключей и аудита.
- Двойной submit создания услуги/точки, включая задержку 1,5 с и асинхронную
  валидацию, не создаёт дубликат на одно намерение.
- Матрица атомарности аудита подтверждена fault injection по каждому
  критическому классу команд; post-commit исключения не названы гарантией.

<a id="rg-dr"></a>
## Восстановление и обновление

Связанные High: H-05, H-06, H-07, H-08. Владелец: эксплуатация/backend;
статус: `REQUIRED_NOT_VERIFIED`.

- На чистом хосте и новом PostgreSQL-кластере восстановлены роли, данные,
  политики, grants, ключи и совместимая сборка.
- Измерены фактические `RPO <= 15 min` и `RTO <= 4 h`, включая время до
  независимой пригодной копии, а не только локальное создание дампа.
- После восстановления проходят RLS, денежный путь и фоновые процессы.
- Rollback/forward-fix проверен по матрице схемы и сборки, без удаления
  migration journal, подмены checksum, снятия readiness или отключения RLS.

<a id="rg-deploy"></a>
## Конфигурация и периметр

Связанные High: H-09, H-10. Владелец: эксплуатация/backend/security;
статус: `REQUIRED_NOT_VERIFIED`.

- Имя ключа шифрования сверено с конфигурационным кодом и чистой установкой;
  недокументированный alias не предполагается.
- Write-only передача bot token соответствует ADR 0045, значения не
  попадают в логи, клиентское долговременное хранилище или документацию.
- Доверительная цепочка proxy проверена: прямой обход закрыт, подделанный
  forwarded header не обходит лимит, разные клиенты не превращаются в один IP.

<a id="rg-data"></a>
## Согласие и жизненный цикл данных

Связанные High: H-11, H-12. Владелец: владелец данных/backend/AI.
Статус: `BLOCKED_DECISION` для значений retention и `REQUIRED_NOT_VERIFIED`
для исполнения утверждённой политики.

- Утверждены сроки по каждому классу, начало отсчёта, purge/обезличивание,
  исключения, резервные копии и восстановление после удаления.
- Grant → feedback → revoke → новый export не включает отозванные данные;
  гонка отзыва с передачей экспортной партии обработана.
- Неизменяемый `dataset_eligible` хранит историю, а не бессрочное разрешение.
- Реальные клиентские данные не включаются в новые ML-наборы до прохождения
  этих проверок; текущие benchmark-наборы остаются синтетическими.

<a id="rg-ai"></a>
## AI и правила риска

Связанные High: H-13, H-14, H-15. Владелец: AI/Risk/QA;
статус: `REQUIRED_NOT_VERIFIED`.

- Один tuple связывает веса, prompt v6, schema/validator, параметры,
  dataset hash, оборудование и все обязательные метрики.
- Старый отчёт по v5/60 golden не подтверждает v6/400 golden.
- Claim ревизии 5, поступление ревизии 7 и завершение старой инструкции
  не применяют устаревший результат как свежий.
- Дедупликация меняет только `PENDING/RETRY`; leased/running snapshot неизменяем.
- Пять правил используют бизнес-время согласно ADR 0043; календарное время
  или конфигурационная таблица не вводятся старым рецептом задачи.

<a id="rg-sse"></a>
## Актуальность Radar

Связанный High: H-16. Владелец: product/reliability/frontend/QA.
Максимальная устарелость **30 секунд** утверждена владельцем 2026-10-05
для online/visible Radar при доступном сервере. Safety refetch — каждые
15 секунд только для активных запросов выбранной организации, без отмены
идущего refetch и без запросов из hidden/offline вкладки. Возврат online/visible
вызывает немедленную сверку. Это реализованный механизм; полный RG-SSE остаётся
`REQUIRED_NOT_VERIFIED` до multi-API/LISTEN и нагрузочного прогона.
Число нельзя подменять интервалом heartbeat: это разные гарантии.

- Lost NOTIFY при живом SSE автоматически вызывает восстановление в пределах
  утверждённого срока, без клика, focus или смены online.
- Проверены несколько API, восстановление LISTEN, buffer overflow,
  `resync.required`, `risk.false_positive`, reconnect и tenant isolation.
- При недоступном REST показывается устарелость, но успешное обновление не
  обещается; после восстановления выполняется обязательная сверка.

<a id="rg-tests"></a>
## Обязательные тесты

Связанный High: H-17. Владелец: backend QA/CI;
статус: `REQUIRED_NOT_VERIFIED`.

В обязательном режиме отсутствие/недоступность PostgreSQL и ошибка подготовки
схемы являются failure, не skip. Пропущенные обязательные сценарии RLS, денежных
транзакций, аренды, свежести и crash recovery блокируют gate.

Артефакт прогона содержит список и число выполненных/пропущенных тестов,
не только exit code. Негативный тест с недоступной БД должен провалить этот job;
последующий успешный smoke миграций не заменяет пропущенные проверки.

<a id="rg-capacity"></a>
## Производительность

Связанный High: H-18. Владелец: performance/AI/эксплуатация;
статус: `REQUIRED_NOT_VERIFIED`.

Нужен текущий mixed-workload прогон с сетью, TLS, proxy, rate limits,
реальным AI tuple и согласованным профилем нагрузки. Отчёт фиксирует arrival rate,
распределение tenant, длительность, ошибки, backlog, throughput, latency,
память и восстановление после пика; обратные p50/p95 не называются ёмкостью.

<a id="rg-external"></a>
## Внешние зависимости и Telegram

Связанный High: H-19. Владелец: технический владелец/Connector/QA;
статус: `REQUIRED_NOT_VERIFIED`.

Все необходимые объекты из [реестра артефактов](EXTERNAL_ARTIFACTS.md)
получены для одного выпуска. В [Telegram-матрице](../roadmap/TELEGRAM_SPIKE_REPORT.md)
подтверждены контролируемые входящее/исходящее сообщения, edits/deletes/вложения,
десять повторов, устойчивые ID после reconnect, `/start` и реальная доставка.

Старое наблюдение подключения бота не закрывает полный сценарий. Данные
чужих реальных переписок без согласованного основания для проверки не используются.

<a id="rg-docs"></a>
## Документация и упаковка

Связанный High: H-20. Владелец: документация;
статус определяется отдельным отчётом сборки, не состоянием runtime.

Все исходные материалы имеют судьбу в manifest; машинные зависимости названы
явно; ссылки проходят локальную проверку; производные страницы совпадают с
каноном; ZIP не содержит LFS-указателей вместо данных. Проверка внутри Notion,
прав и обратного экспорта остаётся отдельной приёмкой после реального импорта.

## Локальное подтверждение 2026-10-06

RG-TESTS выполнен локально для source hash из [summary](evidence/2026-10-06/db-summary.json),
с отдельными отрицательными проверками. RG-DOCS-LOCAL проходит builder/check и
unit tests. RG-MONEY и RG-SSE имеют проверенные части, но не считаются целиком
закрытыми: H-04 оставлен открытым, а deployment/E2E проверки перечислены в
[матрице сверки](HIGH_REVIEW_2026_10_06.md). Остальные production gates сохраняют
указанные выше ограничения. Эти результаты не заполняют автоматически шаблон
production release manifest и не дают разрешения на deploy.
